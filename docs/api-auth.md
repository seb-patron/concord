# Authentication API

CLI, `concord start`, `concord land`, MCP, and the runner can load their connection credential from an owner-local profile file. Configure `CONCORD_CONFIG` or `~/.config/concord/profiles.json` with a default profile and entries containing `url`, an absolute `tokenFile`, and optional `tokenKey` for selecting a field from a JSON token file. Plain one-token files are also supported. Both files must be owned by the current user and have no group/world permission bits; use mode `600`. Resolution order is `CONCORD_TOKEN` > `--token-stdin` > `--profile NAME` > `CONCORD_PROFILE` > the profile file default, with `CONCORD_URL` overriding a selected profile's URL. `land` accepts `CONCORD_REVIEWER_TOKEN` or `--reviewer-profile NAME` / `CONCORD_REVIEWER_PROFILE` for the independent reviewer, which must resolve to a different principal. Missing profiles, unreadable token files, and insecure permissions report `PROFILE_NOT_FOUND`, `PROFILE_TOKEN_UNREADABLE`, and `PROFILE_PERMISSIONS`; diagnostics never include token contents. `concord whoami` calls `GET /v1/me` and prints the profile, URL host, principal ID, and roles.

`GET /v1/me` requires a bearer credential and returns the standard `{ "data": ..., "version": 0, "eventSeq": 0 }` envelope. Its `data` is exactly `{ "principalId": string, "tenantId": string, "roles": string[], "repoIds": string[] | "*", "expiresAt": number | null, "model": string | null }`; absent credentials return `401`. No token, token digest, or secret is returned. An `AUTH_TOKENS` entry may set `model` to a 1–64 character label using only ASCII letters, digits, `.`, `_`, `:`, `/`, and `-`; invalid labels cause `AUTH_CONFIG_INVALID` when the mapping loads. An absent label appears as `null` and is captured on new changes as `authorModel: null`.

When Access is configured, a request without an Authorization header can authenticate with `Cf-Access-Jwt-Assertion` or the `CF_Authorization` cookie. The Worker verifies the RS256 signature against the team's certs, audience, issuer, and time claims, then maps the email through trusted `humans`. Unknown emails return `403 HUMAN_NOT_MAPPED`; invalid assertions return `401 UNAUTHORIZED`. Bearer credentials take precedence. `GET /v1/session` accepts either method and returns `principalId`, `roles`, `authMethod` (`access` or `bearer`), and `expiresAt` in the usual envelope. Access sessions also include `logoutUrl`. Event payloads for Access actions contain `authMethod: "access"` and identify the actor by mapped principal ID.

Only `GET /v1/session/signin` needs a Cloudflare Access policy. It validates the assertion, sets a short-lived `concord_access` cookie scoped to `/v1` with `HttpOnly`, `Secure`, and `SameSite=Strict`, then redirects to `/`. The Worker accepts this cookie for subsequent API requests. `GET /v1/session/signout` clears it and redirects through the team's Access logout endpoint when configured. Access-authenticated writes require an `Origin` matching the request origin; bearer writes are unaffected.
