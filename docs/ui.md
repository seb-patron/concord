# Repository tracker

Once signed in, every repository opens on **Tracker**. The repository picker changes the active tracker; the Fleet desk and Inbox remain available in the repository navigation. The light tracker canvas is read-only for claim, check, review, queue, and landing state. It shows Ready to claim, Awaiting claim, Claimed, Checking & review, Queued, Blocked, and Landed so an existing draft or blocked entry never looks free. The milestone selector defaults to the first open milestone (or the first recorded milestone), and “All milestones” shows every issue. Filters show All, Ready, Held by agents, or Mine. Only an open issue without an active change appears Ready. A draft without a live lease appears Awaiting claim; a blocked entry shows its reason. Checking & review covers a checking change or queue entry, and a ready change that has completed inspection and awaits independent review. An admitted or reserved entry is Queued even when its change is ready. Manually closed issues leave the lanes; issues closed by landing appear Landed, as does an issue whose current change already merged even if its close event has not arrived. The Claimed lane uses the complete live `leases.heldItems` projection when available and shows each unit's holder, available model label, and time until expiry. Queue state uses the current change and admitted revision. Friction issues are excluded from the lanes.

Select a card to see its issue number, title, lane, holder, and timeline of related events, including carried verdict events resolved through approval history. Approval history loads on demand for the issue open in the drawer (at most its current and closing changes) and rendered Queued cards; a shared loader caps all surfaces at four in-flight requests and 10 pages per change, then says older approvals are not loaded. “Open issue” expands the issue body, labels, and milestone in the drawer. Owners and agents can edit issue titles, bodies, and labels there; the server checks the pinned issue version and authorization. **Working now** lists each holder with only their live units. The tracker polls `events?after=` through the existing app loop and refreshes the snapshot when the repository version advances. Cards and counts update without a page reload. It retains the last snapshot during a connection error and reports the error; an empty repository shows guidance.

The five **Swarm today** tiles expose supporting records when clicked. Agents working counts unique live lease holders, including leases claimed before midnight. Collisions avoided counts `lease.refused`; Stale main blocks counts `queue.entry_blocked` with reason `STALE_MAIN`; Approvals carried counts `verdict.carried`; Landed today counts linked changes in `queue.promotion_applied`. Main movement blocks stale entries in the current backend; it does not automatically rebase them. The app keeps at most 500 recent events and 40 evidence records per tile while incrementally counting the current day's events; initial backfill may span multiple polls. The desk's **Main: green** state means at least one landing was observed today.

The **Friction log** maps lease refusals, stale main blocks, verdict carry events, failed `runner.result` records — labeled by the job kind recorded in the snapshot's runner jobs (inspection, stack check, delta check, or promotion, with a generic label when the job is unrecorded) — check/queue failures, and retries to “When / What slowed us / Cost / Concord did.” It also shows issues labelled `friction`. An owner or agent can add a row, which creates a normal issue with that label and optional milestone. The tracker uses ordinary issue routes and no separate server store. Text from API records is inserted as text, never HTML. On phones the lanes scroll horizontally, the drawer moves below them, and controls have 44 px targets.

# Fleet desk

## Repository Code page

Choose a repository, then select **Code** in the repository navigation. **For humans** shows a directory browser pinned to the observed canonical `main` commit, a safely rendered subset of root `README.md`, live claim badges, latest recorded landing, About counts, and agents with active claims. Directory names open their children and file names preview bounded text. Missing main, README, and permission or read errors have explicit messages. Claims and work state are read-only here.

**For agents** shows the `repo_context` JSON envelope (`GET /v1/repos/:r/snapshot`) with credential-shaped strings shown as `[REDACTED]`, matching the MCP output filter's fixed patterns, and the root `AGENTS.md` plus immediate `agents/*.md` files when present. Token counts are estimates, based on text length. Agent documents can be opened on this screen. Human README and docs are kept out of this panel. The displayed clone command uses the existing read-only `repo clone` CLI route. Both audiences use the same light cards and remain usable on a phone.

The browser reads `GET /v1/repos/:r/tree`, `file`, and `readme`. Those routes accept an optional commit `oid`, reject unsafe paths, and return text only within 64 KiB. When the snapshot has no observed OID yet, the page resolves current canonical `main` through the content routes; later reads stay pinned to the returned OID while the snapshot continues to refresh for live state.

For a local preview, run `npm ci --no-audit --no-fund`, then `npm run dev -- --persist-to .wrangler/state/local-ui`. Open `http://127.0.0.1:8787/`.

Open the deployed `web/` page. The UI first checks `/v1/session`; with a Cloudflare Access session it opens the desk and shows the mapped principal and Access sign-out link. Without one, Concord explains leases, exact-head checks, and bisection, then offers a password-type token field. The token stays in this tab's JavaScript memory. Sign out clears it. A read-only demo button appears only if the host explicitly sets `window.CONCORD_DEMO_VIEWER_TOKEN` (and optionally `window.CONCORD_DEMO_REPO_ID`) before `app.js` loads; there is no bundled demo token.

When `/health` reports `accessSignIn: true`, signed-out visitors also see a “Sign in with Cloudflare Access” link. It opens the path-scoped Access login and returns to the UI without copying a token. Token sign-in errors include the browser's redacted network message; token-shaped text is removed. Pasted tokens containing spaces, line breaks, or non-ASCII characters are rejected locally with the character position.

After sign-in, choose a repository in the header. The desk shows live counts, a work board, agents, leases, and the merge queue. Select a change for its head, units, actions, and approval history. The change details also show findings and repair state, runner health, history availability, and related event evidence; the Fleet column carries a compact Runners line. An Inbox decision preserves its title, reason, evidence, and approval history beside its actions, and opens the same change details. The Inbox groups isolated bisection culprits, lease refusals, and published changes awaiting a verdict. Other diagnoses keep their honest labels: interaction set, dependency group, red baseline, or inconclusive. The UI shows a model only when the API supplies `authorModel` or `model` (`web/app.js`).

The Milestones screen lists each milestone's title, state, due date, plain-text description, and issue and landed-change progress. It shows 50 at first and offers the remaining milestones on demand. Owners and agents can create milestones by default; owners can restrict creation to owners with the permission control. The form is hidden from viewers and users without creation permission.

| Fleet desk area | Evidence shown now | Honest fallback |
| --- | --- | --- |
| Summary and Work | Snapshot changes and leases; landings and red events from observed event pages | Empty work guidance and unknown main state when no evidence exists |
| Fleet and runner health | Agent cards from changes; runner summary and health from the runners projection | “No runners reported” or an explicit unavailable state |
| Merge queue | Ordered entries, blocked reasons, diagnosis, and bisection results from the queue projection | Empty queue guidance; inconclusive diagnoses remain labelled inconclusive |
| Change details | Findings rounds, runner health, paginated verdict provenance, and related events | Permission or unavailable messages; History explicitly says no replay dataset ships |
| Inbox | Decisions derived from snapshot and event evidence | No alert when there are zero decisions |

This mapping follows `web/app.js`, `web/views.js`, and the panels in `web/index.html`; it describes the current desk rather than a future feature slice.

At phone widths below 768 px, use Work, Fleet, Leases, and Queue tabs. The summary strip scrolls sideways; the page itself does not. The Inbox opens from the alert row.

The page polls `events?after=` each second and refreshes the snapshot when the repository version moves. A per-repository version high-water mark drops older event pages and snapshots so delayed responses cannot replace newer evidence. Actions remain disabled after a newer mutation or event version is observed until a snapshot at that version or later loads. A stale-version refusal raises that high-water mark to the server's current version, so an older snapshot already in flight cannot re-enable actions after refresh fails. Verdict history comes from `GET /v1/repos/:repo/changes/:change/verdicts`, following `nextCursor` for at most 10 pages per change, including direct and carried approvals with parent review and delta evidence. At most four requests run at once across the desk, Inbox, and tracker; history loads only for the selected desk change, selected Inbox item, issue open in the tracker drawer (current and closing changes), and rendered Queued cards. Longer histories display “Older approvals not loaded.” Merged changes stay cached for the session. `/v1/me` supplies the principal, roles, and repository allowlist when available. A `/v1/me` 404 leaves the role unverified and offers server-checked actions; the server still rejects missing roles and self-review. A verdict 403 reads “Approval history is visible to reviewers.” A 401 returns to sign-in; a 403 on a repository says the token cannot see it.

Field parity with the pre-rewrite panels (`025117692ae91d1dfd4b67cfc0cdb1e1833d97a3`): header retains repository, backend, principal, roles, and model; summary and main footer retain working agents, live leases, queue count, landings, main state, red events, and observed tip. Work cards retain intent, unit keys, author, model, status, and event age; Fleet agent cards retain agent, model, intent, and status; a separate Runners line summarizes the runners projection. Active leases retain unit, change ID, state, holder, countdown, and waiting requester; they also show intent, fence, absolute expiry, and conflict holder, intent, and expiry. Merge queue rows retain position, change ID and intent, state, admitted revision, backend sequence, and blocked reason, including landed and withdrawn rows in a collapsed history; diagnosis and blamed set remain visible. The bisection tree shows active job, members, diagnostic jobs, subsets, and outcomes. Change details retain change ID, agent, model, status, units, revision, base, head, actions, verdicts, findings, runner health, history availability, and events. Inbox retains decision kind, title, reason, evidence, and actions. In-progress input remains mounted during polling when the action is still eligible; a status transition removes ineligible actions. Successful mutation versions advance the high-water mark before refresh.

When `/v1/me` responds, actions follow its roles and principal; when it is absent, the server checks each attempted action. Ready changes remain visible for review or enqueue regardless of whether approval history is readable. The author enters the approved verdict ID supplied by the reviewer; the enqueue route checks that ID against the active revision and finding set. Claim accepts distinct unit keys and a nonempty intent for the author's draft or ready change. Claim, verdict, enqueue, and withdraw use a fresh Idempotency-Key; the latter three also use the current snapshot's expectedVersion. Enqueue needs current lease fences. A stale response refreshes the snapshot before another attempt. Empty repositories, work columns, fleet, leases, and queue show explicit guidance; a zero-decision alert is hidden.
## Path protections

Owners see a Path protection settings panel in the desk. Add a relative file path or import-style glob, choose `agents`, `human-approval`, or `human-only`, and optionally record a note. Remove clears one rule. The panel writes versioned repository settings. Changes awaiting owner approval show protected file paths, before/after modes and byte digests, and a bounded text preview from the inspected base and head in the change actions. The decision buttons become available after that preview loads; unavailable or binary previews require inspection through the repository diff. An owner enters an evidence digest and chooses **Approve** or **Request changes**; the decision applies to that inspected revision. The independent reviewer approval remains a separate step.

## Issues panel

The read-only Issues panel lists open Concord issues for the selected repository. It shows each issue's milestone, linked change status, and live held leases. The panel reads the coordinator snapshot's complete `leases.heldItems` projection (the paged `leases.items` list can stop at 100 records) and renders task text as plain text.
