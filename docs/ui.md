# Fleet desk

For a local preview, run `npm ci --no-audit --no-fund`, then `npm run dev -- --persist-to .wrangler/state/local-ui`. Open `http://127.0.0.1:8787/`.

Open the deployed `web/` page. With no token, Concord explains leases, exact-head checks, and bisection, then offers a password-type token field. The token stays in this tab's JavaScript memory. Sign out clears it. A read-only demo button appears only if the host explicitly sets `window.CONCORD_DEMO_VIEWER_TOKEN` (and optionally `window.CONCORD_DEMO_REPO_ID`) before `app.js` loads; there is no bundled demo token.

After sign-in, choose a repository in the header. The desk shows live counts, a work board, agents, leases, and the merge queue. Select a change for its head, units, actions, and approval history. The change details also show findings and repair state, runner health, history availability, and related event evidence; the Fleet column carries a compact Runners line. An Inbox decision preserves its title, reason, evidence, and approval history beside its actions, and opens the same change details. The Inbox groups isolated bisection culprits, lease refusals, and published changes awaiting a verdict. Other diagnoses keep their honest labels: interaction set, dependency group, red baseline, or inconclusive. The UI shows a model only when the API supplies `authorModel` or `model` (`web/app.js`).

| Fleet desk area | Evidence shown now | Honest fallback |
| --- | --- | --- |
| Summary and Work | Snapshot changes and leases; landings and red events from observed event pages | Empty work guidance and unknown main state when no evidence exists |
| Fleet and runner health | Agent cards from changes; runner summary and health from the runners projection | “No runners reported” or an explicit unavailable state |
| Merge queue | Ordered entries, blocked reasons, diagnosis, and bisection results from the queue projection | Empty queue guidance; inconclusive diagnoses remain labelled inconclusive |
| Change details | Findings rounds, runner health, paginated verdict provenance, and related events | Permission or unavailable messages; History explicitly says no replay dataset ships |
| Inbox | Decisions derived from snapshot and event evidence | No alert when there are zero decisions |

This mapping follows `web/app.js`, `web/views.js`, and the panels in `web/index.html`; it describes the current desk rather than a future feature slice.

At phone widths below 768 px, use Work, Fleet, Leases, and Queue tabs. The summary strip scrolls sideways; the page itself does not. The Inbox opens from the alert row.

The page polls `events?after=` each second and refreshes the snapshot when the repository version moves. A per-repository version high-water mark drops older event pages and snapshots so delayed responses cannot replace newer evidence. Actions remain disabled after a newer mutation or event version is observed until a snapshot at that version or later loads. A stale-version refusal raises that high-water mark to the server's current version, so an older snapshot already in flight cannot re-enable actions after refresh fails. Verdict history comes from `GET /v1/repos/:repo/changes/:change/verdicts`, following `nextCursor` through all pages, including direct and carried approvals with parent review and delta evidence. `/v1/me` supplies the principal, roles, and repository allowlist when available. A `/v1/me` 404 leaves the role unverified and offers server-checked actions; the server still rejects missing roles and self-review. A verdict 403 reads “Approval history is visible to reviewers.” A 401 returns to sign-in; a 403 on a repository says the token cannot see it.

Field parity with the pre-rewrite panels (`025117692ae91d1dfd4b67cfc0cdb1e1833d97a3`): header retains repository, backend, principal, roles, and model; summary and main footer retain working agents, live leases, queue count, landings, main state, red events, and observed tip. Work cards retain intent, unit keys, author, model, status, and event age; Fleet agent cards retain agent, model, intent, and status; a separate Runners line summarizes the runners projection. Active leases retain unit, change ID, state, holder, countdown, and waiting requester; they also show intent, fence, absolute expiry, and conflict holder, intent, and expiry. Merge queue rows retain position, change ID and intent, state, admitted revision, backend sequence, and blocked reason, including landed and withdrawn rows in a collapsed history; diagnosis and blamed set remain visible. The bisection tree shows active job, members, diagnostic jobs, subsets, and outcomes. Change details retain change ID, agent, model, status, units, revision, base, head, actions, verdicts, findings, runner health, history availability, and events. Inbox retains decision kind, title, reason, evidence, and actions. In-progress input remains mounted during polling when the action is still eligible; a status transition removes ineligible actions. Successful mutation versions advance the high-water mark before refresh.

When `/v1/me` responds, actions follow its roles and principal; when it is absent, the server checks each attempted action. Ready changes remain visible for review or enqueue regardless of whether approval history is readable. The author enters the approved verdict ID supplied by the reviewer; the enqueue route checks that ID against the active revision and finding set. Claim accepts distinct unit keys and a nonempty intent for the author's draft or ready change. Claim, verdict, enqueue, and withdraw use a fresh Idempotency-Key; the latter three also use the current snapshot's expectedVersion. Enqueue needs current lease fences. A stale response refreshes the snapshot before another attempt. Empty repositories, work columns, fleet, leases, and queue show explicit guidance; a zero-decision alert is hidden.
