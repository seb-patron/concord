# Fleet desk

For a local preview, run `npm ci --no-audit --no-fund`, then `npm run dev -- --persist-to .wrangler/state/local-ui`. Open `http://127.0.0.1:8787/`.

Open the deployed `web/` page. With no token, Concord explains leases, exact-head checks, and bisection, then offers a password-type token field. The token stays in this tab's JavaScript memory. Sign out clears it. A read-only demo button appears only if the host explicitly sets `window.CONCORD_DEMO_VIEWER_TOKEN` (and optionally `window.CONCORD_DEMO_REPO_ID`) before `app.js` loads; there is no bundled demo token.

After sign-in, choose a repository in the header. The desk shows live counts, a work board, agents, leases, and the merge queue. Select a change for its head, units, actions, and approval history. The change details also show findings and repair state, runner health, history availability, and related event evidence; the Fleet column carries a compact Runners line. An Inbox decision preserves its title, reason, evidence, and approval history beside its actions, and opens the same change details. The Inbox groups isolated bisection culprits, lease refusals, and published changes awaiting a verdict. Other diagnoses keep their honest labels: interaction set, dependency group, red baseline, or inconclusive. The UI never assigns a model unless the API provides `authorModel`.

At phone widths below 768 px, use Work, Fleet, Leases, and Queue tabs. The summary strip scrolls sideways; the page itself does not. The Inbox opens from the alert row.

The page polls `events?after=` each second and refreshes the snapshot when the repository version moves. A per-repository version high-water mark drops older event pages and snapshots so delayed responses cannot replace newer evidence. Verdict history comes from `GET /v1/repos/:repo/changes/:change/verdicts`, following `nextCursor` through all pages, including direct and carried approvals with parent review and delta evidence. `/v1/me` supplies the principal, roles, and repository allowlist when available. A `/v1/me` 404 leaves the role unverified and offers server-checked actions; the server still rejects missing roles and self-review. A verdict 403 reads “Approval history is visible to reviewers.” A 401 returns to sign-in; a 403 on a repository says the token cannot see it.

When `/v1/me` responds, actions follow its roles and principal; when it is absent, the server checks each attempted action. Ready changes remain visible for review or enqueue regardless of whether approval history is readable. The author enters the approved verdict ID supplied by the reviewer; the enqueue route checks that ID against the active revision and finding set. Claim accepts distinct unit keys and a nonempty intent for the author's draft or ready change. Claim, verdict, enqueue, and withdraw use a fresh Idempotency-Key; the latter three also use the current snapshot's expectedVersion. Enqueue needs current lease fences. A stale response refreshes the snapshot before another attempt. Empty repositories, work columns, fleet, leases, and queue show explicit guidance; a zero-decision alert is hidden.
