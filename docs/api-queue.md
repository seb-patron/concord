# Queue API and recovery runbook

Queue decisions live in one repository coordinator. Workers use `RepoStorage` only to read immutable commits and refs; checker and promoter jobs run through `runners.schedule`. A missing repos change view, findings gate, verdict gate, lease reservation, or runner scheduler blocks the dependent action.

## Routes and limits

| Route | Caller | Body or result |
| --- | --- | --- |
| `GET /v1/repos/:repoId/queue` | repository reader | Ordered entries, generation, stack members, diagnostic results, contest reasons, ticket, and final canonical SHA. |
| `POST /v1/repos/:repoId/queue/enqueue` | change author or owner | `{expectedVersion, changeId, verdictId, leaseFences}`. Requires an idempotency key. |
| `POST /v1/repos/:repoId/queue/withdraw` | change author or owner | `{expectedVersion, changeId, reason}`. Releases the queue reservation. |
| `POST /v1/repos/:repoId/contests` | owner | `{intentKey, intentText, unitKey, baseOid, profileId, childChangeIds:[a,b], verdictIds:[va,vb], leaseFences:[fa,fb]}`. Dispatch-lab only in v1; a generic policy returns `409 CONTEST_UNSUPPORTED_FOR_PROFILE`. Both children pass normal admission and share one reservation atomically. |

At most eight candidates are active. A composed stack has at most four. Entries use server event sequence order and a unique `entryId` for each admission. Admission moves an entry from `admitted` to `reserved`; stack scheduling moves it to `checking`. A completed entry becomes `landed`, `blocked`, `withdrawn`, or `failed`, and that transition releases its reservation. A confirmed old-ref failure returns `checking` to `reserved` for a fresh check. The queue checks the live lease and exact fences before scheduling and before issuing a promotion ticket; expired reservations block the entry. The queue waits up to two seconds after admission to coalesce candidates, then schedules an immutable `validate-stack` job. A contest schedules one child job for each of its two reserved candidates. The contest record owns their shared reservation, backed by the first child's fenced claim; each child record stores only its contest ID. Both children must present the same fenced units. Lease reservation and live checks consult the contest record, so an unselected child cannot use its own claim row. The winner remains reserved for stack scheduling; the loser becomes `failed` while the shared reservation remains live. Winner landing changes the contest to `landed`; winner blocking changes it to `blocked`. These transitions and the shared lease release occur in one transaction. Withdrawing either child, losing eligibility, or failing a contest job blocks the contest and releases the shared reservation once. A loser needs a fresh claim after the winner's terminal transition releases it. Contest creation rolls back if the shared reservation is unavailable.

Admission reads the exact ready revision and registered head/base/ref from the repos view. It requires lease fences for every verified unit, a findings gate with no open finding or pending repair round, and a verdict gate for the requested verdict and the same finding-set version. The verdict gate is responsible for independent reviewer and coverage checks. Every job and ticket records policy/profile pins. An approved candidate with an old canonical base may enter the queue for automatic rebase. Dependencies must already be admitted or merged; the stack planner includes only dependency-closed candidates. Any changed head, eligibility, or canonical main increments the queue generation and invalidates prior checks.

## Automatic rebase after main moves

When main changes, the queue keeps reserved entries and invalidates any older stack result. It schedules one `rebase-candidate` checker job for each stale change, in queue order. An entry based on a still active prerequisite waits for that prerequisite. The job pins the old candidate base/head, the new canonical OID, policy and profile, verdict, and a fresh ref in the candidate fork. It composes the candidate with the runner's declared unit merger, inspects the new revision, runs the pinned candidate check, and compares `git patch-id --stable` for the old and new base-to-head diffs. Only a passing result is published to the assigned candidate fork ref. A checker receives a write credential for that fork; it never receives a canonical write credential.

The coordinator checks the runner result, records revision N+1 on the same change, and carries the independent verdict with `carriedFrom:{sourceOid,method:"patch-id"}` when the patch IDs match. When patch IDs differ, carry is permitted only if the trusted table policy declares every changed row and the reviewed row bytes, modes, and paths remain equal. The new manifest and dependency scope come from the fresh inspection. The entry keeps its sequence and lease reservation. It must pass a new ordinary combined-stack check against the current main before any promotion ticket is issued. If review cannot carry, the new revision remains ready for review, the queue entry blocks with `REVIEW_REQUIRED`, and an open finding names the changed units.

An undeclared file conflict or divergent row edit blocks with `REBASE_CONFLICT`; a failing candidate check blocks with `REBASE_CHECK_<outcome>`. A failing combined-stack check of a single rebased change blocks with `REBASE_CHECK_FAIL` and records the check finding. These failures emit `queue.rebase_blocked` with the change ID, paths or units, and an issue reference when the change intent links one. Multi-change stack failures follow the ordinary diagnosis path before assigning blame. The trusted `queue.maxAutomaticRebases` setting defaults to five per change and may be set from 1 to 100. Exhaustion blocks with `REBASE_LIMIT`. One outstanding job per admission and target main prevents duplicate rebases; a newer main invalidates an older job. Successful rebase never skips the normal combined-tree gate.

For any trusted profile whose policy checker ID is not `dispatch-lab`, the queue builds a stack from eligible candidates in admission order, starting at the observed canonical base. Intent keys do not select a test scene. The runner composes the pinned candidate heads in job order and runs the profile's pinned checker on the composed commit. The job pins the policy and profile digests, canonical base, expected refs, candidate heads and order; its input digest covers those values. Generic stack jobs have no `caseId`. Generic contests, including those configured with score policies, are unsupported in v1 and are refused before reservation or job scheduling. For any checker, disjoint TSV row edits can merge when the trusted unit policy declares the file as a table. Undeclared file conflicts and divergent edits to the same declared row return `MERGE_CONFLICT`.

Only a policy with checker ID `dispatch-lab` uses the scripted demo case table. Its queue job carries the trusted `caseId` selected from the current demo stage and intent keys; an unplanned combination is rejected. The demo's case table remains strict and does not constrain other profiles.

## Failure isolation and arbitration

The baseline diagnostic uses `validate-stack` with `baseCheck: true` and no candidates. The runner checks the pinned canonical base alone. Other ordinary stack jobs require at least one candidate.

A red stack starts with a baseline check, then checks deterministic halves from the same canonical base. Subsets include prerequisites. Only a reproduced red singleton receives individual blame. Red baseline is `BASE_RED`; two green halves with a red whole are `INTERACTION`; inseparable prerequisites are `DEPENDENCY_GROUP`. After a singleton, all survivors are checked together before a ticket. Eight diagnostic jobs per generation is the limit; exhaustion is `INCONCLUSIVE`. A completed diagnosis blocks and releases every original member that has no promotion ticket, including members outside the final diagnostic subset. A second timeout or environment failure blocks and releases the affected admissions. The snapshot retains each subset, job ID, result, and confidence; events retain the same observations.

Contest results must share canonical base and checker, toolchain, oracle, environment profile, and policy pins. Named hard gates must pass before scoring. A score uses the policy's fixed denominator, so comparing matched byte counts is exact. Hard-gate policies choose the first valid green by server result sequence; equal scores choose the lower creation sequence. Non-comparable results block arbitration. The queue rejects a bad result digest before recording the result. Arbitration waits until both child results have passed processing and any required scratch checks. A timeout or environment error leaves its child unsettled while a retry is pending. A retry of an environment failure uses the same immutable input. A different retry outcome records `SUSPECTED_FLAKE` and stops automatic landing.

## Promotion and reconciliation

A green result is checked against the scratch ref and immutable commit/tree through `RepoStorage`. The queue rechecks main and each admission gate before it creates a durable ticket with expected old OID, checked new OID, generation, and frozen admission IDs, revisions, heads, verdicts, finding versions, policy/profile pins, and reservation fences. While pending or reconciling, related repository mutations return `409 PROMOTION_IN_PROGRESS`. The pending promoter may poll and use only its ticket job's heartbeat, credentials, and result routes. Runners must enforce the promoter role and claim fence. An empty-repo bootstrap uses an internal owner-authorized handoff from repos and a ticket with `expectedOldOid:null`; the promoter must conditionally require branch absence. All other tickets require ordinary change admission.

Readback examples for a ticket expecting `old=111…`, `new=eee…`:

| Canonical readback | Action |
| --- | --- |
| `eee…` | Mark the ticket applied and entries merged; record `eee…` as final canonical SHA, even if the promoter response was lost. |
| `111…` after timeout or an environment response | Keep the ticket and freeze in reconciliation. The queue may schedule one retry of the same ticket and expected old/new OIDs. A delayed first push may still arrive. |
| `111…` with definitive `OLD_REF` responses from every ticket attempt | Mark that ticket failed, release the freeze, and requeue the entries for a fresh check. An unresolved earlier attempt keeps the freeze. |
| Any third OID | Keep the freeze and require manual reconciliation. Do not issue another ticket. |

The queue never marks entries merged from a promoter response alone. `RepoStorage.resolveRef` must read back the exact checked new OID. The promoter performs Git ancestry validation and conditional push outside Workers; slice 05 supplies that execution and result dispatch. Slice 02 supplies the authoritative read-only change view and owner-only bootstrap route. Until those modules register their hooks, dependent queue paths fail closed.

After an exact readback confirms Concord's own promotion, its ticket members land and release their reservations. Other active entries retain their queue position and are rebased as needed. Ticket creation still verifies that each member's recorded base is current main or an earlier member's head whose dependency chain reaches current main. Reconciliation replay leaves terminal entries alone and cannot create a ticket from an obsolete check. `dependencyChangeIds` declares change-level prerequisites for stack ordering and admission; `dependencyKeys` belongs to policy unit definitions and describes unit-level dependencies.
