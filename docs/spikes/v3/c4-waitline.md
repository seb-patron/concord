# Wait-line prototype: automatic grant or fresh claim?

## Summary

This in-memory prototype compares two ways to handle a claim that must wait. Automatic mode grants the lease when the queue can serve the request. Fresh-claim mode opens a short priority turn; the agent must then make a new authenticated claim. The repaired model rejects a second writing hold while an agent has a live queued request, checks the change identity on retries and turn claims, and does not let an offline agent make a fresh claim.

At twenty-five agents, two hundred paired runs of the baseline produced a mean of 37.17 completed tasks with automatic grants and 22.00 with fresh claims. The respective 95% intervals were [36.36, 37.99] and [21.42, 22.57]. Mean calls were 97.17 [95.76, 98.57] and 116.84 [113.97, 119.71]. This is a small synthetic workload, not a prediction of production results. There is no interval for the difference between modes, and throughput does not decide the design.

The original wait-queue design grants using the credential checked when the request entered the line. A separate regression test shows that a credential revoked while waiting can still receive that automatic grant. The fresh-claim design checks authorization again at the turn claim. The source material recommends a fresh claim when the coordinator cannot authenticate and grant in one atomic operation. An atomic operation here means one all-or-nothing coordinator transaction. The supplied material does not establish whether Concord's planned coordinator can do both steps together, so that architecture question remains open.

## Terms and model

A **wait line** orders requests that cannot yet receive all their requested units. **First in, first out** means that earlier requests keep priority over later requests for any overlapping unit; unrelated units can proceed. A **lease** is a time-limited right to write named units. A **turn** gives a waiter brief priority but is not a lease. A **writing hold** blocks another writer until release, expiry, or first publication. A **published hold** remains attached to a change while it is being landed, but no longer blocks another writer. A **landing hold** is that same published lease during the landing phase.

A **unit** is one file or one named part of a file that a request wants to write. A **credential** is proof of an agent's identity. A **principal** is the identity associated with that credential. The real **authorization catalog** is the service that records whether delegated credentials are valid or revoked; this simulation uses a small in-memory substitute. **Revocation** makes a credential fail a later authorization check. A **request key** identifies one request attempt. Reusing the key with different units or a different change is rejected. A **task** may have several attempts and counts as complete only when work finishes and its lease is released.

The model uses a **monotonic clock**, meaning simulated time only moves forward. Its **event clock** advances in integer ticks shared by both modes. The one-transaction rule for claims means a multi-unit request is granted in full or not at all. A lease **fence** is a number that rises on each new lease so a storage system can reject writes from an old lease; fences are not implemented here, and this report makes no stale-write guarantee. **Estimated time of arrival** means an advisory estimate of when a wait may proceed; the model does not calculate one.

The model includes normalized file and named-part overlap, multi-unit claims, queue order, bounded wait and lease deadlines, retries, credential revocation, and publication and landing phases. Normalized means that equivalent path spellings are reduced to one identity. A whole-file unit overlaps a named part in that file; distinct named parts do not overlap. It forbids **hold-and-wait**: an agent with a writing lease cannot queue for another writing lease, and an agent with a live queued request cannot acquire another writing lease. Automatic advancement also skips a waiter who already has a writing lease. This prevents the modeled incremental-acquisition cycle by restricting acquisition; the model does not detect cycles or implement the separate cycle-refusal design.

The model does not expire credentials by age, verify real cryptographic proof, save state between runs, model simultaneous real transactions, map actual repository paths into units, connect to a real authorization catalog, or run a real landing queue. The automatic arm checks authorization at enqueue and intentionally does not check it again when granting. The fresh-claim arm checks authorization when the agent claims its turn.

## Deterministic checks

Eight scenario groups cover queue order and turn guards, simultaneous deadlines, offline claim rejection, the different revocation outcomes, retry and terminal recovery, queued hold-and-wait prevention, multi-unit expiry progression, and published holds. Assertions also check immediate advancement after cancelling a turn, successful progress after the holder expires while the wait remains live, payload reuse across different change identities, turn deadlines capped by wait deadlines, one grant event, and stale-turn rejection. Both modes test publication and landing while two published holds overlap on the same unit. A multi-unit waiter never receives a partial grant, and a later overlapping request cannot pass it.

## Seeded comparison

Each result cell uses two hundred seeds. A seed is a starting value that produces a reproducible schedule. Separate random streams prepare arrivals, crashes, credential revocations, and fresh-claim attempt behavior. Both modes replay the same scheduled arrivals and faults for each seed. One integer-tick event clock advances the run, so request handling does not advance other agents' deadlines.

Baseline cells use two, five, ten, or twenty-five agents, three planned tasks per agent, five shared units, a ninety-tick wait deadline, a twenty-four-tick lease, and a forty-five-tick turn. Each run observes one hundred ten ticks. A crash leaves an agent offline for the rest of that run; held leases expire, and offline agents cannot submit fresh claims. These are scenario settings, not recommended timeouts. A task attempt gets a new request key after a terminal wait or a lost lease. Completion is counted only at completed release.

The baseline assumes a two-tick request reaction and a sixty-percent chance of attempting a claim on each fresh-claim poll. A **reaction delay** is the time from a turn opening to the simulated client's next request. **Attempt probability** is the chance that the client makes that request when it polls. The sensitivity sweep changes turn length, reaction delay, and attempt probability on the same twenty-five-agent seed set. Results for every cell appear in the [generated output](../../../spikes/v3/c4/output.txt).

The revised design says a client must not poll more frequently than every two seconds. This is a minimum interval between polls; it gives no maximum reaction time and does not guarantee a request arrives within two seconds. The model's two-tick reaction is only one scenario assumption. Other reaction delays and attempt probabilities are included in the sweep.

**Completed tasks** counts useful finished work. **Online waiting grants** counts queued grants or turn claims made while the recipient is online at the grant event. **Waiting grants** counts all queued grants, including automatic grants to agents that went offline after queuing. **Calls** counts claim, release, and fresh turn-claim requests. **Wasted unit-ticks** integrates writing leases held by offline agents and open turns over the same fixed observation window in both modes; time beyond the window is not included. **Action latency** is the time from queue entry to grant for an online recipient. The reported ninety-fifth percentile is the value at or below which ninety-five percent of observed action latencies fall. **Revoked-credential grants** counts automatic grants whose credential was already revoked at the grant event; authorization is recorded at that event, not checked later.

At twenty-five agents in the baseline, the mean online waiting grants were 32.88 [32.01, 33.76] for automatic mode and 18.69 [18.14, 19.24] for fresh-claim mode. Mean wasted unit-ticks were 141.71 [135.67, 147.75] and 292.60 [286.41, 298.78]. Automatic mode averaged 3.31 [3.07, 3.54] grants after revocation; fresh-claim mode averaged zero. The results vary with all three swept settings, so they do not establish a generally faster or safer production design. The intervals use the normal-curve method to summarize uncertainty in each mean across the seed-level results; no interval was calculated for the difference between modes.

## Limits and sources

The workload is synthetic, uses five frequently requested units and a short fixed observation window, and assumes crashed agents never return. It does not model agents changing behavior in response to waits, real network delays, task acceptance checks, repair costs, saved queue state, updated change versions, a real authorization catalog, or checking an actual merged result. A confidence interval describes run-to-run variation under these assumptions; it is not a decision threshold. The experiment cannot answer whether the planned coordinator can authenticate and grant in one transaction.

The source designs read in full for this repair are:

- “Wait queue” design (source file: `v2-history/72-lease-wait-queue.md`): automatic queue grants, order, and limits.
- “Fresh-authentication wait turn” design (source file: `v2-history/116-lease-wait-v2.md`): a later authenticated claim, turn expiry, and queue limits.
- “Refuse deadlocking lease growth” design (source file: `v2-history/73-lease-deadlock.md`): cycle detection and yielding in a protocol that allows incremental claims.
- “Published leases stop blocking” design (source file: `v2-history/181-published-leases-stop-blocking.md`): the change from blocking writing holds to nonblocking landing holds.

The complete supplied Opus and Astra reviews, the complete delta review, and the four prototype files on this branch were also read. The source designs specify additional production behavior not modeled here: queue capacity, position, advisory arrival estimates, ownership and closing, force release, renewals, keeping a turn when capacity blocks a grant, and ensuring changes that touch the same units land one after another.
