# Concord v3 on our current Cloudflare setup

## Plain summary and recommendation

**Recommendation for our own repositories and agents:** keep Cloudflare for the existing website and, if useful, a thin application gateway. Build the v3 Git and SQLite core on a rented server with local bare Git repositories. Keep Artifacts for the live v2 deployment during migration, but do not make it v3's source of truth. A short-lived Artifacts workspace is an optional experiment, not a prerequisite. This is a recommendation for the MVP, not an approved hosting change. It follows v3's need for server-side Git landing and the documented Artifacts limits, not a claim that a production v3 benchmark has failed. The owner has said that leaving Artifacts is acceptable if it does not scale; the owner has **not** decided the new host. Selling a hosted service is outside this study.

The choice is most acute for the *largest individual repository*, not the count of repositories. Artifacts permits at most **1 GB per repository and 32 MB per file/blob**. The largest local Git directory in the supplied records is 542 MB, but local disk size does not prove its Artifacts size. A 500 MB to 1 GB import, a large push, and many simultaneous writers have not been tested. A v3 change is a server record, so v3 can remove v2's fork per change; retaining Artifacts as main Git storage still leaves the size ceiling and an undocumented concurrent-ref-update contract. See the supplied **Cloudflare Artifacts full documentation read** and [Artifacts limits](https://developers.cloudflare.com/artifacts/platform/limits/).

This study uses the current **Workers Paid** account, one `workers.dev` application and one Artifacts namespace. The owner screenshot shows 487 Artifacts repositories and a six-day partial billing cycle. It shows 1.07 million Durable Object requests and 2.21 billion rows read; Artifacts operation charges are not visible in the captured rows. V2 proves that Cloudflare serves our small pilot. It does not establish v3 capacity. Every forward-looking count and cost below is an **estimate** unless explicitly called a documented limit or a measured v2 observation.

## What the v3 design asks of a platform

Here a **Worker** is Cloudflare's request handler; a **Durable Object** is a named, single-threaded handler with a SQLite database; **Artifacts** is its Git-compatible repository service; **R2** is object storage. A **claim** records an agent's work on a file or function. **Land** means the server merges an approved change into the canonical `main` branch. A **repo actor** serializes metadata writes for one repository. A **revision** is one version of a proposed change; it need not be a Git fork.

The supplied **Concord v3 Architecture draft** proposes one server process with bare Git and SQLite on disk. It is a design, not deployed v3. Its default claims are shared; only selected paths are exclusive. That would reverse the owner's existing **exclusive lease decision (D-UNIT-1-EXCLUSIVE)**, so this report does not assume the policy is approved. The platform mapping works with either claim policy, but exclusive claims add wait-line pressure. The draft's server-side landing prototype correctly found nine conflicts among twenty synthetic parallel changes; it ran locally and proves neither Cloudflare throughput nor Artifacts compare-and-swap behavior.

We use `workers.dev` with **no zone**. The documented 100 MB upload cap applies to Free/Pro **zones**; the inputs do not establish the applicable `workers.dev` Git-upload cap. Never treat the zone figure as a proven cap or exemption for our hostname. If a future Git hostname is proxied through a Free/Pro zone, the 100 MB cap becomes relevant. A direct server Git hostname avoids that proxy cap but must provide its own TLS and access control. ## Three Git placements, one workload

The comparison assumes one new repository with **0.2 GB of retained Git history**, one revision per change, one claimed unit, one check and one land attempt per change, four full client clones and sixty incremental fetches per repository per month, and two browser API reads plus one event connection per repository per day. A light repository makes **one change/day** (30/month); a busy swarm makes **thirty changes/day** (900/month). Each option delivers the same logical actions, although the transport differs. Retries, red checks, agent model fees, source growth, backup versions and Git transfer bytes are excluded from the simple tariff. These are **workload estimates**, not v3 observations.

**A — Artifacts is canonical Git.** Keep a single Artifacts repository per logical repository. Agents may clone it; proposed file edits go to the v3 change API. A Git-capable server merges and pushes `main` back to Artifacts. The Durable Object holds metadata and events. This removes v2 forks but does **not** remove the need for a Git engine or establish an atomic ref update. A local Git cache must reconcile with the remote; a failed or racing push needs a new merge/check. The Artifacts binding cannot implement land alone. Artifacts remains the availability and size boundary for the source of truth.

**B — Artifacts only for short-lived work repositories.** Choose **server disk** as canonical Git, since bare Git plus SQLite on disk is the v3 draft's tested design shape. One Artifacts repository per task receives a baseline, the agent clones and pushes a candidate, the server fetches it, records a v3 change, lands to disk and deletes the task repository after a bounded retention window. R2 is plausible for immutable packs and backup, but the supplied R2 pricing/docs do not establish Git smart HTTP or atomic ref writes, so **R2 as live canonical Git is unproven**. This option uses Artifacts more often than A, even though it keeps large canonical history elsewhere. An agent could instead work directly against the server, making these task repositories unnecessary.

**C — No Artifacts in v3.** The rented server owns bare Git, the repo actor, SQLite, land, checks and events. Cloudflare serves the static browser app; an optional Worker gateway may proxy bounded API/event requests. Agents clone and push to the Git server directly. This matches the v3 draft. A single 320 GB server is a starting point, not a 1,000-repository capacity guarantee. Encrypted Git bundles **and consistent SQLite snapshots** need an independent provider; a GitHub mirror of selected refs cannot restore issues, claims or events. The earlier hosting report is used here only for server prices and backup notes.

## Action accounting

The following are **v3 planning estimates**, not measurements. `W` is a dynamic Worker invocation, `D` a Durable Object request, `R/W` SQLite rows read/written, `A` an assumed Artifacts operation, and `CPU` estimated Worker CPU milliseconds. A Git protocol request is not a Worker invocation when a client talks directly to Artifacts or the server. The Artifacts price page names create, push, pull and clone as examples but does **not** say whether one protocol exchange, binding method, token call, fork or delete bills as one operation. Therefore `A` is an activity proxy, never an invoice count. Published v2 numbers are code-path counts; v3 rows and CPU are intentionally shown as ranges or unknowns because no v3 trace exists. One event append is assumed per successful mutation; a real action can emit more.

For options A and B, assume the v2 account's Worker plus one catalog Durable Object and one repository Durable Object per logical repository, but replace JSON snapshots with indexed v3 tables. A normal mutation takes one Worker invocation and one repository-object request; repo creation also takes one catalog-object request. Authentication from a delegated principal can add a catalog request, as v2 does. The range `1–5/1–3` means estimated rows read/written and includes the event row where relevant. The v3 draft budgets a claim at at most five rows **per unit**, a ready-set page at sixty, a change read at twenty and event catch-up at 200; it supplies no actual per-action row measurements.

The C and B server reference is the earlier captured **Hetzner CPX42 8-vCPU, 16-GB, 320-GB disk, $81.99/month before VAT**. It is a price point, **not a proven minimum or capacity**. A also needs a Git-capable server; add its price and independent backup to A's displayed floor. B's displayed floor likewise excludes its required canonical server. An independent Backblaze copy of current 0.2 GB/repository is about **$0 / $0.07 / $1.32** at 10/100/1,000 repositories using the earlier report's price and first-ten-GB allowance; Git plus consistent SQLite backup, versions, restore traffic and origin egress are additional. The GitHub mirror copies only selected refs. A separate R2 backup would share Cloudflare's provider failure domain and is insufficient as the only independent copy.

Under the same simplifying workload, A/B dynamic API calls are roughly **271 per light repository** or **5,491 per busy repository** monthly (one create, ninety browser reads/connections, six change-related calls per change). Thus 1,000 busy repositories imply about **5.49 million Worker requests**, below the *nominal* ten-million inclusion before v2 and retries. One repository's thirty changes/day is an average, not a 1,000-requests/second peak test. Durable Object requests are of similar order plus delegated-auth lookups, runner messages, alarms and reconnects; at 1,000 busy repositories they can exceed the shared one-million inclusion, but the request overage tariff alone is small. CPU, SQL rows and **hibernation failure** can dominate: 1,000 objects active eight hours/day at 128 MB would accrue about **110.6 million GB-seconds/month**, far beyond the 400,000 inclusion; hibernatable idle sockets can avoid most of that duration. Those are **scenario estimates**, not observed charges.

At **0.8 GB per canonical repository after one year** (an earlier report's growth assumption, not a forecast), A approaches its 1 GB per-repository ceiling even before unusually large files. At 1,000 repositories, 800 GB remains below the 1 TB account storage limit, but any 32 MB blob still fails. B's one-day full-baseline task copies would average **24 GB per busy logical repository**, violating the account cap with fewer than fifty such repositories unless retention falls, baselines shrink or Cloudflare raises the cap. Deleting after one hour instead of one day reduces that average by roughly 24-fold; deletion timing and storage accounting must be measured. C's 800 GB canonical data would exceed one 320 GB CPX42 disk before SQLite, working packs and backup space. Splitting repositories across disks/servers or buying more storage is necessary. Neither the quoted server nor the Artifacts limit guarantees 10–50 simultaneous pushes; Artifacts publishes 2,000 Git requests per ten seconds **per repository**, but not a same-ref writer concurrency or latency guarantee. Control-plane requests also have a 2,000-per-ten-second **per namespace** limit.

## What v3 fixes, keeps and could worsen

| V2 problem | V3 design effect on Cloudflare |
| --- | --- |
| Idle polling and alarms | The v3 event stream and real-deadline-only timers avoid routine polling **if implemented**. The deployed v2 alarm fix cut one observed sequence from 38 Artifacts events/hour to 8/hour for five hours; it did not prove zero. Nonhibernating v3 WebSockets could replace operation cost with a larger duration cost. The owner's **polling fix decision (D-POLL-FIX-FIRST)** and **WebSocket push decision (D-PUSH-AFTER-SUBMISSION)** motivate this design. |
| Fork accumulation with no deletion | A and C avoid it because a v3 change is a database object, not a fork. B deliberately reintroduces task repositories, so explicit deletion, retry safety and retention are mandatory. The owner's **storage lifecycle decision (D-STORAGE-SCALE)** calls for a scaling fix; this report does not deliver that decision. |
| Per-repository coordinator serialization | One repo actor still orders metadata writes. Different repositories scale across Durable Objects, but one busy repo remains single-threaded with a soft 1,000 requests/second limit. V3 moves long Git checks/merges out of the actor and uses nonblocking claims, so serialized work should be shorter; the same-repository speedup is unmeasured. |
| Snapshot rebuilds and history-size reads | Indexed rows, page budgets and immutable Git reads remove the v2 all-state snapshot route in the v3 design. This should reduce the 2.21 billion six-day row reads, but index layout, event replay, browser behavior and SQL scan counts must be measured before claiming a bill reduction. |

V2's measured path counts and account totals are evidence about **v2**, not v3. The v3 local land and event prototypes prove specific mechanisms under synthetic conditions. Cloudflare's Artifacts API and limits document a possible service surface but leave operation metering, safe same-repo concurrent writes, large upload behavior and a backup restore contract untested for Concord. Workers Builds currently deploys the v2 Worker from Artifacts canonical `main` under the owner's **Workers Builds deployment decision (D-DEPLOY-WORKERS-BUILDS)**; moving v3 Git requires a separate deployment and rollback plan, not a silent change to that live path.

## Smallest measurements to approve before a hosting decision

These are **proposals for owner approval, not experiments performed here**. First, inventory each real canonical repository's Git bytes, largest blob and one-week growth, and obtain Artifacts operation counts from billing or support. This quickly tests whether a core repository already violates 1 GB or 32 MB and whether the activity proxies above are close to billable units. Second, in a disposable repository, import a **500 MB to 1 GB** history and attempt one **over-100-MB push** through our actual `workers.dev`/Git route; record error, body size, time, memory and bytes. Third, run **10 then 50 concurrent agent pushes** to one repository, including competing `main` updates, and record success/conflict/retry, p50/p95 latency, pack CPU and billed Artifacts activity. A fourth small trace can compare one v3 claim, publish, land, browser file read and idle WebSocket hour against Worker CPU, Durable Object requests/rows/duration and Artifacts operation counts. Set short bounded runs and cleanup before starting.

If a real repository crosses Artifacts' per-repository or blob limit, A cannot be the main store without a documented limit change. If B's task copies have significant retention or operation cost, use direct server workspaces. If a server meets the bounded swarm test and recovery drill, C becomes the lowest-complexity v3 path. The owner should approve a host, region and backup loss/restore target only after those facts; this report makes no deployment or account change.
