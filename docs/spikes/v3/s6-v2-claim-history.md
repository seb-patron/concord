# Concord v2 claim and lease history for v3

Research snapshot: v2 source in this checkout, read 2026-10-15. This report records the design history and separates written plans from behavior verifiable in source. It does not treat a proposal, approval, or accepted spec as shipped behavior.

## Executive summary

V2 moved through three different questions that are easy to conflate: how an agent reserves code units, how it signals ownership of an issue, and whether two changes that have already published should keep blocking one another. The owner approved C+ (“declare, grow, verify”) on 2026-10-12: claim declared units at start, grow claims during a run through fair waiting and deadlock refusal, then derive and claim the actual diff at publish/land. Most of that end-to-end design remained paperwork. The present code has a lower-level `POST /leases` claim and start-time file leasing, but no dedicated `concord claim`, no start `--units`, no diff auto-claim, and no durable lease wait queue.

Some later lease work did land. The checked-out v2 source supports policy-defined file, TSV row and configured Git-funcname symbol units; single and batch renewal; owner force-release with a fence bump; and a change's active leases cease to block new claims after publication. Queue stack selection skips overlapping published entries except when dependency closure requires them. Issue-level claims did not land. The 2026-10-14 wait-line v2 is a design for a bounded queue-priority turn followed by a fresh authenticated claim, and explicitly avoids automatic lease grants; it is not the original C+ wait queue and is not present in the lease routes.

The practical v3 question is not just “should claims grow?” It is whether growing a declared, exclusive write set is still the right interaction when issue assignment, advisory intent, symbol scope, published landing holds, and merge-time conflict handling are separate choices. The original C+ answer favored explicit mid-run growth. Later evidence supports preserving an explicit extension path where scope is knowable and useful, while making its atomicity, fairness, fencing, queue semantics, expiry, overlap rules and fallback scope explicit. The supplied history does not decide whether v3 should retain it.

## Planned models and exact contracts

The specs are implementation contracts, not statements about current behavior. API/CLI/MCP shapes and acceptance criteria below are transcribed from the named input files; file paths identify the contract source.

### C+: declare, grow, verify (69–73)

**Start declares units (70).** `concord start ... --units 'JSON_ARRAY'` or `--units-file FILE` would claim declared keys all-or-nothing, validated by server policy. An issue's optional validated `units` list would be used by `start --issue N`; absent it, start falls back to whole-file `--allowed-files`. For merge-aware paths listed only as files, the spec proposes leaving them unclaimed until `claim`/publish auto-claim and printing that fact. Acceptance: start with explicit units, issue units, fallback, notice for skipped merge-aware files, reject invalid key; issue worker test; CLI/issue docs and `scripts/validate.sh`. Source: `70-start-units.md`.

**Grow mid-run (69).** `concord claim --repo R --intent-key K UNIT... [--wait DURATION] [--json]` finds the owned change by intent, skips units covered by held leases, and submits the rest in one claim using its hold TTL. No wait: exit 3 with holder/intent/issue/expiry; with wait: print positions/ETA, poll to grant/expiry/deadlock. `concord release --intent-key K UNIT...` would release selected units, and MCP `concord_claim` would match. Acceptance: grant, covering skip, conflict exit, acquire after release, deadlock exit, per-unit release, MCP, CLI/MCP docs and validation. Source: `69-concord-claim.md`.

**Publish/land derives claims from the diff (71).** A shared `cli/units.ts` imports the runner's derivation rules (file, TSV row, Markdown section, declared keyed line; new-file prefixes; generated outputs excluded). Before push, publish/land would atomically claim missing touched units and release this change's untouched units; `--no-auto-claim` retains old behavior. A conflict returns exit 3 `PUBLISH_UNCLAIMED`, unit/holder/intent/expiry/next action, with no push; JSON emits `auto-claim` with claimed/released lists. Acceptance: auto-claim file, release untouched, conflict/no push, no-auto-claim compatibility, derivation parity on TSV/new-file, docs and validation. Source: `71-publish-autoclaim.md`.

**Original wait queue (72).** `POST /v1/repos/:r/leases` adds `wait: true` and `waitSeconds` (30–3600, default 600); conflict returns 202 `LEASE_QUEUED`, `waitId`, per-unit position/max position, ETA, and conflict holder details. FIFO is per overlapping unit; no barging by a later direct claim; multi-unit grant all-or-nothing. `GET .../leases/waits/:waitId` returns queued/granted/expired/cancelled; `DELETE` cancels; owner of change or owner may inspect/cancel. Events: `lease.queued`, `lease.granted_from_queue`, `lease.wait_expired`, `lease.wait_cancelled`; limits 64 waiters/repo and 8/change. It would grant an actual lease automatically in the RepoCoordinator transaction. Acceptance covers release/expiry grants, FIFO, no-barging, atomicity, cancellation, expiry, caps and auth. Source: `72-lease-wait-queue.md`.

**Deadlock refusal (73).** When a wait would queue, build a bounded waits-for graph including already queued waits. A cycle returns 409 `LEASE_DEADLOCK`, `details.cycle` with each change's held/wanted units, and `yields` naming the youngest change (later `createdAt`). If requester is older, refuse that request, preserve its current lease, emit `lease.deadlock_detected` for the younger change and cancel its queued wait as `DEADLOCK`. Acceptance covers 2- and 3-change cycles, correct yield/cancel/events, and no false positive for a chain. Source: `73-lease-deadlock.md`.

The broader issue-claim spike's Q-ISSUE-LEASE-1–12 make separate decisions on exclusivity/contests; assignee vs linked change vs issue lease; principal vs change vs principal+change holder; TTL/heartbeat vs activity; text edit strategy; who may edit; edits during active work; `start --issue`; per-holder caps/progress gates; expiry/owner force-release/wait line; whether renewal changes fences; and what can ship under the deadline. It reports no answers for those questions. Its prior-art review groups tracker assignments, queue/lease systems, agent task boards and collaborative editors. Failure modes it calls out are cookie-licking, stale claims, hoarding, starvation/livelock, zombie holders, renewal races, too-short holds, claim churn, lost updates and status drift. Source: `issue-leases-research.html`.

Together these specs make C+ a set of linked promises: declaration bounds initial work; growth makes discovery recoverable; FIFO reduces retry races; deadlock detection prevents circular waiting; publish/land verifies that actual writes have matching claims. If any of these pieces is omitted, the workflow changes materially.

### Wait line v2 (116), replacing original auto-grant

Spec 116 explicitly says the line never grants a lease on its own. Migration 2 adds `leases_waiters` with opaque ID, principal/change, intent, normalized keys, SQLite sequence, waiting/turn state, timestamps/deadlines/version; no token is stored. It permits one identical set per principal/change, makes repeat enqueue idempotent, limits each wait to 64 normalized units, total wait age to 5 min, turn to 45 sec, and live rows to 32/repo (`LEASE_WAIT_CAPACITY`). `POST /leases` remains immediate by default; `wait:true` registers/returns a 202 wait; `waitId` submits the exact set from a live turn as a new authenticated claim. Turn reserves priority, not a lease/fence. Earlier overlapping rows block later requests (including aliases/parent-child overlap); unrelated work proceeds. Status is `GET .../waits/:id`; cancel is `POST .../waits/:id/cancel`; only the waiter owner can access it, and status hides other waiters' identities. Cancel/expiry/release/force-release/close/terminal queue transitions advance the line transactionally. A new claim after a turn must pass authentication again, so completed token revocation prevents a later turn claim; the spec disclaims ordering against a request already authenticated before a concurrent revocation.

CLI `concord start --wait DURATION` creates/reuses one change, enqueues missing keys once, polls no faster than `retryAfterSeconds` (minimum 2s), claims only on its turn with fresh version/idempotency key, and returns success only with complete fences. Timeout and signals cancel best-effort; auth/close/lost lease cannot report success. MCP adds `wait`/`waitId` to `lease_claim` plus `lease_wait_status` and `lease_wait_cancel`. Acceptance includes overlapping FIFO/no-barging, multi-unit aliases and disjoint work, turn timeout/late alarm, every release hook, reservation blocking, idempotency/caps, stale/foreign turns, revoked delegated credentials, CLI resume/timeout, and MCP privacy. Source: `116-lease-wait-v2.md`.

The design deliberately avoids auto-grant because the RepoCoordinator transaction is synchronous while principal revocation is in a separate catalog Durable Object. It says an awaited catalog read cannot be safely inserted into the transaction; only a fresh later request provides the documented authentication boundary. This is a materially safer but less automatic model than 72 and the later D-LEASE-QUEUE-AUTO proposal.

### Symbol scope and issue claims

**Symbol growth (#92, 127).** `--symbols FILE` contains canonical `symbol:<path>#<name>` keys, one per nonempty line; `--allowed-files` remains the path authorization envelope and owner `symbolRules` authorizes each symbol. File-only start remains compatible; duplicates normalize; file/symbol overlap, malformed/unknown/out-of-envelope keys, and >64 units reject before mutation. `concord claim --repo R --intent-key K --symbols FILE [--hold 5m]` grows the same owned draft/ready change's declared scope via an explicit server mutation, then claims only missing keys. Grow is additive/idempotent and cannot remove old scope, widen frozen/terminal changes, bypass conflicts or claim for another author. MCP offers matching start/claim or explicit `change_scope_grow`, using the same routes and keys. Acceptance covers selected-only start, compatibility, rejection-before-mutation, restart fences, growth/renew/release/publish, idempotency/conflict preserving prior scope, ownership/frozen/overlap/policy/protected-path refusals, publish-scope enforcement, and MCP parity. Source: `127-sym-grow-92.md`.

The same spec cautions that Git funcname rules select lines, not AST extents. Intervals are from a selected line to the next selected line; nested declarations and Markdown headings start new intervals. Duplicate names, changed signatures, boundary insertions, crossing hunks, unknown/binary drivers and changed rules widen conservatively to file scope. The observed baseline had no tracked `.gitattributes`; TypeScript needed an owner-pinned custom driver/rule. Key derivation must match across CLI, runner and server or exact-footprint admission rejects the change. The current `src/leases/symbol-keys.ts` and `units.ts` implement canonical keys and conservative proof primitives; the spec's entire CLI/API/MCP scope-grow workflow is not implemented.

**Issue claim research.** `issue-claim-research.md` separates (a) claiming issue text, typically seconds–30 minutes, from (b) claiming the work, typically hours. Text editing already had per-issue `expectedVersion` lost-update protection, but author/owner-only edit rights and no MCP edit tool blocked multi-agent writing; section leases, merge/presence or CRDT were options, not a decided need. Work had no lock: multiple changes could link one issue and different-file implementations duplicated effort. A work claim cannot replace file/unit leases. The report's concrete 10-13 evidence: issue #1 had six attempts and at least three change replacements; it lost 14 file claims to ten parallel chains; a same-task duplicate run was cancelled manually. A claim anchored only to `changeId` would not survive attempt churn.

Its nine work/text options were: O0 keep `expectedVersion` only (safe text writes, no work protection); O1 durable assignee (visible/advisory, no expiry); O2 derive work claim from linked nonterminal change (no new primitive, but idle draft can stick and issue cannot be claimed before change); O3 separate fenced TTL issue lease (survives change churn, must stay out of verified unit fences and needs its own cap); O4 short section leases for issue text; O5 optimistic section merge plus nonblocking presence; O6 CRDT text co-editing (convergence does not ensure agreement); O7 atomic `start --issue` with issue and file claims; O8 stale/hoarding controls including human force-release. The recommendation was assignment plus a separate issue work lease, explicit claim before start initially, with issue and unit claims separate. It was not owner-approved as a product choice.

Questions Q-ISSUE-CLAIM.1–5 ask what claim promises, who may claim/override, ordering relative to files, TTL/recovery and what to ship; the spike recommends temporary exclusive lease distinct from assignment, current-holder fence for renew/release, owner audited force release, issue-first then atomic unit set or bounded rollback, short renewable TTL and manual issue selection before a scheduler. Its narrow contract includes open issue only, idempotent claim, holder/lease/fence/expiry, renew/release with current fence, authoritative server expiry, close/reopen serialization, start success only after issue and all units acquired, and event/snapshot visibility. Source: `issue-claim-research.md`.

### Lease granularity findings and claims as coordination

`lease-granularity-research.html` measured 2,496 same-file in-flight pairs across Concord, Mother Base, mwcc-rs and gen-v-decomp. 1,799 (72%) were apart according to merge (upper-bound touch count 582; confirmed 292). 374 pairs were apart but under the same funcname/section proxy; 132 touching pairs would not be blocked by that proxy. The same-file pair counts were 79, 114, 683 and 1,620 respectively. File-kind touch rates were 13–24% code/tests, 10–18% TSV, 15–46% generated outputs, 7–9% Markdown. Notable hot files included decomp `data/derived-syntax-known-conflicts.tsv` (399 pairs), `derived/include/callees.h` (339), and Mother Base `docs/architecture.md` (69 pairs, zero confirmed touching). The research notes important limits: worker start is approximated from first commit, rebase histories lose intermediate versions, Mother Base fallback precision was low, and semantic conflicts are not measured.

The studied alternatives were file leases plus better merge; language-agnostic finer blocks/lines; tree-sitter symbols; owner plugins; optimistic intent plus merge/conflict repair; and hybrid locking by file kind. The authors favored shifting fine conflict decisions toward landing, because it recovers most needless waiting without a new key identity, while preserving exclusive locks for unsafe/generated kinds. This was analysis, not the owner's selected C+ policy. The spike also found unit identity plugins risky: CLI/runner disagreement can reject all publishes or make different keys cover the same lines; merge-time plugins/advice are safer because the checker still gates the composed result. It lists unknowns E1–E6: Mergiraf resolution rate; clean-merge build failures; whether declarations predict diffs; actual FIFO wait time; best Markdown level; and line-range survival through rebase. No experiments are authorized in this task, and none are reported as run. Source: `lease-granularity-research.html`.

## Renewal, TTL, force-release and published leases

The renewal spike `lease-renewal-research.html` is grounded in main a72e2a0 and a 10,801-event live log, not a new implementation spec. It recorded 128 expiry events on Oct 12–13; 101 followed renewal in the prior ten minutes, indicating live holders. 75/121 inspections exceeded five minutes (median 6.8, max 39.2); three of 18 stack checks exceeded the fixed 30-minute queue reservation and two entries expired/blocked. Review waits ran 3–218 minutes (median 37). Eighteen sequential renewals took about 31 seconds and the last lease expired. In another incident, a sidecar renewing four leases invalidated land's fences and caused `LEASE_STALE` at enqueue. The spike found no renewal during the agent edit or review gap and no MCP renew tool at that point.

Options a–g ranged from retain 2h; stable fence on renewal; one background heartbeat per change/session; server-held leases during platform phases; land-only renewal; owner-approved long-hold exceptions; no-TTL locks with override; to advisory-only optimistic merge. The spike's key recommendation was not to switch to five minutes without a working renewer. Ten unresolved questions Q-LEASE-1–10 cover fence changes, renewal unit/actor, server-held phases, TTL/cadence/grace, expectedVersion exemption, lapse recovery, queue reservation duration, exception approval, holder/session identity and what to ship. These are research questions, not decisions in this task.

The checked-out code now differs from that spike baseline. `src/features/leases.ts` defines a 120-second server default, 300-second fixed maximum constant and 40-second renew guidance, but validates against trusted `maxLeaseHoldSeconds`; `cli/start.ts` defaults to 5m and `src/state.ts` configures a 14,400-second default maximum (with a larger configuration ceiling). Single `renew` extends expiry without changing the fence. `renew-batch` renews active leases for a change in one transaction, uses `max(old expiry, now + TTL)`, keeps reserved rows in its response, and has no `expectedVersion` requirement in its route path. The start CLI uses batch renewal; `renew --every ... [--while-pid ...]` provides a periodic CLI renewer. MCP exposes `lease_renew` for batch renewal of a change, alongside `lease_claim`, `lease_release`, `lease_force_release` and `lease_list`; it does not expose a periodic background session heartbeat. A live lease's fence is advanced by a new claim and owner force-release, not by renewal. Reservation is still fixed at 30 minutes (`RESERVATION_MS`) and is not extended by batch renewal. Source: `lease-renewal-research.html`, `src/features/leases.ts`, `src/state.ts`, `cli/start.ts`, `cli/main.ts`, `mcp/tools.ts`.

Owner force-release is live in `src/features/leases.ts`: only owner role, reason required, active/reserved row only; it increments the per-unit fence, releases the lease and emits `lease.forceReleased` including actor and reason. Ordinary release needs current holder/fence. `releaseForChange` releases active and reserved rows when called by change-close/merge hooks. These controls are separate from the still-unimplemented human wait-line move-to-front/pause controls described in D-LEASE-WAIT-LINE.

Spec 181 addresses the bottleneck observed when changes remained active throughout checking/review. The current claim code reads each holder change; another active lease conflicts only while its holder change has not published. Reserved leases are excluded from claim conflicts, and a claimant whose own change already has a published head can claim despite other writing holds. Reservation admission checks the claimant's own current fenced units and verified footprint; the inspected implementation has no cross-change overlap refusal in `reserve`. `src/queue/plan.ts` exports `unitsOverlap` and avoids stacking overlapping unit sets unless dependency closure requires the pair. The known gap in spec 181 is whole-file vs TSV-row overlap in one stack; symbol/file overlap is handled. This is a deliberate change from “lease stays exclusive until land”: exclusive writing hold ends at first publish, while the queue serializes overlapping published changes and later land/rebase handles stale main or real conflict. Source: `181-published-leases-stop-blocking.md`, `src/features/leases.ts`, `src/features/queue.ts`, `src/queue/plan.ts`.

## Findings across the four earlier research spikes

### Issue-claim research (`issue-claim-research.md`, `issue-leases-research.html`)

- Assignment communicates intended responsibility but is not exclusive, expires neither, and can become stale. A work lease should be separate from an assignee if the product needs both.
- Text-edit concurrency and work ownership are different. Existing issue `expectedVersion` prevents lost updates, but write permissions (author/owner only) and absent MCP edit tooling were the blocker for broader issue editing; section locks are not automatically the answer.
- A linked `issueNumber` is metadata, not a claim: multiple active changes may link the same open issue. A work lease must survive a worker's change/intent churn or it releases too early.
- Issue locks cannot substitute for file/unit leases: a task can span many files, exceed 64 normalized units, or be blocked on one resource while holding the issue. Ordering and rollback/bounded hold must be explicit.
- A useful issue claim needs atomic acquisition, holder/expiry visibility, renewal/release fences, authoritative expiry, stale-holder behavior, owner override and audit. Shared tokens make principal identity a poor proxy for separate agent sessions.
- `issue next`, label/milestone pools and priority/fairness are scheduler projects, not a small extension to claims. Retry loops can starve/livelock; any issue queue needs ordering and anti-hoarding policy.
- Editing an issue while work is claimed can change Goal/Done-when/Allowed-files beneath the worker; choose allow-and-notify, block selected fields, or version/abort behavior.
- The spike's specific observed history: #1 six attempts; at least three change replacements; 14 file claim refusals against ten chains; duplicate same-task run cancelled manually; expired leases were the only cleanup for abandoned claims. These observations motivated research; they do not establish the frequency of a future v3 system.
- Nine options and Q-ISSUE-LEASE-1–12 are captured in the original spike. For text: optimistic version-only, section leases, merge+presence, CRDT. For work: no-op, assignee, linked-change lock, issue lease, start integration, and human anti-hoarding controls. Its conclusion favored assignment plus an independent issue lease as a possible end state, with manual issue selection initially, but left the policy questions to the owner.

### Lease granularity (`lease-granularity-research.html`)

- 72% of same-file concurrent pairs were merge-apart in the measured sample; file locks over-serialize, especially hot Markdown, TSV and generated files.
- A funcname/section proxy still over-blocks apart edits (374 pairs) and misses touching edges (132); symbol keys improve declaration-level independence but do not prove semantic isolation.
- Sub-file leasing is bounded by what the verifier can prove. Cross-component identity drift between CLI, runner and server can make every publish fail or keys alias unsafe footprints. Conservative fallback to file scope is required.
- Line ranges are precise only after edits and fragile across rebase, so they fit “grow/verify” better than initial declaration. New symbols/units require mid-run growth.
- Evidence favors exploring merge-time composition, advisory overlap or a hybrid file-kind policy alongside locks. Structural merge can reduce text conflicts but cannot catch semantic errors; the checker on the composed tree remains necessary.
- Data are counts, not waiting time; dates approximate worker starts; Git rebases erase history; Mother Base fallback touch precision was weak. Unknowns E1–E6 were listed, not tested here.

### Lease renewal (`lease-renewal-research.html`)

- Five-minute default without a continuously running renewal path leaves a live hour-long edit unprotected after five minutes. A two-hour fixed TTL masks missing renewal but leaves dead holders blocking much longer.
- Renewal that increments the fence makes concurrent renewers invalidate one another; stable fence across renewal, new fence on new ownership/force release is the tested design principle in the spike and is current source behavior.
- Serial per-lease renew plus whole snapshot fetch scales poorly and can expire later leases before their turn; batch and expectedVersion-free heartbeat are the proposed fix. Current batch route addresses much of this; reservation duration and agent/review renewal remain separate.
- A land-only client cannot heartbeat during blocked operations, editing or review. Background/session timers help only if tied to a live agent; orphan keepers create long holds in disguise.
- Queue reservations are server-owned and fixed at 30 minutes despite checks reaching over 40 minutes; the wait-v2 spec would need to reason about reservation transitions and late alarms. Current code still uses the fixed reservation.
- Lapse policy, heartbeat cadence/grace, long-hold exception, holder/session identity, and review-phase server holds remained open Q-LEASE questions.

### Published-lease bottleneck (`181-published-leases-stop-blocking.md`)

- Active leases held through inspect/review made agents block one another for a long time; queue admission only needs a change's own verified fenced footprint, not exclusivity against every other published candidate.
- Separate writing from landing: unpublished active leases are exclusive writing holds; after publish, a lease is a landing hold, and overlapping candidates must not be placed together in an ordinary stack. Later candidates rebase after earlier land; actual merge conflict returns to the author.
- Preserve own lease/fence validation, exact verified footprint, contest inheritance and fixed reservation semantics; remove only cross-change claim/admission overlap refusals and add overlap-aware stack selection.
- Symbol vs file overlaps and row vs row are handled by key/policy behavior; the report explicitly identifies whole-file vs row lease stack overlap as a known gap. This means “leases no longer block after publish” depends on queue serialization and rebase/conflict repair, not on simultaneous writes being proven compatible.
- Its acceptance tests require unpublished writer A to refuse B, then allow B after A publishes (two active rows with different fences); a third writer still conflicts with B; reserved rows do not appear as holders. Admission of published A is allowed despite another writer's active lease; a published claimant can claim while that writer holds; ordinary overlapping contest-child claims become ordinary grants. Planner tests expect duplicate file units to split stacks, dependency-required overlap to remain together, distinct symbols/rows to compose, file+symbol overlap to split, dependents of skipped entries to wait, and entries without unit metadata to preserve prior selection. End-to-end landing starts the second same-file change after the first publishes, without a `LEASE_CONFLICT` event, and still requires review evidence. Source: `181-published-leases-stop-blocking.md`.

## Lessons and questions v3 must answer

1. **Should a mid-run grow operation exist?** C+ explicitly says yes; specs 69/127 provide the user workflow. The granularity evidence says declarations can be unknowable at start, especially for new symbols, while line ranges are only knowable after editing. Against this, each new scope mutation adds policy/version/atomicity and stale-holder paths. Decide whether v3 needs additive grow, intent-only/advisory marking, or diff-derived scope at publish, and which model applies to which resource types.
2. **What is the unit of authorization and proof?** Decide whether exclusive units are file, TSV row, Git funcname symbol, issue, or a mix; define owner policy, canonical key, alias/overlap semantics, maximum size, and fail-closed fallback for parser/config changes, renames, binary/generated paths, boundary edits and unknown units. Keep CLI/runner/server derivation identical and pin rules to trusted policy.
3. **What does “claim” promise?** Separate assignment, advisory “working on” intent, exclusive write authority, issue task ownership, and landing order. A lease linked to an issue does not reserve the issue, and an issue lock does not prove the code diff is covered.
4. **When may a claim be extended?** Pick immediate conflict/refusal, original auto-grant FIFO wait (72), or a short priority turn with a fresh claim (116). Specify exact FIFO overlap, no-barging, all-or-nothing sets, alias handling, unrelated-work progress, ETA limits, cancellation, durable retention, caps, identity/auth at grant, deadlock behavior and failure recovery. The current source supports none of these wait routes.
5. **How are holders identified and fenced?** Shared principal tokens collapse multiple runs into one identity. Decide whether principal, change, run/session, or combination is the holder. Fences should reject an old owner after takeover/force-release without making routine renewal invalidate another process. Also specify whether lapse can be reclaimed silently or must fail closed.
6. **What is held after publish?** 181 changes the lease from a long-lived blocking lock to a writing hold plus landing hold. Preserve or revise its queue stack serialization, mixed-granularity gap, dependency exception and author repair flow if v3 explores advisory overlap or concurrent merge.
7. **What should issue start mean?** Decide if issues gain declared units, assignment, work lease, or only link metadata; whether `start --issue` atomically obtains issue+unit claims; how edits to a claimed issue behave; and how close/reopen/allowed-files changes affect a live work claim.
8. **How does renewal cover human and platform time?** The edit process, inspection, review and queue check have different liveness/ownership. Choose who renews, how often, how background processes terminate, whether review uses a server hold, the reservation deadline, long-hold approval and user-visible lost-lease response.
9. **What is the fallback when merging is safe enough?** The measured false-wait rate motivates merge-time composition, advisory signals and hybrid locks; semantic conflicts still require the checker. Decide whether a lease is a lock, an intent marker or selectable per unit, and which guarantees the product promises.
10. **What must v3 measure before choosing?** The old studies measured pair counts but not time cost. With explicit authorization, compare observed wait durations, claim growth frequency, conflict/repair cost, queue starvation, renewal lapses and issue duplication. This task ran no experiments, as instructed.
