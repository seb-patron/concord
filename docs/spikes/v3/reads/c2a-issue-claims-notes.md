**Meaning for Concord.** Keep issue ownership and source authorization as separate resources. The recorded Issues UI decision maps “assigned to” to the agent or agents holding the issue lease (D-GITHUB-UI), while the issue lease lifecycle remains open for this spike. A clean candidate must acquire the issue and every declared unit, and make a unit conflict all-or-nothing or use a bounded visible reservation with rollback. Preserve exclusive unit claims as the anchor (D-UNIT-1-EXCLUSIVE); changing it requires owner approval. The prescribed tests require event-time knowledge, uncensored demand and explicit assumptions; behavioral claims need a later current-agent pilot. **STRUCTURAL (source date: 2026-10-15):** an offline timeline cannot reveal whether an agent notices presence. **CAPABILITY-DEPENDENT (source date: 2026-10-15; re-test):** issue-footprint prediction, waiting and repair behavior.

## 2. Concord v2 issue-claim research

**Input:** `/Users/sebastianpatronsoto/agent-runs/_manual/concord-specs/v3-reads/inputs/v2-history/issue-claim-research.md`, “Spike: what claiming an issue means for agent swarms,” prepared 2026-10-13. Read all 175 lines.

**What it says.** The spike separates assignment (“who is expected to work”) from an expiring issue lease (“the right to work for a limited time”), and both from file-unit leases. At the reviewed v2 snapshot, issue records had no assignee or claim field; a change could link an open issue, but distinct changes could link the same issue. Start claimed Allowed-file units and did not select an issue. It compares assignment-only, issue lease, both, implicit issue claim at start, claim-next scheduling, pools, and status-only. The proposed direction was assignment plus a distinct issue lease, with explicit claim first and start integration later; it was not a decision. Failure cases include duplicate starts, busy files after issue acquisition, dead agents, stale resumption, many-file requests, issue mutation, assignment mismatch and unfair retries.

**Key quotes and locations.** “Summary / Recommendation in one paragraph”: “make the lease the concurrency authority.” “What Concord does today / Change linkage is not an issue claim”: “there is no uniqueness check across active changes by issue number.” “Failure cases with 10 concurrent workers,” items 1–8, details the cases above. “Options,” option 4, requires rollback if change creation or unit claims fail; “Suggested narrow contract” says start “must not report success” if a required unit conflicts. “Q-ISSUE-CLAIM.2” proposes agent self-claim for open work and owner-only reasoned override; Q-ISSUE-CLAIM.3 proposes release or bounded retry when units are busy; Q-ISSUE-CLAIM.4 recommends a short renewable lease with fencing. “Q-ISSUE-CLAIM.5” explicitly says these are recommendations, not selected policy.

**Meaning for Concord.** This is useful failure analysis and a candidate recommendation, not authority to ship it. An issue lease keyed to a principal alone may collapse multiple workers sharing one token; a lease keyed to one change may disappear during replacement. Candidate designs should use a run/session identity plus a stable issue intent, link replaceable changes as children, and keep source-unit fences separately checked. **STRUCTURAL (source date: 2026-10-13):** a lease on an issue cannot confer authority over code units. **CAPABILITY-DEPENDENT (source date: 2026-10-13; re-test):** whether explicit assignment or queue signals reduce duplicate work.

## 3. Concord v2 issue-leases research

**Input:** `/Users/sebastianpatronsoto/agent-runs/_manual/concord-specs/v3-reads/inputs/v2-history/issue-leases-research.html`, “Issue Claims Research,” written 2026-10-13. Read all 665 lines, including the HTML source, evidence tables, nine options and twelve questions.

**What it says.** The page separates issue-text editing from claiming work on an issue. Text edits already used optimistic issue versions, but only authors or owners could edit in that snapshot; issue work had no protection against separate changes. Existing unit leases assumed trusted file policy, a change-owned holder, file-based overlap and exact correspondence between fenced leases and verified writes. Therefore an issue is not safely added as a fake file unit. The research compares doing nothing, assignment, deriving ownership from linked changes, a distinct expiring work lease, short section leases for issue text, optimistic merge plus presence, CRDT editing, atomic start integration and stale/hoarding controls. Historical observations include repeated issue attempts, duplicate execution, lease lapse and renewal/fence races. Evidence and dates refer to the 2026-10-13 v2 snapshot, not present v3 behavior.

**Key quotes and locations.** Header/“Two cases”: “claiming an issue to write its text, and claiming an issue to do the work.” “What Concord has today”: “Nothing protects work today.” “Can an issue be a lease unit?” explains five model assumptions and recommends a separate claim table or a deliberately generalized unit model, not a fake path. “How claims fail” names “Cookie licking,” “Hoarding,” “Starvation and livelock,” “Zombie holder,” “Renewal race,” “Hold shorter than work,” and “Claim churn.” Option O3 defines a principal holder, optional change, TTL and fence, and says issue claims must stay out of queue write fences. Option O7 requires issue and file claims “in one all-or-nothing step.” Q-ISSUE-LEASE-9 recommends considering per-holder caps; Q-ISSUE-LEASE-11 distinguishes fences that change on renewal from fences that change on new grant/override. The page's “Method” and Q-ISSUE-LEASE-12 state options and delivery timing were not decisions.

**Meaning for Concord.** Issue-text editing and issue-work ownership are separate questions. This assignment concerns work ownership and automatic acquisition of declared code leases, not collaborative issue-description editing. Never pass an issue-claim fence as a code-write fence. A changed issue specification must be versioned and surfaced to the active worker; close must revoke or reject atomically; reopen must create a fresh eligible claim state. The old incident counts are one operator/repository history, not rates. **STRUCTURAL (source date: 2026-10-13):** issue and code units need distinct identity and authorization checks. **CAPABILITY-DEPENDENT (source date: 2026-10-13; re-test):** whether a queue or activity signal prevents duplicate agent effort.

## 4. Agent Mail implementation notes

**Input:** `/Users/sebastianpatronsoto/agent-runs/_manual/concord-specs/v3-reads/inputs/s2c-agent-mail-impl-notes.md`, pinned implementation and test notes fetched 2026-10-15. Read the full 121-line note, including its guard, app, lifecycle tests, changelog and findings sections.

**What it says.** Agent Mail records project-relative path patterns owned by an agent, with shared/exclusive mode, reason, expiry and release metadata. Optional local pre-commit and pre-push hooks can block, but can be absent or bypassed; server enforcement described for archive paths is separate. **Key quotes and locations.** “What it means for Concord v3” under `guard.py`: “direct writes remain possible and hooks can be bypassed or absent.” Under lifecycle tests: “conflicts are observations in the result rather than a denial of creation.” “Reservation model findings / Advisory versus enforced” says a conflict “does not block the grant.” “Problems found in use” lists reverse-glob false negatives and archive compensation. The full-read file names the source functions and test line ranges for each finding.

**Meaning for Concord.** Borrow visible holder, reason, expiry and audit history; do not confuse reservation visibility with a server-enforced exclusive claim. An issue claim should serialize at the authoritative server and gate work start, with its own transactional lifecycle. Simulate pattern/declared-unit overlap using Concord's canonical unit rules, not Agent Mail's globs. **STRUCTURAL (source date: 2026-10-15):** optional local hooks cannot be the sole correctness boundary; permissive conflict reporting does not prevent duplicate starts.

**What it says.** The GitHub and Linear sections primarily document issue relations, parent/sub-issue hierarchy and project dependencies. **Key quotes and locations.** In this input: “About issues,” item 8: “Subscription notifications and assignees support awareness and responsibility.
