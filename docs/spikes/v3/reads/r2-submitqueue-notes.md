## Sections
1. **Abstract** — The paper presents SubmitQueue as a change management system for giant monorepos with three goals: green mainline, high throughput, and low turnaround time. It serializes commits only after all required builds pass, while using parallel speculation to target thousands of daily commits.
2. **1 Introduction** — Individual pre-submit success does not prevent concurrent changes from breaking a mainline; the authors describe a production performance regression that took hours to bisect and delayed a release. They define green as every commit point passing every build step and argue that the system must serialize changes while meeting practical turnaround SLAs despite hours-long builds and high arrival rates. SubmitQueue uses a probabilistic speculation graph and conflict graph to choose parallel builds and independent commits; the paper’s contribution is applying these techniques together and evaluating them in production.
3. **2 Background** — This section contrasts intermittently green mainlines with systems that require all build steps to pass before each commit. It frames the central problem as the interaction between concurrency, changes that may pass alone but fail together, and slow build capacity.
4. **2.1 Intermittently Green Mainline** — Trunk-based commits with only per-change pre-submit checks can still fail in combination, leaving post-submit tests, diagnosis, and rollback to recover the branch. The paper reports a 5% real-conflict probability with two concurrent potentially conflicting changes, rising to 40% at 16, and historical data showing even one-to-ten-hour-stale changes have a 10–20% breakage probability. It identifies delayed rollout, limited rollback choices, and lost developer productivity as costs of a red mainline.
5. **2.2 Always Green Mainline** — A strict FIFO queue is correct but unscalable: at 1,000 daily changes and 30 minutes of builds, the tail could wait more than 20 days. Batching raises failure and retry costs, Chromium’s two-stage batches require manual fault attribution and yield shippable batches rather than individually shippable commits, and optimistic execution repeatedly discards downstream work after a failure. The section motivates selective speculation as a way to preserve correctness without those throughput and diagnosis problems.
6. **3 Dev Life Cycle & System Overview** — The authors define a revision as a container of changes and a change as a patch, build steps, and metadata; approval precedes submission to the queue. SubmitQueue gives developers a single-queue model while internally coordinating a distributed queue, planner, speculation engine, build controller, conflict analyzer, and repository commits.
7. **3.1 Development Life Cycle** — A developer creates a branch from mainline HEAD, submits a revision/change for review, may amend it, and submits an approved change for landing. The patch reaches HEAD only after all required build steps succeed; that successful commit is called landed.
8. **3.2 SubmitQueue Overview** — The API accepts submitted changes and reports their state; the core service executes builds and either lands or aborts each pending change. The planner periodically obtains high-value build choices from a logistic-regression-based speculation engine, schedules or cancels builds, and commits safe changes; a conflict graph trims speculative work and identifies changes that can land independently.
9. **4 Probabilistic Speculation** — Each change is ultimately accepted or rejected based on its build outcome, so the system can run candidate builds before earlier outcomes are known. A binary decision structure represents possible sequences of outcomes and uses edge probabilities to prioritize speculative execution, trading build cost against expected turnaround and throughput.
10. **4.1 Speculate Them All** — Running every possible build for n mutually conflicting pending changes costs 2^n−1 builds, although only n results are ultimately needed. Many jobs become irrelevant as soon as an earlier result is known, so exhaustive speculation wastes resources even though it could minimize waiting.
11. **4.2 Probabilistic Modeling** — SubmitQueue ranks builds by expected value: benefit multiplied by the probability the result will be needed. Estimating individual change success and pairwise conflict probabilities lets it select builds likely to contribute to a decision; static heuristic probabilities performed poorly because mis-speculation is expensive and does not adapt to observed outcomes.
12. **4.2.1 Value of Build** — The needed probability of a later build depends on prior build outcomes; for example, a combined build is useful only if its prefix succeeds. The authors model conditional success of a combined build from the next change’s individual success probability minus its conflict probability, then estimate these quantities with regression rather than fixed guesses. Build benefits could encode team quotas or priority, though their implementation assigns each build equal benefit.
13. **4.2.2 Speculating Independent Changes** — Independent changes need not be chained into one speculative path: their separate builds can run in parallel and their commits can proceed independently. Knowing independence changes the speculation tree into a graph and can reduce unnecessary builds; the paper proceeds to describe how it detects conflicts.
14. **5 Conflict Analyzer** — The analyzer builds a conflict graph to expose parallel commits and prune speculative combinations. Examples show that the gain depends on conflict topology: independent changes create parallel work, while one change conflicting with several others constrains the graph.
15. **5.1 Build Systems & Targets** — Conflict analysis depends on a build system’s target dependency DAG, whose targets represent source files, dependencies, and output-producing actions. Build targets provide a structured unit for determining what a change affects and for reusing hermetic build work.
16. **5.2 Conflict Detection** — A change’s affected targets are derived transitively from modified files and dependent targets; intersecting affected target names detects many conflicts. Because build-graph topology can change, the authors give a stronger condition and a union-graph algorithm that propagates affected status through dependencies, treating overlapping affected nodes or a cycle conservatively as conflict. Computing complete graphs for every pair is too expensive, so the union-graph method uses HEAD and each individual change’s graph; only 7.9% of iOS changes altered the graph in their measured period.
17. **6 Planner Engine & Build Controller** — The planner refreshes prioritized work each epoch, cancels running builds no longer selected, and schedules replacements according to available capacity. The controller avoids repeating already completed target work, balances estimated durations across workers, and reuses build-system artifact caches.
18. **7 Implementation** — SubmitQueue’s API service and core were implemented in Java, with Buck, MySQL, Helix, and RxJava among its infrastructure. The speculation engine’s worst-case search is exponential, but a greedy best-first search follows highest-probability nodes and is described as optimal in memory for the graph’s decreasing path values, with O(n) space.
19. **7.1 API & Core Services** — The stateless API exposes change landing and status, with a web UI for tracking changes; the core coordinates speculation and conflict analysis. Greedy best-first traversal is used to handle hundreds of pending changes without retaining the full exponential graph.
20. **7.2 Model Training** — Logistic regression predicts individual success and pairwise conflict from historical outcomes and roughly 100 handpicked features spanning change size/targets/checks, revision behavior, developer history, and speculation outcomes. A 70/30 train-validation split produced reported 97% accuracy; recursive feature elimination reduced runtime features, and successful speculations, revision plans, and initial checks were strong positive predictors. Developer features were predictive but varied across developers, a material operational and fairness consideration when adapting the method.
21. **8 Evaluation** — The evaluation compares SubmitQueue with speculate-all, single-queue, optimistic speculation, and an oracle that knows outcomes perfectly. It examines turnaround and throughput across arrival rates and worker counts, then studies conflict analysis, pre-launch mainline health, and developer survey responses.
22. **8.1 Setup** — Experiments replayed real iOS and Android changes, varying only arrival spacing to create fixed rates of 100–500 changes per hour; similar build-duration distributions led the authors to report iOS results. The setup used Mac Minis for iOS builds and Linux API/core machines, and Oracle ran with 2,000 workers without contention to establish a lower-bound comparison.
23. **8.2 Turnaround Time** — SubmitQueue’s P50 latency was at most 2.98 times Oracle and P95 at most four times under constrained capacity; at 500 workers for 500 changes/hour, the reported percentiles were about 1.2 times Oracle. Speculate-all was up to 15 times slower at P50 and 24 times at P99, while single-queue was much worse; optimistic speculation beat speculate-all in latency because many changes succeed. Actual latency grew with offered load, while normalized comparisons varied with Oracle’s performance and capacity.
24. **8.3 Throughput** — SubmitQueue had the smallest throughput slowdown among evaluated practical approaches, improving toward roughly 20% below Oracle with 500 workers and matching Oracle at 100 changes/hour. Single-queue suffered a 95% slowdown; optimistic throughput plateaued because it was limited by contiguous successful changes, and additional workers did not help its or the deep-graph speculate-all workload.
25. **8.4 Benefits of Conflict Analyzer** — Conflict analysis improved Oracle P95 turnaround by up to 60% and also substantially helped SubmitQueue and speculate-all. Its benefit was limited for optimistic and single-queue approaches when the iOS build graph was deep and conflicts common; wider dependency graphs should offer more parallelism.
26. **8.5 Mainline State Prior to SubmitQueue** — Before launch, the iOS mainline was green only 52% of one observed week; the authors report that mainlines remained green after launch. This is a before/after production claim that motivates the service’s correctness objective, though this section does not provide a controlled causal evaluation.
27. **8.6 Survey on Benefits of SubmitQueue** — Forty internal respondents reported perceived effects: 93% said an always-green mainline improved personal productivity and 86% said it helped production deployment, while 95% rated queue performance at least on par with prior experience. The evidence is a self-reported internal survey, not an independent or randomized outcome measure.
28. **9 Related Work** — The paper distinguishes awareness-based proactive conflict tools, transactional concurrency control, defect detection/localization, test selection, and speculative execution. Awareness tools notify rather than prevent breakage; transaction systems generally handle shorter work; defect tools can be included as build steps. SubmitQueue itself runs all required tests and treats test selection as future work.
29. **10 Discussion** — The system preserves submission order, which can make small changes wait behind a large slow change; reordering independent changes is proposed with fairness and starvation concerns. Other future work includes alternate prediction models, less aggressive cancellation near build completion, and batching independent changes to improve utilization while managing false-prediction latency costs.
30. **11 Conclusion** — SubmitQueue combines serializable green-mainline commits, probability-ranked speculative builds, and conflict analysis to scale continuous integration. Its graph-based selection seeks to use parallel resources without exposing an unverified commit as the mainline.
31. **Acknowledgments** — The authors thank colleagues, shepherd Steven Hand, and anonymous reviewers for feedback on earlier paper versions. This credits review and feedback contributions without changing the technical claims.
32. **References** — The bibliography contains 47 references spanning build systems and queue implementations, monorepo practice, conflict awareness, transaction systems, bug/regression analysis, test selection, and speculative execution. These references establish the paper’s connections to prior work; this note records the complete bibliography as part of the full-read pass rather than re-summarizing each cited work as if it were independently read.
## What it means for Concord v3
The supplied v3 context’s **server-side changes that land** and **one-way GitHub mirror** agree with SubmitQueue’s central invariant: validate the exact prospective state, then advance the canonical mainline through an ordered landing mechanism, instead of relying on post-submit recovery. SubmitQueue specifically demonstrates why individual change checks do not establish safety under concurrency and why a queue can expose one simple submission model while the backend runs planning and builds in parallel.
The paper’s **claims for presence** and issue coordination are different from its exclusive queue ordering: it does not evaluate agent presence, issue dependencies, ready sets, runs/swarms, or human review as workflow primitives. Its conflict analyzer uses build-target dependency graphs and probabilistic predictions, so it supports considering dependency-aware parallelism but does not establish that Concord should use file locks or adopt its ML model; the v3 context’s correction about Cursor’s task-file locks remains separate evidence. The paper’s many Java services and external build infrastructure also do not support the v3 choice of one TypeScript/Bun server with Git and SQLite on a VPS; the applicable lesson is the separation of submission/operation interface from internal scheduling, not a validated implementation stack. SubmitQueue preserves submission order and does not cover a single operation table across HTTP/CLI/MCP or WebSocket events, so those v3 choices are outside this paper’s evidence.
