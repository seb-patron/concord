## Sections
1. **Configuration Cheat Sheet** — This is a broad app.ini reference with defaults and explanations for most Forgejo settings. It instructs operators to edit the configuration file, explains environment/default notation, quoting, and says changes require a full restart.
2. **Repeating configuration key patterns** — Multiple modules share prefix-based JWT signing settings. The common scheme supports symmetric secrets or asymmetric key files, accepted old keys for rotation, and file URIs rooted at APP_DATA_PATH.
3. **JWT signing key configuration** — Algorithms include HMAC and asymmetric choices; HMAC secrets must be unique base64 32-byte values, while private keys use PKCS8 files. Accepted key entries support migration and wildcard file URIs; modules restricted to asymmetric signatures must omit shared secrets.
4. **Default Configuration (non-app.ini configuration)** — Runtime paths come from command flags, environment, build defaults, then derived paths, with relative paths resolved against the relevant application directory. TMPDIR also holds temporary operation data, so its disk must accommodate expected uploads.
5. **Overall (DEFAULT)** — These values set the visible application identity, OS account, operating mode, and work path. The guide warns that RUN_USER must be a dedicated system account and invalid values prevent startup.
6. **Repository (repository)** — Repository defaults govern storage root, privacy, creation limits, clone URLs, enabled units, forks, migrations, and branch behavior. Several controls are global defaults or policy switches, and some units cannot currently be disabled.
7. **Repository - Editor (repository.editor)** — This section controls which extensions wrap in the editor and which file modes have preview APIs. The preview tab depends on the extension matching a supported mode.
8. **Repository - Pull Request (repository.pull-request)** — PR defaults cover work-in-progress markers, issue-closing/reopening keywords, merge styles, generated messages, and update style. Squash-message limits and child retargeting are separately configurable.
9. **Repository - Issue (repository.issue)** — Issue settings include lock reasons and a per-repository pinned-issue limit. Setting the limit to zero disables pinning.
10. **Repository - Upload (repository.upload)** — Upload controls include enablement, temporary path, type allowlist, size, and file count. Empty or wildcard type rules allow all content.
11. **Repository - Release (repository.release)** — Release attachments reuse the attachment configuration section; this section sets allowed types and release-list pagination. It separates release presentation from shared attachment storage policy.
12. **Repository - Signing (repository.signing)** — Commit signing can use OpenPGP or SSH, with trust models and policy for initial commits, wiki, CRUD actions, and merges. Policies can require public keys, two-factor login, parent signatures, approvals, or signatures across every commit.
13. **Repository - Local (repository.local)** — Temporary local repository copies have a configurable path. Their contents are removed when Forgejo restarts.
14. **Repository - MIME type mapping (repository.mimetype_mapping)** — Administrators can map extensions to download Content-Type values. The example assigns Android packages their vendor MIME type.
15. **Badges (badges)** — Repository badges can be enabled and use a URL template for a generator service. The default template is shields.io.
16. **CORS (cors)** — CORS is disabled by default and exposes explicit origin, method, cache age, credential, and header controls. X-Frame-Options is configured here too, and the page warns that incorrect origins can be harmful.
17. **UI (ui)** — UI settings cover list sizes, feed and graph limits, themes, file display size, reactions, user-name display, search behavior, and ambiguous-Unicode detection. Detection can be skipped for selected rendering contexts.
18. **UI - Admin (ui.admin)** — Separate pagination defaults govern administrator lists for users, repositories, notices, and organizations. Each is adjustable independently.
19. **UI - User (ui.user)** — The user-facing repository list has its own page size. This does not alter admin pagination.
20. **UI - Metadata (ui.meta)** — Homepage author, description, and keyword metadata are configurable. These values affect page metadata rather than instance identity settings.
21. **UI - Notification (ui.notification)** — Notification polling uses a minimum delay, step, and maximum delay, increasing when counts stay unchanged. EventSource with SharedWorker can replace polling; a separate interval controls notification-count database refreshes.
22. **UI - SVG Images (ui.svg)** — SVG rendering is enabled by default. Disabling it makes SVGs display as text and prevents embedding them as Markdown images.
23. **UI - CSV Files (ui.csv)** — CSV table rendering has a byte-size cap. Zero removes that cap.
24. **Markdown (markdown)** — Markdown settings govern soft line breaks, extra URL schemes, recognized extensions, and math detection. Comments and documents can use different line-break behavior.
25. **Server (server)** — Server settings span data paths, protocol and bind addresses, public and worker URLs, SSH, TLS, LFS, compression, profiling, landing page, and graceful lifecycle timeouts. Proxy protocol, sockets, certificates/ACME, and request timeouts require choices matched to deployment topology.
26. **Database (database)** — The database section supports MySQL, PostgreSQL, SQLite, optional primary/replica routing, TLS, connection pools, retries, migrations, and slow-query logging. SQLite defaults to WAL for read concurrency, while pool sizing must respect database capacity.
27. **Indexer (indexer)** — Issue and code indexing can use local or external engines, with separate connection settings, paths, inclusion/exclusion filters, and size limits. Repository code indexing is off by default and uses substantial disk space.
28. **Queue (queue and queue.*)** — Queue-wide defaults select level, channel, Redis, or dummy storage and tune batching, lengths, connections, and worker counts. Forgejo defines named shared and unique queues; per-queue sections override common behavior.
29. **Admin (admin)** — Administrators can set default email notifications, restrict organization creation, disable user capabilities, and notify admins about registrations. External-login feature restrictions supplement the general user restrictions.
30. **Security (security)** — Security controls include install lock, persistent secrets, two-factor requirements, proxy identity trust, hook/webhook and local import controls, password hashing, password policy, and token handling. The page emphasizes safeguarding encryption secrets and warns that custom Git hooks can execute arbitrary host commands.
31. **Camo (camo)** — Camo image proxying is disabled by default and requires a server URL and HMAC key. The ALWAYS option extends proxying to HTTPS image URLs.
32. **OpenID (openid)** — OpenID sign-in and signup are separately configurable. URI regex allowlists and blocklists can constrain accepted providers.
33. **OAuth2 Client (oauth2_client)** — OAuth client settings control email confirmation, scopes, automatic registration, avatar refresh, account linking, and username derivation. Automatic linking based on matching identity data is explicitly risky unless providers are trusted to guarantee uniqueness.
34. **Service (service)** — Service settings define registration, login, email confirmation, external/reverse-proxy authentication, CAPTCHA, user defaults, dependencies, time tracking, visibility, and account lifecycle behavior. Proxy/API authentication has explicit CSRF responsibility, and external registration toggles alter who may create accounts.
35. **Service - Explore (service.explore)** — Explore can require sign-in or independently hide user, organization, and code listings. These switches affect discovery surfaces.
36. **SSH Minimum Key Sizes (ssh.minimum_key_sizes)** — Administrators can set minimum key sizes per algorithm or disable an algorithm with -1. DSA is disabled by default and reenabling it may require SSH daemon changes.

38. **Mailer (mailer)** — Mail supports SMTP variants, sendmail, and dummy logging, with transport-specific TLS, authentication, sender, and buffering options. Passwords may come from files; bypassing certificate checks is called unsafe, and SMTP authentication requires encrypted transport or localhost.
39. **Incoming Email (email.incoming)** — Incoming mail handling requires IMAP details and a tokenized reply address, with TLS, mailbox, deletion, and size settings. Handled messages are deleted by default.
40. **Cache (cache)** — Cache adapters include memory, Redis variants, two-queue, and memcache, with adapter-specific connection formats. Item TTL controls expiration, and -1 disables caching.
41. **Cache - LastCommitCache settings (cache.last_commit)** — Last-commit caching has a long default TTL and activates only for repositories above a commit-count threshold. These options target large repositories selectively.
42. **Session (session)** — Sessions may use memory, files, database, or external cache providers. Cookie security follows HTTPS ROOT_URL when unset; cookie naming, lifetime, domain, and SameSite are configurable, with a warning that strict SameSite can disrupt external OAuth login.
43. **Picture (picture)** — Avatar settings choose remote providers, federation, local storage, dimensions, size limits, and fallback behavior. Repository avatars have independent paths and fallback choices.
44. **Project (project)** — Project board defaults define basic Kanban and bug-triage columns. They are templates for newly created boards.
45. **Issue and pull request attachments (attachment)** — Shared issue/PR attachments have enablement, allowed types, size, and count limits. Storage location is configured through storage settings.
46. **LFS client (lfs_client)** — Mirroring an upstream LFS endpoint can cap pointers per batch and concurrent upload/download operations. These are client transfer controls.
47. **Log (log)** — Logging sets root path, output modes, global level, stack traces, and per-logger overrides. Access, router, XORM, and SSH loggers can be configured separately.

65. **Cron - Clean up deleted branches (cron.deleted_branches_cleanup)** — Deleted branches older than a day are removed at startup and daily by default. Success notices can be enabled.

72. **Cron - Delete generated repository avatars (cron.delete_generated_repository_avatars)** — Generated repository avatars can be periodically deleted by an optional job. It defaults to disabled.

## What it means for Concord v3
The **Server-side change landing** direction can adopt Forgejo’s separation of instance-wide policy from repository-specific defaults (Repository, Security, and Service sections), while Concord’s stated direct landing workflow avoids the PR merge-style machinery documented under Repository - Pull Request. The **Claims for presence** concept is a different coordination purpose from Forgejo’s repository locks and SSH/session settings; this page offers no evidence that locks on files are needed or that task coordination locks hurt. **Issue dependencies and ready set** align with Service’s explicit dependency defaults and repository issue controls, while Forgejo’s per-instance configuration and cron jobs show the operational value of configurable lifecycle policies. **Runs and swarms** could use Actions’ execution timeouts, retention, and task-liveness settings as operational comparisons, but Actions is a separate CI subsystem and does not establish Concord’s run model. **One operation table / HTTP, CLI, MCP** and **WebSocket events** have no direct analogue in this configuration reference; its HTTP/API and notification settings are deployment and UI controls, not a unified operation/event architecture. Its database and queue settings are relevant to the draft’s **TypeScript/Bun, git + SQLite on a VPS** deployment tradeoffs, though Forgejo’s options do not demonstrate that SQLite is sufficient for Concord’s expected concurrency. The page documents migration/mirror policy, but its **one-way GitHub mirror** direction should keep remote URL restrictions and outbound access in view.
