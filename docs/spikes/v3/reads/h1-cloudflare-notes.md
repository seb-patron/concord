## What it means for Concord v3
Workers can be inexpensive for the web UI and stateless control endpoints: the $5/month account floor includes 10M dynamic requests and 30M CPU-ms, while static asset requests are free/unlimited and egress/bandwidth is uncharged. A git forge has very different load: clones/fetches repeatedly request and transfer growing packfiles, and Worker CPU/request limits plus request charges need explicit modeling; the pricing page says no Worker egress fee, but does not make storage durable or provide a git server.

R2’s 10 GB-month, 1M Class A and 10M Class B free allowances, $0.015/GB-month Standard storage and free egress make it a plausible object-data layer, subject to git pack/read/write request pattern and metadata design. R2 storage scales with history retained; estimate repository growth and object operations instead of pricing only current checkout size. Containers have included but finite active compute and region-dependent egress, and therefore do not establish predictable always-on hosted forge economics by themselves.

Persistent WebSockets are billed as Worker upgrade requests, with messages not counted as Worker requests; Durable Objects separately bill messages under their request dimension and can bill wall-clock duration for nonhibernating accepted connections. A DO-per-repository shape makes idle-read and socket lifecycle costs multiplicative: v2’s reported ~$120/month idle-read leak is a concrete warning to count alarms, reads, live duration, storage and per-repo idle behavior. This pricing evidence supports the v3 concept of a single TypeScript/Bun git+SQLite server on a VPS for the stateful forge, with Cloudflare static UI or edge delivery considered separately; it does not quantify VPS economics.

## What it means for Concord v3
Workers are not a drop-in git server under these ceilings: the paired pricing page lists a $5/month Paid account minimum, 10M requests/month and 30M CPU-ms included, then $0.30/million requests and $0.02/million CPU-ms, with no egress/bandwidth charge. Even Paid handlers have 128 MB isolate memory and 5 minutes maximum CPU, request URL/header limits are 16/128 KB, and only six outbound connections can be awaiting headers at once. A clone/fetch packfile needs streaming, backpressure and retries; a push upload is additionally bounded by the zone plan’s request-body maximum (100 MB Free/Pro, 200 MB Business, Enterprise up to 5 GB). Worker response bodies have no enforced cap and HTTP wall time is unlimited while connected, but runtime drains, caller disconnect and CPU limits remain.

Static UI is a better fit: 20,000 Free or 100,000 Paid files per version, each at most 25 MiB, with the pricing page’s free/unlimited static request treatment. For hosted users bringing arbitrary repositories, 100/500 Worker account quotas and route/domain caps make per-repository Workers or routes a poor scaling assumption; service bindings share the six-connection ceiling. These limits reinforce the v3 single TypeScript/Bun server with git and SQLite on a VPS as the stateful core, while edge/static delivery may serve UI separately.

The v2 report of roughly $120/month in idle reads highlights that a technically permitted DO-per-repo topology can still have an unexpected cost profile. Limit review adds that DO WebSockets keep objects active absent hibernation, and long requests can still be cut by platform lifecycle events; claims and WebSocket event delivery must tolerate reconnects.

A SQLite-backed DO can hold at most 10 GB per object even on Paid, while each SQL row/BLOB is capped at 2 MB, which rules out storing a large repository as one row and makes large histories require sharding or an external git object store.
