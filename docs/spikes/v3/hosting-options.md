# Where Concord should run

## Summary and recommendation

Start Concord's stateful Git service on one rented virtual private server in a European region, with Git repositories and SQLite on local disk, an offsite backup, and test runners elsewhere. Ship the same server and browser code for self-hosted installs. For our hosted service, serve the browser interface as static Cloudflare Workers assets and send authenticated API and event traffic to the server. A self-hosted operator can serve those same files from the server, with no Cloudflare account. This keeps the first hosted bill predictable and the installation simple. It also preserves the owner's choice to build Concord as its own agent-oriented forge, with GitHub as a mirror. One server is a launch design, not a promise that it handles a thousand active repositories or survives a regional outage. Measure Git traffic, disk growth, sockets, and restore time before offering a large hosted tier. The comparison below is a scenario, not a forecast or an observed bill.

## Glossary

| Term | Plain meaning |
| --- | --- |
| Active repository | A repository with users or agents making requests during the month. It can still be quiet most of the time. |
| Virtual private server (VPS) | A rented virtual machine with a fixed CPU, memory, and disk allocation. |
| Static assets | The browser's HTML, JavaScript, CSS, images, and fonts. They do not need a server to compute each response. |
| Edge | A network service close to users that can deliver files or forward requests. |
| Durable Object | Cloudflare's stateful, single-threaded compute unit. Concord currently uses one per repository. |
| R2 / object storage | Storage addressed by object name. It suits backups and prepared files; it is not a replacement for live SQLite or Git without an adapter. |
| Artifacts | Cloudflare's Git-like repository storage product, billed by repository operations and retained bytes. |
| Egress | Bytes sent out to users or another provider. Git clones can use much more than page views. |
| Clone / fetch | A clone downloads a repository; a fetch downloads new history. Both can create network and CPU load. |
| Multi-tenant | Many customers share one service, while authorization and resource accounting keep their data separate. |
| Self-hosted | The customer runs the server, storage, backups, and updates on infrastructure they control. |
| Hosted service | We run the infrastructure and charge or otherwise support customer use. |
| Runner | A separate machine that executes checks or agent work. It must be isolated from the Git server. |
| WebSocket | A persistent connection for live events. An open connection need not generate application requests, but it holds resources. |
| Capacity limit | A point where disk, memory, CPU, transfer, connections, or an account quota forces a different deployment. |

## What we use and pay today

The supplied measured usage record covers Cloudflare account counters on October 12–15, 2026. Over those four days and the first three requests of October 16, it records 997,407 Worker requests and 1,175,856 Durable Object requests. Worker CPU was about 1.12 million milliseconds. The Durable Object counters include about 2.66 billion SQLite rows read. These are account totals, not per-repository measurements or a v3 forecast. On October 13 alone, the account had 508,963 Worker requests and 566,159 Durable Object requests. The included monthly allowances in the same record were 10 million Worker requests, 30 million Worker CPU milliseconds, 1 million Durable Object requests, and 400,000 gigabyte-seconds of Durable Object duration. The paid Workers plan has a $5 monthly list-price minimum under the Cloudflare pricing page retrieved October 16, 2026. The Durable Object request allowance had already been exceeded; the record does not include the invoice, so the full bill is unknown.

After the idle alarm fix deployed, the measured October 15 evening hours showed eight Durable Object requests and eight Artifacts events per hour, after an initial hour of 38 each. This is much lower than the earlier reported idle-read leak of roughly $120 per month, but it is not zero. The usage note records 486 Artifacts repositories holding 3.42 GB at 11:53 a.m. Central time. It explicitly says Artifacts billable usage was missing from the datasets. We therefore cannot state the actual Artifacts bill, map agent API calls to Artifacts operations, or claim that the old leak still costs $120 per month. The v3 architecture draft calls for removing the Artifacts adapter and keeping the v2 Worker live during migration; this report does not change that plan.

Local Git directories measured 11 MB for agent-workflows, 38 MB for gen-v-research-tools, 55 MB for Concord, 172 MB for mwcc-rs, and 542 MB for gen-v-decomp. Their simple mean is about 164 MB, but the spread is more useful than the mean: a customer can bring a repository several times larger than the typical one in this sample. The supplied record also counts 299–636 worker runs per day on October 10–14. Those are run-directory counts, not concurrent agents, Git operations, or billable model calls. The earlier platform spike used 10 repositories, 20 concurrent agents, 300 changes per day, and a peak of about 2,000 agent API calls per hour as a planning scenario. None of that establishes production capacity. The local event prototype held 200 quiet connections for 60.001 seconds with no additional HTTP requests, bytes, or application timers, and about 47 KB of combined server-and-client heap per connection. It did not measure a deployed bill, persistent replay, or production socket capacity. These distinctions follow the supplied event spike and platform review.

## The shared comparison scenario

All tables below are **estimates in US dollars per 30-day month**, before tax. They are price floors for the named components, not customer prices, all-in operating cost, or capacity promises. Published prices were retrieved on **October 16, 2026** from the vendor pages linked below, except the earlier platform review, which retrieved its corrected CPX42 and Durable Object figures on October 15. The service and usage assumptions are ours. They are deliberately explicit so a later measurement can replace them.

Each active repository starts with **0.2 GB of Git data**, rounded up from the five measured local Git directories' 0.164 GB mean. Assume **0.05 GB of additional retained Git history per repository per month**. At the end of the first year, that would be about 0.8 GB per repository before compression, forks, large-file storage, indexes, or backup versions. Current-month tables use 0.2 GB per repository. They assume **four full clones per repository per month at 0.2 GB each**, plus **60 fetches per repository per month at 0.02 GB each**: 2 GB of outbound Git traffic per repository per month. That fetch size is an estimate, not a measured transfer. Assume 30 changes per repository per month, four billed Artifacts operations per change, and one operation for each clone or fetch: **184 Artifacts operations per repository per month**. The actual operation mapping is unknown. Assume 3,000 dynamic API/event-setup requests per repository per month, 2 connected agents per repository during a work window, and 30 browser UI visits per repository per month, with five static file requests per visit. These request and visit figures are estimates; v2's much larger account request counts cannot safely be divided by active repositories or carried into a push-based v3.

For storage, the tables include one current-size copy of Git history in offsite object storage. They exclude backup versions, database snapshots, logs, large files, runner and model spend, paid support, domain and email, operator labor, incident recovery, VAT, and any unquoted transfer overages. The server also needs free disk for SQLite, packs, temporary files, and upgrades. A 0.2 GB repository therefore needs more than 0.2 GB of provisioned disk. For a hosted service, customer limits must be set from observed tail sizes and transfer, not the five-repository mean.

| Active repositories | Current Git data | Git growth in one year | Monthly Git egress | Connected agents in scenario | Monthly UI visits |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 0.2 GB | 0.6 GB added | 2 GB | 2 | 30 |
| 10 | 2 GB | 6 GB added | 20 GB | 20 | 300 |

| 1,000 | 200 GB | 600 GB added | 2,000 GB | 2,000 | 30,000 |

The growth column is twelve months at 0.05 GB per repository per month, not a measured growth rate. The 1,000-repository row does not imply that one machine can host 2,000 simultaneous sockets or the associated Git work. Every option needs request, bytes, disk, and socket measurements before capacity commitments.

## Hosting options

### Keep Cloudflare for the server and the UI

In this design, static Workers assets serve the interface. A Worker handles authentication and API traffic. One Durable Object per repository orders state changes and sends events. Artifacts stores Git-like repositories; R2 holds a separate current-size backup copy or prepared packs. A full v3 Git write and fetch path across these services still has to be designed and proved. The supplied pricing pages establish billing, not that Artifacts' current bindings implement every proposed Git operation. The platform review specifically rejected an unsupported claim that the binding cannot write commits; a direct API test is needed. The v3 draft instead proposes Git on local disk.

[Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/) gives a $5 monthly paid-plan minimum, 10 million dynamic requests and 30 million CPU milliseconds included, then $0.30 per million requests and $0.02 per million CPU milliseconds. Matching [static asset requests](https://developers.cloudflare.com/workers/static-assets/billing-and-limitations/) are free and unlimited, and assets have no extra storage fee. [Durable Objects pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/) includes 1 million requests and 400,000 gigabyte-seconds per month, then $0.15 per million requests and $12.50 per million gigabyte-seconds. SQLite rows and storage have separate charges. [Artifacts pricing](https://developers.cloudflare.com/artifacts/platform/pricing/) includes 10,000 operations and 1 GB-month, then $0.15 per 1,000 operations and $0.50 per GB-month. [R2 Standard pricing](https://developers.cloudflare.com/r2/pricing/) includes 10 GB-month, 1 million write/list operations and 10 million read operations; excess storage is $0.015 per GB-month and direct egress is free. All five pages were retrieved October 16, 2026, in the supplied Cloudflare notes.

The estimate below assumes Artifacts holds one current-size copy, R2 holds another, dynamic requests hit both the Worker and the repository's Durable Object, and Durable Object duration, SQLite rows, Worker CPU, and R2 operations stay within their included allowances. The included allowances are account-wide. Figures combine the paid-plan minimum and estimated Artifacts, R2, and Durable Object excess; they do not count the same $5 base twice. Artifacts operation rounding may move cents to the next billing unit.

| Active repositories | Estimated monthly priced components | Main unpriced exposure |
| ---: | ---: | --- |
| 1 | about $5 | Git adapter development, rows, duration |
| 10 | about $5.50 | same |
| 100 | about $16 | same; 18,400 assumed Artifacts operations |
| 1,000 | about $134 | same; 184,000 assumed Artifacts operations and 3 million assumed Durable Object requests |

This is a low component-price scenario, not evidence that Cloudflare is the cheapest working forge. It assumes only 3 million Worker requests at 1,000 repositories. If each repository instead makes 100,000 dynamic requests per month, the Worker request component alone rises by roughly $27 at 1,000 repositories, before extra CPU, Durable Object requests, duration, rows, storage, or operations. That sensitivity matters because the measured v2 account generated nearly one million Worker requests in about four days. The measured data do not tell us v3's request rate after polling is removed.

The main limits are engineering and quotas. [Workers limits](https://developers.cloudflare.com/workers/platform/limits/) give a 128 MB isolate, a five-minute paid HTTP CPU maximum, six simultaneous outbound connections awaiting headers per invocation, 100 MB Free/Pro request bodies, and limits on routes and Worker count. [Durable Object limits](https://developers.cloudflare.com/durable-objects/platform/limits/) cap a SQLite-backed object at 10 GB and describe a soft 1,000 requests-per-second limit for one object. Those pages were retrieved October 16, 2026. A large Git push or hot repository can hit a different limit long before the account reaches a storage total. Nonhibernating sockets can accrue duration; eligible hibernation avoids idle duration but still bills setup and incoming messages. An alarm, unfinished I/O, or reconnect storm can reverse the cheap-idle estimate. Cloudflare outages, storage/API changes, and a complex custom Git adapter are the failure and lock-in risks. Keeping live Git state in Artifacts and Durable Objects would make later self-hosted parity harder unless the storage interfaces and export path are tested from the start.

### One VPS for Git, API, events, and optionally the UI

Run the proposed TypeScript/Bun server, Git command line, and SQLite on one VPS. Keep bare repositories and databases on local disk. Serve UI files from Bun on the same origin or publish the exact same files to a static CDN. The Git server controls writes and can stream smart HTTP clones and fetches. Separate runners execute untrusted work. Nightly encrypted Git bundles and consistent database copies go to an independent object store; practice a complete restore. These are architecture requirements, not capabilities verified by the supplied prototype.

The corrected [Hetzner price-adjustment page](https://docs.hetzner.com/general/infrastructure-and-availability/price-adjustment/) lists the European CPX42 at **$81.99 per month** in the earlier platform review, or €69.49 on the October 16 source capture, before VAT and IPv4. The earlier spike records its shape as 8 vCPU, 16 GB memory, and 320 GB NVMe. The dynamic [Hetzner Cloud page](https://www.hetzner.com/cloud/) did not expose a numeric transfer allowance or overage rate in the supplied capture. Do not infer free Git egress from that omission. [Hetzner Object Storage](https://www.hetzner.com/storage/object-storage/) is $7.99 per month with 1 TB of storage and 1 TB of egress included, then $8.86 per additional TB-month and $1.20 per additional TB of egress. It bills at least 64 KB per object, so packed backup archives fit better than tiny loose objects. The latter three sources were retrieved October 16, 2026.

| Active repositories | Estimated monthly priced components | Capacity reading |
| ---: | ---: | --- |
| 1 | $89.98 | Large fixed minimum for a small installation |
| 10 | $89.98 | 2 GB current Git data fits the listed disk, subject to tests |
| 100 | $89.98 | 20 GB current Git data fits by bytes; CPU and transfer unproved |
| 1,000 | at least $89.98; expansion unpriced | 200 GB current Git data, 800 GB after one year, plus working space: the 320 GB disk cannot hold the year-one scenario |

The table assumes the offsite backup copy stays under the object store's 1 TB included storage. It does not price the VPS's outbound traffic because the supplied Hetzner page does not give the allowance or excess rate. A constant VM list price does not mean total cost remains constant as traffic, storage, backups, and labor grow. A single VPS also means power, disk, region, deploy, or operator errors can take all repositories offline until restored. SQLite and a single writer per repository simplify correctness but do not give automatic failover. At high scale, partition repositories across servers, keep customer and repository identity stable across moves, and test migrations and restores before adding a second live writer. A VM and standard Git/SQLite data formats offer relatively low provider lock-in, although moving live traffic and backups still takes work.

### Hybrid: Cloudflare UI and edge, VPS Git and server

Host the browser files as Workers static assets. Send API calls, Git smart HTTP, and WebSockets to the VPS; use a small Worker only where edge authentication or routing actually adds value. This is the recommended hosted launch shape if the VPS is chosen. The static path reduces UI bandwidth on the VPS and deploys independently. The server still authenticates and authorizes every operation. It cannot trust an edge header alone. A Cloudflare outage can affect login, routing, or UI even while the VPS is healthy, and the VPS remains the source-of-truth failure point.

The same [Workers prices](https://developers.cloudflare.com/workers/platform/pricing/) and [static asset billing](https://developers.cloudflare.com/workers/static-assets/billing-and-limitations/) retrieved October 16, 2026 apply. This scenario conservatively reserves the $5 paid-plan minimum, though a static-only deployment might fit the free tier; no free-tier production guarantee is assumed. It adds the Hetzner VM and backup prices above. At the assumed 3,000 dynamic requests per repository per month, all four rows fit the Workers included monthly request volume if a Worker handles each API call. The table excludes any unquoted edge-to-origin transfer and the VPS's unquoted outbound transfer.

| Active repositories | Estimated monthly priced components | Capacity reading |
| ---: | ---: | --- |
| 1 | $94.98 | Fixed VM, backup, and Workers plan |
| 10 | $94.98 | UI delivery scales separately from Git |
| 100 | $94.98 | Git CPU, disk, egress, and sockets still need tests |
| 1,000 | at least $94.98; expansion unpriced | VPS disk and likely compute need a larger or partitioned fleet |

This option adds routing, certificates, two deployments, and cross-provider troubleshooting. It buys a cheap static UI and leaves the stateful code portable. If direct browser calls cross origins, the server must manage credentials and cross-origin policy correctly. Prefer one public hostname with explicit paths when possible, and verify that WebSocket upgrades and large Git transfers pass through the selected route without buffering. The supplied sources do not establish a tested Cloudflare Tunnel price or a transfer guarantee. Do not count a tunnel as automatic high availability.

### Fly.io machine with volume, as a second VPS-like choice

Fly.io can run the same Bun/Git/SQLite image on a continuously running machine with a persistent volume. It is credible for a small deployment, especially where a region or machine workflow is convenient. The [Fly.io pricing page](https://fly.io/docs/about/pricing/), retrieved October 16, 2026, lists a shared CPU machine with 2 vCPU and 2 GB memory at $13.39 for 30 days in its lower-price US region example. It lists provisioned volumes at $0.15 per GB-month, snapshot bytes at $0.08 per GB-month after the first 10 GB, and North America/Europe outbound traffic at $0.02 per GB. These are separate charges. The earlier draft's $43–$51 quote for a four-core, 8 GB machine was not supported by the source and is not used here.

For this table, provision a volume of at least 10 GB or twice current Git data plus 10 GB, whichever is larger. Assume one snapshot copy equal to current Git data and the same $7.99 independent object backup as the VPS table. Charge 2 GB of outbound Git traffic per repository at the source's North America/Europe rate; do not assume a CDN hit ratio. The 2 GB machine is a price floor, not a tested capacity match for the workloads. Values are rounded estimates.

Snapshots on the same provider are operationally helpful, but do not replace an independent backup. A Fly machine and its volume share a regional failure domain. More regions add cost and require a single-writer or replication design for SQLite and Git. Fly's documented per-byte egress makes large clone traffic easier to price than the captured Hetzner page, but its volume billing grows with reserved capacity. The platform API and volume layout create more deployment coupling than a generic VPS; Git and SQLite data can still be exported.

## One codebase, two ways to run it

The owner has already chosen Concord as its own forge and GitHub as a mirror in the architecture draft. The remaining hosting choice is how to deploy that forge. Keep one core server and one set of HTTP, CLI, Git, event, and browser behaviors. Package a versioned image or binary with a documented data directory. A self-hosted installation can use one server, local Git and SQLite, a reverse proxy for TLS, and optional remote runners. It should not require our Cloudflare account, billing service, or hosted login. Exporting Git history, database data, and configuration must be possible without a vendor API. The UI can be bundled static files served by the same process.

Our hosted service adds an account-to-repository boundary. Every API, Git, event, backup, and cache path must bind a request to the correct customer and repository before reading or writing. A shared database or filesystem prefix alone is not an authorization boundary. Keep per-repository write ordering, but make customer identity, ownership, roles, token scope, and deletion explicit. If one customer exhausts disk, sockets, or runners, others must retain their budget. Start with quotas for repository bytes, monthly Git transfer, concurrent connections, change operations, runner minutes, and retained backup versions. Meter the same units the service pays for; record peaks, not only monthly averages. Give administrators a safe migration path between hosts as one VPS fills. Keep customer secrets separate from build/test runners. Define data deletion, retention, and restore ownership before taking third-party repositories. These are design needs, not implemented v3 features.

Billing belongs in hosted mode. A self-hosted operator pays their own cloud bill and decides whether to charge their users. The hosted service needs plan enforcement, usage attribution, invoices or another payment mechanism, abuse limits, and a policy for overages or suspension. The supplied sources do not price Concord's model calls, runner machines, support, or payment fees, so no break-even customer price is justified here. A no-charge tier could be considered only after the service can cap history storage, clone traffic, run spend, and recovery obligations. Publish what counts toward each quota; do not hide a Git byte cost behind an agent request count.

Upgrades also split. We can deploy hosted patches centrally and migrate customer data in controlled waves. Self-hosters need pinned releases, backup-before-upgrade instructions, schema migration and rollback rules, compatibility windows for CLI and API clients, and a security-update channel. One server codebase can still have optional hosted billing and administrative services around it. Avoid a second, diverging Git engine or UI. That boundary is a design recommendation drawn from the following vendor precedents, not a claim that Concord already has those facilities.

The [Forgejo FAQ](https://forgejo.org/faq/) and [Codeberg description](https://docs.codeberg.org/getting-started/what-is-codeberg/), retrieved October 16, 2026, show a self-hostable forge and a separate hosted community service based on it. They do not disclose Codeberg's hosting bill or exact architecture. Forgejo's image tags support automatic patch or minor updates, while major upgrades require human verification. [Plausible's self-hosting page](https://plausible.io/self-hosted-web-analytics), retrieved the same day, describes a shared codebase, customer-run Community Edition, and a managed Cloud service whose subscriptions fund development. Plausible assigns backups, uptime, and upgrades to self-hosters, while its Cloud manages those jobs. Its analytics workload cannot size a Git forge.

[PostHog's self-hosting page](https://posthog.com/docs/self-host) says its hosted and self-hosted products share behavior but the operator runs and upgrades the self-hosted stack. Its [Kubernetes support retrospective](https://posthog.com/blog/sunsetting-helm-support-posthog) says a small share of deployments caused a disproportionate support burden; the lesson for Concord is to keep the supported self-hosted footprint narrow. These sources were retrieved October 16, 2026; the retrospective was published February 8, 2023. [Sentry's self-hosting guide](https://develop.sentry.dev/self-hosted/), retrieved October 16, lists billing, spend allocation, and some managed features as hosted differences. It also warns that its self-hosted package has no dedicated support. Sentry's license has restrictions on competing hosted use; it is a precedent for deployment shape, not a license recommendation for Concord. [GitLab's pricing page](https://about.gitlab.com/pricing/) distinguishes GitLab.com, customer-operated Self Managed, and managed single-tenant Dedicated. Its [installation requirements](https://docs.gitlab.com/install/requirements/) say repository storage must cover all repository histories and show how added services enlarge the footprint. Both were retrieved October 16, 2026. GitLab's listed customer prices are not evidence of its infrastructure cost or a Concord price. Across all five precedents, common product behavior can coexist with different operational responsibility; none supplies a proven Concord socket, clone, or cost limit.

## Where the web UI should live

The UI is mostly static files and should be built once for both modes. For our hosted service, publish it as Cloudflare Workers static assets on the public hostname. Matching static requests are free and unlimited under the retrieved [asset billing page](https://developers.cloudflare.com/workers/static-assets/billing-and-limitations/) from October 16, 2026; Worker code executed first would change those economics. Keep authenticated data and event streams on the server, with explicit routes through the edge if needed. This gives a fast, low-cost page delivery path without turning Git clone/fetch into Worker code. It also allows the UI to remain reachable as a static page during an API outage, where it should show a clear service error rather than stale private data. The UI needs version compatibility with the API; deploy a compatible server before new browser code, or pin assets to the server version.

For self-hosting, include those same compiled files in the server package and serve them on the same origin. That removes a required CDN account, keeps login and WebSocket routing simple, and lets an operator add their own CDN later. A same-origin single server costs no extra static-hosting subscription, but UI requests and transfer share the server's capacity. The monthly scenario has only 30–30,000 UI visits and 150–150,000 assumed static-file requests; without file sizes, it cannot price UI egress. Measure actual bundle size, visits, cache hit rate, and browser errors before moving any additional UI logic to the edge. Neither Cloudflare static assets nor a CDN gives the stateful Git service high availability.

## Recommendation and owner decision questions

**Where should the first hosted Git service run?** Recommend the one-VPS Bun/Git/SQLite design with offsite backups and external runners. It has a clear starting compute price and a portable state store. The CPX42 is a priced starting point, not a tested minimum or a promise of 20-agent capacity. Verify CPU, disk, traffic allowance, restore time, and Git push/fetch behavior before launch. If the vendor's actual outbound transfer terms or sustained CPU make it poor value, compare a measured Fly or another VPS deployment on the same workload.

**Should we keep Cloudflare?** Recommend keeping it for the hosted static UI and optional ingress. Do not commit v3's live Git store to Artifacts and Durable Objects now. Their unit prices can be low, but the supplied evidence leaves write-path fit, operation mapping, duration, and large-pack behavior unproved. Keep Cloudflare as a future server option only behind tested Git and event interfaces. The owner's prior direction to move live updates to push after submission remains relevant regardless of host; the local idle prototype supports that design but is not a production bill.

**Should we offer both self-hosted and hosted Concord?** Recommend yes, from one core codebase. Ship the self-hosted package first or alongside a small private hosted pilot. Make the hosted service multi-tenant only after tenant authorization, quotas, backup/restore, usage metering, deletion, and upgrade paths are tested. Do not set public plan prices from these infrastructure floors. The precedents show a shared product with distinct operating duties, not a free path to scale.

**When should a single server become several?** Recommend a measured trigger, not a repository count alone. Track occupied disk and free working space, full and incremental clone bytes, pack CPU, SQLite latency, peak event sockets, request rate, backup duration, and restore time per repository and tenant. Use the largest repositories in the pilot, not the mean, for capacity tests. Before the first server fills, add a repository-placement map and move whole repositories to additional servers under one-writer rules. Price replication and failover only after the desired recovery time and data-loss window are chosen. Until then, present the service as a single-node pilot with tested restore, not a highly available forge.
