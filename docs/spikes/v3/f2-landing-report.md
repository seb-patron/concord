## Design changes implied by the reads

1. **Separate candidate work from ref publication.** Build immutable change/revision objects and merge candidates concurrently. Serialize only the expected-old-value update of a shared branch ref. A failed CAS invalidates any tests tied to the old candidate and requires recomputation. This is consistent with Git plumbing (PR #88, `r4-bors-git-notes.md`, “git-merge-tree” and “git-update-ref”), Zuul/GitHub speculative candidates (PR #87, `r1-scion-queues-notes.md`, “Project Gating” and “Managing a merge queue”), SubmitQueue (PR #86, `r2-submitqueue-notes.md`, “Keeping Master Green at Scale”), and Mononoke's per-bookmark landing (PR #94, `r3-mononoke-notes.md`, “System Architecture”). It does not make “disjoint files” a proof of semantic independence.
2. **Make test tiers and promotion states explicit.** Keep “submitted,” “candidate built,” “pre-land checks passed,” “landed,” “post-land batch checked,” and “reverted/paused” distinct. The evidence supports both speculative pre-merge gating (Zuul, GitHub, SubmitQueue, bors) and post-merge testing (Scion) (PR #87, `r1-scion-queues-notes.md`, “Project Gating”, “Managing a merge queue”, and “Redesigning source control at Anthropic”; PR #86, `r2-submitqueue-notes.md`, “Keeping Master Green at Scale”; PR #88, `r4-bors-git-notes.md`, “bors-ng README.md and FLOW_EXAMPLE.md”); no single source says one tier fits all repositories. `D-LANDING-SPIKE` remains a research decision; present the hybrid as a proposal and measure CI capacity, conflict/retry rate, and red-main duration before approving defaults.
