# How often did a worker need files beyond its specification?

## Plain answer

**A code-aware work specification usually named enough files for a candidate to pass the launcher's file gate, but that is only a lower bound on planning accuracy.** In the collected run history, a small fraction of implementation attempts left a visible record of needing an undeclared file. Many runs declared files they never changed, and repairs to an existing pull request sometimes introduced files absent from the first run's list. For Concord v3, the evidence supports treating an initial list as a revisable claim request: record each attempted addition, permit an authorized mid-run grow operation, and verify the final diff. It does not establish that issue text alone can predict the right initial claims or that a particular lease policy improves throughput.

The key correction to the earlier audit is that a launcher state called `refused-scope` is **not** synonymous with editing outside the Allowed list. The state also covers malformed or absent candidate commits. The earlier declared-footprints study counted roughly 13% of runs in that state; this study reads the launcher's actual unmatched-file lines. That changes the meaning of the number, not the historical records. “Allowed files” means the repository-relative paths named in a worker run's `allowed-files.txt`. A “visible need” is either a launcher refusal that identifies an unmatched file or a blocked implementation report that explicitly says an additional file is required but out of scope. A “claim held for nothing” here means a declared file absent from the candidate diff; it is a proxy for unused file-level lease occupancy, not a measurement of an actual Concord lease.

## Results

**Finding 1 — STRUCTURAL (source: launcher runs through 2026-10-16).** The scan found **9,781 unique eligible runs** after discarding archived copies of the same recorded run. They comprise **7,203 implementation runs** and **2,578 review-only runs**. Reviews are counted in the repository, worker, kind and state tables but excluded from prediction rates. The implementation runs split into **4,898 first runs** and **2,305 repairs onto existing pull requests**. A run is called first when it has no target pull request; a target pull request makes it a repair. This is a launcher metadata classification, so a mislabeled target remains possible. The [raw output](../../../../spikes/v3/round2/c5/output.txt) gives every repository, agent/model, run-kind and final-state stratum, including small and unknown groups.

**Finding 2 — CAPABILITY-DEPENDENT (source: worker runs through 2026-10-16; re-test with current agents).** Across implementation runs, **164 of 7,203** had a visible need, **2.3%** with a simple 95% Wilson interval of **2.0–2.6%**. The initial and repair rates were **125 of 4,898 (2.6%)** and **39 of 2,305 (1.7%)**, respectively. These are observed failure signals under the old launcher, not the probability that a worker actually discovered a missing file. Their distribution depends on agents, orchestration, task mix, and how much code the spec writer had already read. For example, Concord's visible rate was **27 of 738 implementations (3.7%)**, while the research-tools repository had **7 of 538 (1.3%)**. Worker differences are also visible in the raw table, but model mix is confounded by task and repository mix.

**Finding 3 — STRUCTURAL (source: launcher diagnostics through 2026-10-16).** The final state was `refused-scope` in **1,325** eligible runs, but only **35** had an explicit unmatched-file diagnostic in the saved log. A sample of the other state reasons included failures to create a bounded candidate, no commit, wrong candidate shape and Git metadata problems. The unmatched diagnostics named **94** distinct extra-file mentions across those refusals, counted per run. The state-name count from the earlier study therefore substantially overstates the number of confirmed file-list misses. Conversely, an agent can have needed another file but stopped before attempting an out-of-scope edit; accepted diffs cannot reveal that need.

**Finding 4 — CAPABILITY-DEPENDENT (source: worker reports through 2026-10-16; re-test with current agents).** Of **473 blocked implementation runs**, a conservative text rule flagged **129** as saying an additional file was needed outside the allowed scope. The rule searches only the report's `Blocked:` section and requires three cues together: a need or impossibility word, a scope/authorization phrase, and a file or path cue. It avoids general prompt boilerplate and does not treat a failed test elsewhere as a file requirement by itself. I hand-checked a seeded random sample of **30 blocked reports**. The rule agreed with the reading in **27 of 30** cases: three flagged reports were ambiguous or described environment/PR work rather than an explicitly needed repository file. This is **90% sample agreement**, a quality check on the rule, not a sensitivity estimate for all missing needs. The rule can miss reports that explain the problem outside the `Blocked:` section or use different words. Extra-file counts from blocked prose are approximate path mentions; a zero visible path means unknown, not zero needed. Across the 164 visible-need runs, **21** had no extractable path, **92** had one, **23** had two, and **28** had three or more; these are text counts, not adjudicated unique required files.

**Finding 5 — CAPABILITY-DEPENDENT (source: local candidate commits through 2026-10-16; re-test with current agents).** Of **4,354 completed implementation runs**, **4,056** had a locally usable base-to-candidate diff. The remaining **298** do not enter the unused-file denominator. In diffable completions, **5,570 of 21,967** declared entries were unchanged, or **25.4%** (simple Wilson 95% interval **24.8–25.9%**). The first-run share was **17.4%** and the repair share **37.9%**. The figures pool file entries, so large specifications contribute more than small ones. They measure declared-but-unchanged entries, not necessarily mistaken declarations: a file may have been read, examined, reserved for a plausible branch, or edited then reverted. The Wilson ranges treat entries as independent even though files from one run and repeated repairs are correlated; use them as descriptive uncertainty only.

**Finding 6 — CAPABILITY-DEPENDENT (source: linked pull-request runs through 2026-10-16; re-test with current agents).** Among **323** pull-request families with both a recorded first run and a later repair, **88 (27.2%; simple 95% interval 22.7–32.3%)** had at least one repair declare a file beyond the first list. There were **653** linked repair runs, of which **154 (23.6%; interval 20.5–27.0%)** enlarged the first list; their lists contained **313** added entries across repairs and **195** distinct additions after deduplication within a family. This is declaration growth across separate runs, not an observed mid-implementation lease claim. **961** repair families lacked a locally observed first-run baseline and are excluded from that comparison. The conditional rate should not be generalized to all repairs. The raw tables also split linked repair growth by repository and worker.

## Method and reproduction

The script scans every readable worker directory under the local agent-runs root that has `allowed-files.txt` and either `work-spec.md` or `prompt.md`. It does not traverse local clones, nested worktrees, dependency directories or scratch directories as if they were fresh runs. It deduplicates archived copies by the `run_dir` value in `status.json`, falling back to their directory identity, and retains missing-status records as an explicit final-state group. Fixture-like repository labels are retained in the raw table but do not drive the interpretation. Blank and comment lines in the allowed list are ignored. The scan reads metadata and report/log files, and never changes a source run or clone. It writes only aggregate tables; no source-run file list, spec prose or report text is committed.

Repository comes from status metadata; agent and served model are used when present, then requested or observed model, then `unknown`. Review-only is determined from explicit review flags or launch class before checking for a target pull request. The final state is kept as recorded, including failures, cancellations and malformed candidates. The implementation prediction denominator includes first and repair attempts of every state. That is why the visible-need share is an attempt-level share, not a completion-only success rate.

For file-refusal evidence, the script requires `refused-scope` plus a saved launcher line identifying a path unmatched by the Allowed list. It reads the log's tail, where scope checks normally appear, and recognizes both old and newer diagnostic forms. A status label alone never counts. The blocked-report rule is declared above and implemented in the script, making false positives and false negatives inspectable. The random sample uses seed **20261016**. The manual labels treated blocked prose about a PR body, shared test environment or unspecified future source change as negative unless it clearly identified a repository file outside the run's scope. This conservative judgment is part of the measurement, not a fact established by the regular expression.

For a completed non-review run, the script tries `git diff --name-only` between the saved base and candidate identifiers in the matching local clone, then the run worktree. The optional `--gh` switch tries a read-only pull-request diff if local objects cannot be resolved. That fallback was attempted but did not finish in the available run; the committed output uses local Git only and counts undiffable completions explicitly. A completed run means a launcher state of `pr-opened`, `no-push` or `pushed`, rather than a judgment that the change merged. The unused share is `declared paths absent from changed paths / declared paths` over diffable completed implementations. Exact path matching makes renames and generated side effects important limits. A declaration of a directory, glob or placeholder is not a measured file claim; this history principally uses exact paths.

Repairs are grouped by recorded target or resulting pull-request URL. Within each group, the earliest observed first-run declaration is the baseline. Every repair's declared set is compared against that baseline, and additions are also deduplicated within the family. The run's saved update time orders multiple first-run records; this is a proxy for chronology, not proof of when a file was discovered. No first-run record means growth is unknown. The output uses Wilson 95% intervals for proportions with at least ten observations; for smaller denominators it prints `n<10`. Those intervals describe sampling variability under independent Bernoulli observations and omit repository/task clustering. They are deliberately not causal estimates of what v3 would do.

Reproduce the local aggregate with `PYTHONDONTWRITEBYTECODE=1 python3 spikes/v3/round2/c5/spec_prediction.py`. The exact command and raw tables are saved in the output file. The script is Python standard library only. The previous `s5-declared-footprints.md` report counted the broad status and compared declarations with commits; the `final-c3-blind-footprints.md` report found very little genuinely pre-specification text and identified answer leakage. The full-read `claims-options.md` source, dated 2026-10-15, distinguishes the owner's approved declare/grow/verify direction from shipped v2 behavior. The decision record confirms the measurement request (D-MEASURE-SPEC-PREDICTION), the approved research plan (D-RESEARCH-PLAN-2-GO), the earlier C+ plan (D-LEASE-Q5-CPLUS) and current exclusive-unit policy (D-UNIT-1-EXCLUSIVE). `npm run -s decisions` was attempted but local `tsx` was missing, so its live-status list was unavailable; the readable decision record and supplied owner-status snapshot were used instead.

## Limits and v3 implication

**Structural limit (source: launcher design and these runs, through 2026-10-16):** the launcher refused edits outside the Allowed list. Refusals and explicit blocked explanations are the only visible signs of a miss, and the true miss rate can be higher. A completed diff cannot prove that its declaration covered every needed file. The earlier 25.2% unused-entry estimate from a broader, differently filtered history is directionally similar but not a replication on an identical denominator.

**Capability-dependent limit (source: orchestration practice and worker runs through 2026-10-16; re-test later):** orchestrator agents wrote these specifications and often inspected code first. Their Allowed lists were informed plans, not blind predictions from issue text. The results do not justify automatically reserving all files inferred from an issue, nor do they measure agent behavior after a live grow/wait API exists. Repository mix is uneven, attempts within a repository are related, and older models and launchers coexist with newer ones.

**Structural implication (source: owner decisions recorded 2026-10-12 to 2026-10-16):** a v3 claim protocol should preserve a versioned initial declaration, make later additions explicit and observable, and derive the final changed units at publication. The old plan says declare, grow and verify, while exclusive claims remain the decided policy; this measurement supports instrumenting that workflow rather than setting a lock scope or lease timeout from these percentages. Record every attempted extra file, when it was discovered, whether growth was granted or denied, wait time, abandoned work and the accepted final diff. That prospective record would turn today's censored lower bound into a useful measure of planning accuracy and the cost of mid-run growth. The choice of a default claim policy still needs the separate, approved v3 tests.
