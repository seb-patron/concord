# How well did work specifications name the files workers needed?

## Plain answer

**This history cannot tell us actual planning accuracy or how often an agent would need to increase a lease claim during implementation.** The old launcher enforced each run's allowed-file list. A worker could discover a missing file and stop without creating a measurable edit, while a report parser can mistake an unrelated permission request for a file need. The repaired measurement therefore reports three different things: machine-detected signals, needs established by reading a small sample of reports, and unknown needs outside that sample. It does not turn the absence of a signal into a planning success.

The frozen archive has **5,990 implementation attempts**. A rule marks **197** of them as possible missing-file needs. That is a count of **parser flags**, not confirmed needs or a lower bound on them. In a separate hand-labeled set of **30** blocked reports, **14** actually requested a repository file outside the grant. The rule agreed on **27**: **12** true positives, **15** true negatives, **one** false positive and **two** false negatives. These cases were held out after tuning on a different thirty reports. The sample checks the rule's behavior; it cannot establish how many needs went unreported among all implementation attempts.

The other measurable pressure is declaration growth across separate attempts: **89 of 326** linked pull-request families with an observed first implementation later declared at least one additional valid file. That is evidence of changing specifications across runs, not evidence that an agent made a mid-implementation claim increase. A versioned declare, grow and verify workflow remains the sensible object to instrument, as the owner's prior plan says, but these historical counts cannot choose its lease policy.

## Terms and a worked example

A **work specification** is the task text prepared for a worker. Its **allowed-file declaration** is the list of repository-relative file paths the launcher permitted it to edit. The **file gate** is the launcher's check that a candidate change stays inside that list. A **candidate** is the attempted Git change; its **diff** lists files changed between the saved starting and candidate commits. A **claim** or **lease** reserves a code **unit** for a worker. Here the measured unit is a file; Concord's broader design also considers symbols. **Grow** means requesting another unit after work has started. Historical worker runs did not record that operation directly.

For example, suppose a run declares two valid files, completes, and its saved Git diff changes only one. This audit counts one declared-but-unchanged entry; it cannot say whether the other declaration was wasted, because the worker may have inspected or temporarily edited that file. If a later repair declares a third file, the family counts as growing. If the first run instead stops and asks to add a file, the report parser may flag a possible need. A human still has to decide whether that report actually asks for an additional repository file. None of these observations says when a lease would have been requested or how long a worker would have waited.

**STRUCTURAL** findings arise from the data collection or enforcement design and are expected to persist across agent models. **CAPABILITY-DEPENDENT** findings describe behavior of the agents and task mix in this dated archive; they should be re-tested with current agents. A **stratum** is a subgroup such as repository or run kind. A **fixture** is a fake or probe run and is excluded from worker rates.

## Three measured results

**First, the population changed after review — STRUCTURAL (source: worker archive scanned 2026-10-16).** The frozen manifest contains **9,795** unique eligible records after **1,764** archived duplicates were skipped. It excludes **45** fixture or unknown records from worker rates. Of the remaining **9,750** worker records, **3,760** are review-only and **5,990** are implementation attempts: **3,703** first implementations and **2,287** repairs. Review-only classification comes from explicit metadata for **2,586** runs and strong legacy prompt evidence for **1,174**. The legacy rule requires a final or independent review cue, a no-edit instruction and an outcome cue near the beginning of the prompt. This fixes the prior error in which older reviews without modern metadata were treated as first implementations. A few ambiguous old prompts could still be misclassified; provenance is preserved in the raw table and manifest.

**Second, missing-file signals are incomplete — CAPABILITY-DEPENDENT (source: launcher logs and worker reports through 2026-10-16; re-test with current agents).** The launcher state called `refused-scope` occurs in **1,325** worker records. Only **15** have a clean, genuinely omitted valid path in a saved unmatched-file diagnostic. **Nineteen** instead point to a malformed grant record, and **one** mixes both forms; these groups are separate. The diagnostic is not inferred from the state name alone. The blocked-report rule marks **182 of 461** blocked implementation reports. The union of those flags and clean omissions is **197 of 5,990** implementation attempts, or **3.3%**. The first-run and repair flag counts are **157 of 3,703 (4.2%)** and **40 of 2,287 (1.7%)**. These are text-rule rates, not estimates of true need or true planning failure.

The rule reads an inline or multiline `Blocked:` section. It needs a request or necessity cue, a file-scope permission cue and a file/path cue. It recognizes requests to add, permit, widen or extend allowed files. It does not automatically count a request to rerun validation or a restriction on shell commands as a file need. The held-out labels use a conservative definition: a positive report explicitly requires a repository file outside the grant, even when it proposes a later authorized repair. The one false positive presented a possible scope-widening option alongside an alternative acceptance change; the two false negatives requested a new grant in language the rule missed. Those observed errors prevent treating all **197** flags as adjudicated needs. The **14** positives in the held-out reports are adjudicated for that sample only. The number of genuine needs in the full archive remains unknown.

**Third, declaration size and growth are conditional — CAPABILITY-DEPENDENT (source: local saved Git endpoints and declarations through 2026-10-16; re-test with current agents).** **4,327** implementation attempts ended in a completion state; **4,030** have a usable local before-and-after Git diff, leaving **297** unscored for unchanged declarations. In diffable completions, **5,428 of 21,554** validated declared entries did not appear in the diff, **25.2%**. The first-run count is **2,328 of 13,312 (17.5%)**; the repair count is **3,100 of 8,242 (37.6%)**. These are pooled file entries, so a long specification contributes more observations. Entries within the same run and repairs in one family are related; a simple independent-entry uncertainty interval would understate that dependence. The result describes these runs; it cannot show that a claim policy caused the pattern.

Missing diffs are concentrated. The workshop repository has **351** completed attempts, but only **63** diffable completions and **288** excluded completions. That accounts for **288 of 297** undiffable completions in the worker population. Its **7 of 254 (2.8%)** unchanged-entry result describes a particularly selected subset. The repository table in the raw output reports both completed-diffable and completed-undiffable denominators for every repository. Pooling without that split would conceal the selection.

Among pull-request families with an observed first implementation and a linked repair, **89 of 326 (27.3%)** contain a repair with a larger validated declaration. **150 of 652 (23.0%)** linked repairs declare at least one additional valid file relative to the earliest observed first-run list. Those repairs contain **299** added entries across runs and **192** distinct additions after deduplication within families. Another **945** repair families have no observed first-run baseline and cannot be scored for growth. Saved update time orders first-run records but is only a chronology proxy. Invalid declaration records are excluded from both the unused-entry and growth calculations.

## Method, audit trail and limits

The script reads local worker directories with an allowed-file marker and a task prompt or specification. It excludes clones, nested worktrees, dependencies and scratch trees while finding runs, and deduplicates archived copies by their recorded run identity. It does not edit source runs or clones. Each run gets a SHA-256 identifier derived from that identity. The committed [manifest](../../../../spikes/v3/round2/c5/manifest.tsv) contains those hashes, source-content fingerprints, classification provenance, final state, per-run counts and hand labels. It contains no run paths, declared file names, task text or report excerpts. The [raw aggregate](../../../../spikes/v3/round2/c5/output.txt) gives every repository, worker/model, state and classification-provenance stratum, with denominators and the privacy-safe hand-label ledger.

The input root is required at the command line. The local fresh-scan command is `PYTHONDONTWRITEBYTECODE=1 python3 spikes/v3/round2/c5/spec_prediction.py --input-root "$RUN_ROOT" --refresh-manifest`, where `RUN_ROOT` is set privately to the local worker-run directory. That command deliberately replaces the frozen snapshot. The same command without `--refresh-manifest` rebuilds every published table from the committed per-run count snapshot and does not rescan mutable runs. The saved source fingerprints support a later audit of the snapshot; replay does not claim that source files have remained unchanged. The output records the manifest digest and the exact neutral replay command. Local Git diffs use saved base and candidate commit identifiers. A current pull-request diff is never substituted for a historical candidate. No web source or model was queried for this repair.

Declaration validation accepts one normalized, relative file path per line with conservative path characters and a file-like basename. It quarantines whitespace-separated grants, directory and glob (wildcard) placeholders, prose and code fragments rather than guessing which files they meant. There are **767** quarantined entries across **541** worker runs. This conservative syntax can also quarantine a real file whose name contains spaces or is extensionless outside the recognized common names; the quarantine count is therefore a quality flag, not a count of bad worker intent. A refusal whose path appears inside a malformed line is classified as malformed-grant evidence, not silently counted as an omitted declaration. The sole mixed refusal is reported separately.

The hand check used a deterministic SHA-256 ordering of eligible blocked-run identifiers with seed **20261016**. Ranks **0–29** were a parser-development set. Ranks **30–59** were read and labeled separately after the rule was fixed; their identifiers, parser flags and labels are in the raw output and manifest. The **27 of 30** agreement is a diagnostic on this narrow sample, not a representative confidence interval for the entire history. Reports may omit their discovery, describe it outside `Blocked:`, or ask for a change that would not ultimately be necessary. A candidate diff is likewise censored by the file gate: accepted edits cannot reveal an unattempted outside file. Unknown is not zero.

The owner's supplied decisions snapshot, `owner-decisions-2026-10-16.md` with its status TSV, records the measurement request (D-MEASURE-SPEC-PREDICTION) and the approved round-two plan (D-RESEARCH-PLAN-2-GO), both dated **2026-10-16**. Those two entries are not in this revision's checked-in `docs/decisions.md`; they are cited as supplied snapshot decisions. The checked-in record does contain the earlier declare/grow/verify plan (D-LEASE-Q5-CPLUS) and exclusive-unit policy (D-UNIT-1-EXCLUSIVE). The full-read `final-c3-blind-footprints.md` explains why code-aware work specs are not blind issue predictions; `s5-declared-footprints.md` supplies the older broad state and declaration comparison; `claims-options.md` separates the approved plan from shipped behavior. Their evidence cutoff is **2026-10-15**. The local `npm run -s decisions` command failed because `tsx` is unavailable, so its live-status list could not be checked here.

**Structural implication (source dates: owner decisions and launcher design, 2026-10-12 to 2026-10-16):** to identify actual planning accuracy, freeze the task before code-aware specification, record each discovered unit, attempted grow request, grant or refusal, wait, abandoned attempt and final verified diff. **Capability-dependent implication (source date: worker archive through 2026-10-16; re-test with current agents):** agent discovery and repair behavior may change. The historical attempt rates and declaration-growth rates should not be used as the expected live grow frequency or as a gate for a lease design.
