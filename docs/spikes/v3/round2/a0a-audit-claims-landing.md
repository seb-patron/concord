# Concord v3 draft 4: claims, landing and work-loop audit

## Plain answer

Draft 4 is **not yet a reliable statement of the chosen design**. Its shared-by-default code claims reverse the owner's active exclusive-claim rule; the owner has approved research into alternatives, not that reversal. Its issue model records dependencies and a task, but does not say who owns work on an issue through implementation, review and repair. Its landing diagram combines a local Git demonstration with unapproved choices about test gates, automatic reverts and review. Draft 5 should distinguish current owner rules, tested mechanisms, research recommendations and questions still awaiting evidence. It should keep **code units (files or symbols)** distinct from issue work claims, presence signals and landing authorization.

A **claim** is a server record of who is working on a resource. An **exclusive code-unit lease** refuses a competing writer for a file or symbol during its writing phase. A **fence** is a generation number that makes an old grant unusable after a new grant or owner release. **Revision-bound authorization** means the permission to land is attached to one exact version of a change. **Server-held phase authority** means the server keeps that permission valid while it runs checks, review or the landing queue, subject to a defined end time. **Reconnect grace** is a short interval for a disconnected agent to resume; it is separate from the maximum time an abandoned claim may remain. A **change** is a proposed revision; **landing** makes it part of the canonical Git history. A **merged tree** is the candidate result of combining a change with the current main branch. A **ready issue** is one eligible for dispatch after its blockers and ownership rules are checked. These are different objects and need different lifetimes.

A **syntax-tree parser** (tree-sitter) finds code structure; Git's **function-name rules** (funcname) label code regions for diffs. Neither supplies **human-checked semantic ground truth** about which symbol owns an edit. A **proxy** is an indirect measure, such as agreement between those tools. A **safe fallback** widens an uncertain symbol claim to its file; **atomic authorization** grants all requested units together or none. A **working-tree-free Git operation** (plumbing) writes Git objects without changing checked-out files. A **compare-and-swap** updates the main branch only if its prior commit is still the expected one. A **state machine** lists allowed status changes. **Candidate invalidation** discards a check result when the merged candidate changes; **stale-result rejection** refuses a result for an expired or replaced attempt.

For the studies below, **diffable runs** have a recoverable final file difference; **blind prediction** estimates needed code units from an issue before seeing the work plan or answer. **Versioned selection** stores which issue set a run chose and when. A **budget broker** reserves and accounts spend across agent sessions; **query-local accounting** reports only one provider request, so an in-flight request may **overshoot** a run limit. **Approval carry-forward** reuses a prior review on a later revision. A **speculative stack** tests a proposed ordered set of changes before landing. A **batch tip** is the final commit of one tested landed group; **bisection probes** retest subsets to locate a failure. **Bounded union** combines only proven append-only text; **index regeneration** rebuilds generated output from its source. **End-to-end reconciliation** compares declared claims with the exact changed units before publication. A **leaky redacted tier** hides some answer clues but retains others; **answer-derived sets** use final changed files as hindsight. **Queued-version stacking** starts new work from a reviewed change that has yet to land. A **composed merge** is the combined result of multiple changes; **downstream fencing** makes a late former holder's write fail. A **red-main policy** states what happens when checks fail after main has moved.
