# Build contract for the local claims prototype

16 October 2026. Six bounded runs use real Git objects and scripted agents to compare issue custody, code handover and queued previews on matched past work. Report completed work, waits, repairs, checks and owner intervention. Protocol success cannot prove composed-code correctness. This local study is authorized (round-two research decision, D-RESEARCH-PLAN-2-GO). Show gains beside penalties with no preset bar (results decision, D-GAIN-SEE-RESULTS).

**STRUCTURAL (design and reviews, 16 October 2026):** issue slots, code leases and landing authorizations grant distinct authority; a clean merge proves no semantic compatibility. **CAPABILITY-DEPENDENT (worker studies, 15 October 2026; retest later):** service, repair and wait reactions may change. Numbers below are prototype assumptions or dated anchors, not production defaults. Maximum issue-claim age remains open (D-LEASE-MAX-AGE-OPEN).

## Vocabulary, sources, and invariant

An **issue work slot** reserves one ordinary task across writing, inspection, review, repair and landing; the **actor** is the agent temporarily allowed to write. An **issue generation** rises when an issue reopens; an **actor epoch** rises on transfer; a **fence** rises on each new code grant. A **code unit** is a file or a verified Python symbol. A **principal** is an authenticated identity, and a **stable intent** is one attempt's retry identity. **First publication** sends a revision and ends its blocking writing lease, while server custody continues. A **landing authorization** binds a revision, footprint, checked tree and review. A Git **tree** is content; a **commit** adds parents. An **OID** is Git's object identifier. A **prefix** is a consecutive ordered set of queued revisions; its **preview commit** is a disposable prospective parent. A **ticket** binds that prefix and queue epoch. A **CAS** operation moves `main` only when it still equals the expected OID. A **manifest** freezes replay inputs; an **event ledger** records requests and transitions. **Right-censored** work has no observed completion by the cutoff. The supplied `c123-claims-design.md`, `c123-repair-ledger.md`, `round2-review-astra-120.md`, and `delta-review.md` supply the rules; the supplied snapshots of owner decisions settle authorization, not prototype values. References to review findings below use descriptive names, then their review labels in parentheses.

All new files must live under `spikes/v3/round2/proto/`. Use Python 3 standard library (`ast`, `sqlite3`, `subprocess`, `json`, `hashlib`, `tempfile`, `unittest`, `resource` where available) and the installed Git command line. No package, model, network, paid service, private artifact in Git, or local promoter is needed. `sqlite3` gives one serialized authority and durable events; Git computes actual trees. The source clones and worker records remain read-only. Set `PYTHONDONTWRITEBYTECODE=1`; all disposable Git repositories, indexes, overlays, databases and reports go under an explicitly passed scratch directory. Nothing in this contract authorizes a source-ref update. The earlier supplied `sp-b-landing.md` and its script/output show object plumbing and compare-and-swap only, not claims, semantic checks, or production throughput.

All caps start at phase entry in simulated time and expire before an action at an equal timestamp. A named owner extension must be issued before expiry, include a reason and finite replacement deadline, and be recorded as a separate event. No heartbeat extends server custody. A wait deadline is absolute from first refusal; idempotent retry, pause, priority change and fresh-auth turn do not reset it. At expiry the wait becomes terminal, releases priority, and returns `WAIT_EXPIRED`; a later attempt requires a new request key. A turn ends at `min(opened+45 s, wait deadline)`. At a phase cap, late results lose authority and the issue enters Intervention. Intervention expiry atomically cancels the attempt to Open. These rules come from the design lifecycle and the missing wait deadline finding (N1). **Worked example:** a code refusal at 12:00 expires at 12:05; a pause at 12:02 until 12:17 cannot extend it. A reasoned owner extension made at 12:04 to 12:09 does. The owner unpauses at 12:07:59; a fresh-auth turn opened at 12:08 then lasts 45 seconds, ending at 12:08:45. Without unpause there is no turn.

## Replay input and time rules

**Contract choice (B5): archive adapter v1, frozen 16 October 2026.** Parse positive `wall_clock_used_s` as a JSON number or a base-ten numeric string (no exponent, trim whitespace); reject other strings. `retry_of` accepts a string job ID or an object with required string `job_id` and optional string `attempt_id` and `run_dir`; normalize to `{job_id,attempt_id|null}` and use `run_dir` only as a contained archive locator. A run is `review` when its recorded kind is review or its job metadata links it to a reviewed candidate/revision; otherwise `implementation` when kind is work and no review linkage; ambiguous kind is excluded and audited. Review runs contribute reviewer service, never implementer actions. Prefer explicit candidate OID, then exact linked change revision; `prompt.md` is the work-spec fallback only when `work-spec.md` is absent, and an absent `Validation:` block remains missing. Preserve original field locator and normalized value separately. **Worked example:** status duration `"2701"` becomes 2,701,000 scenario milliseconds; `retry_of:{"job_id":"j","attempt_id":"a"}` links retry `a` to job `j`; a linked review run is excluded from implementation duration. These sanitized shapes reflect the independent review's 16 October archive sample; adapters for new archive versions require a named schema revision.

The source cohort is local Concord, agent-workflows, gen-v-research-tools, mwcc-rs and gen-v-decomp history, by repository labels only in the public report. Sort linked attempts by observed run start UTC, then run ID. Join a candidate and landing only by exact OID or explicit target-change/retry link. Group an explicit issue link first, then a target-change or replacement link; otherwise assign that change a synthetic issue and mark it. Never infer a duplicate from similar prose. Select the first 30 fully linked sequential lands and first ten overlap/replacement attempts per repository if present; audit all failed, cancelled, undiffable, and unlinked records. Retain denominators and exclusion reasons. This is the design's selection rule; the blind-footprint study (15 October) found that final diffs cannot reveal first-touch times and many Allowed lists censor demand.

**Service-time precedence (contract choice resolving R8).** For each run, first use `usage.json.started_at` and `ended_at` when both parse as UTC and end is after start. If absent, use a pair of timestamped `run.log` lifecycle start and terminal markers for that same run ID, with no intervening restart marker. If absent, use a positive numeric `status.json.wall_clock_used_s` plus the run-name UTC as a start proxy, explicitly labeled scenario start; never use `updated_at` as a terminal time. If all fail, use the repository's mixed-session median from the 15 October cost model: Concord 4.5, agent-workflows 10.6, research tools 13.2, mwcc-rs 10.9, decomp 6.1 minutes. These are mixed-role proxies, not measured active service; label the entire demand `scenario`. A zero, negative, over-24-hour, contradictory, or cross-run interval is missing. Preserve the rejected fields and reason in the private audit. `status.json` supplies state, `retry_of`, issue and Git links, never an assumed duration. In a three-record local schema sample, `usage.json` had both time fields and `status.json` had no top-level duration; this sample establishes field availability only. **Worked example:** a valid 10:00–10:12 usage interval gives 12 minutes even if a later status update is at 10:20. A missing usage file and a positive 420-second status field give seven scenario minutes anchored to the run-name start. If both are absent in a Concord implementation, use 4.5 scenario minutes and bound it by 2.25 and 9.

`run.log` supplies productive actions only when a line contains a parseable UTC timestamp, run identity, and explicit planning result, edit/first touch, check completion, review response, or repair step; a generic heartbeat and the final diff do not qualify. Reject nonmonotone/out-of-session entries. An Allowed list is an initial declaration only if a timestamped claim submitted it before editing; otherwise it is a candidate declaration, not observed authority. Diff changed lines from exact parent and child OIDs supply actual units, never discovery order. Commit time can bound order but cannot become active service. Missing history uses an identical synthetic action sequence for every policy: plan for 20% of service, discover and edit the actual changed units in lexical normalized-path-and-line order for 50% (equal slices; empty footprint uses one no-edit slice), local validation for 20%, send for 10%. Claim at each first touch, then perform that slice's work; an initial observed declaration, if verified, is claimed before plan. Each edit slice emits one productive event at completion. An observed action offset replaces its corresponding synthetic offset only if the whole same-run sequence is coherent; otherwise keep the all-scenario sequence and audit why. Reverse first-touch order and all-up-front declaration are separate lower/upper assumption scenarios; they never masquerade as history. **Worked example:** with a 20-minute run and two changed units, plan occupies minutes 0–4, each discover/edit action takes five minutes, validation four, and send two. Reversing unit order changes waits but not the two five-minute edit demands or the progress sequence.

For deterministic parsing, an observed log marker must be one JSON object on a line with `ts` (UTC ISO 8601), `run_id` matching the enclosing run, and `event` exactly one of `work.plan.complete`, `work.edit`, `work.check.complete`, `work.review.response`, `work.repair.step`, `work.send`, `run.start`, `run.restart`, `run.end` or `claim.submitted`; `work.edit` also requires `path`, `start_line` and `end_line`. `work.send` closes worker service. `run.restart` requires a new `session_id` and makes log-derived duration/actions ineligible across that boundary; usage timing still takes precedence. Unstructured prose is not timing evidence. `run.start`/`run.end` can supply a duration only as a valid pair in one session. If this strict grammar finds no entries in older logs, the entire action sequence is scenario-labeled, and the audit reports zero observed actions rather than guessing from prose. This **contract choice (B6)** favors an honest missingness count over parser-specific interpretations of private logs. **Worked example:** start 10:00, plan 10:02, edit 10:05, check 10:08, send 10:09, end 10:10 is complete if the selected duration is ten minutes; a restart at 10:04 or a send after end rejects the observed action sequence and invokes the full scenario split.

Use observed action service only when markers cover start, plan completion, every changed unit's first edit, check completion, send and end, in order, within the chosen service interval. Each action demand is the elapsed difference from the preceding marker; simultaneous markers yield zero-demand actions, and the sum must equal the selected run duration. Otherwise use the complete percentage split above and mark every scheduled action `scenario`, while preserving any partial markers in the private audit as partial evidence. A log-derived full interval that disagrees with a valid `usage.json` interval is rejected in favor of the usage interval and scenario action split. This **contract choice (R8)** gives a builder an exact action-allocation rule without treating a single first-edit line as an entire work trace.

Worker actions are nonpreemptive while executing. A blocked actor retains its worker slot and issue custody, but its next action's remaining service and discovery offset **pause** until grant or terminal release; simulated time and the ten-minute no-progress clock keep advancing. A grant starts the paused action without changing its demand. A dead actor stops renewal, and a hung actor can keep renewing but cannot invent productive events. Repair uses a linked repair run's observed duration where available, otherwise the same-repo proxy; unchanged draft work has zero-reuse and full-reuse sensitivity bounds. Inspection and review are separate server jobs, using linked observed intervals only when uniquely attributable to that exact revision; otherwise use table scenarios. Phase caps may censor their longer service. Queue delay is derived from arm state and one ref writer; the five-minute value is a service-demand assumption, not an exogenous landing timestamp. This resolves action scheduling and blocked time (R9). **Worked example:** last progress at 08:55, refusal at 09:02 and three minutes of edit remaining. At 09:05 no-progress expiry revokes the turn; a 09:06 grant to that actor is refused. A new authorized actor may start at 09:06 and finish its own three-minute edit at 09:09. Its new epoch and lease fence are recorded.

Freeze arrivals, demand/actions, initial `P..C` deltas and fault keys by issue/action, not historical queue timestamps. Dispatch an eligible arrival to the lowest numbered free worker slot; ties are `(arrival UTC, repository, issue key, run ID)`. At one simulated timestamp process, in order: cancellation/revocation and deadline expiry; completed actions; wait advancement; checker/reviewer completions; queue decisions; new admissions; dispatch. Within a category use repository, issue key and request sequence. Checkers serve FIFO by `(ready time, issue key, revision OID)`; a reviewer job enters its separate FIFO only after all required check results are known. No reviewer job starts on unavailable semantic checks except the explicitly marked protocol-only oracle. Review completion precedes queue admission at the same time. One ref writer selects earliest reviewed eligible queue entry, then issue key; no later prefix jumps an earlier dependency. This ordering is a **contract choice (R9)** to make tied events reproducible. **Worked example:** a review and revocation occur at 12:00. Revocation wins; the just-finished review is logged stale and cannot enqueue.

The v2 baseline has immediate code refusal and no wait record. An online actor polls its unchanged request at `first refusal + 2n` seconds, with a new call ordinal each time while its change/run remains active, up to the five-minute absolute wait deadline; each call is counted. A terminal refusal, crash or actor expiry ends attempts. The recommended mode auto-enqueues by default, with a per-request opt-out and refusal details: holder, principal/intent, issue, units, position and advisory expiry. It scans eligible first-in-first-out requests on release, expiry or first publication; disjoint requests may pass, overlapping ones cannot barge. A multi-unit claim is all-or-nothing. The fresh-auth arm opens a 45-second priority turn when all units are free; an online client sends a newly authenticated claim after two seconds, then polls no more frequently than every two seconds; a dead/offline client makes no call and loses the turn. A revoked client is refused. To expose response uncertainty, run a named 60%-attempt sensitivity with a separate `random.Random(seed)` stream keyed by `(seed, repository, issue key, turn ordinal)`; baseline remains deterministic and always attempts when online. **Worked example:** a turn opens at 10:00:00; an online client claims at 10:00:02. An offline client misses it; at 10:00:45 the next eligible waiter is offered priority. A revocation at 10:00:01 beats the 10:00:02 claim. These are contract choices for R9 grounded in the wait-line study's 45-second, two-second and 60% scenarios.

## Authority and composition rules

**Contract choice (B9): canonical policy-independent diff action.** Each changed hunk records `old_path|null`, `new_path|null`, `old_range|null`, `new_range|null`, `change_kind: add|delete|modify|rename`, and `ordinal`; ranges are one-based inclusive and null means that side has no lines. Split hunks into actions by contiguous changed span in Git diff order, then sort by normalized new path (old path for deletion), first nonnull line and ordinal; file and symbol policies consume exactly these actions. For insertion, compare the new lines with the old-side insertion anchor (the line before insertion, zero allowed); for deletion compare old lines with the new-side deletion anchor. An unchanged line shift uses matching node chains after coordinate translation. Choose the innermost uniquely matched function/method containing **all** changed lines on both sides; if no such node exists, try the enclosing class, otherwise widen to file. Deleting a method has no new node and widens; editing inside `Box.open` chooses that method rather than `Box`; inserting a blank line above `open` shifts coordinates but preserves its key. **Worked example:** deleting old lines 20–22 gives `new_range:null`, cannot masquerade as a new-tree range, and claims the file. This conservative fallback is structural, sourced from the symbol design of 16 October 2026.

**Contract choice (B4): complete arm policy, frozen 16 October 2026.** `R` means recommended rules below. All arms retain owner cancellation, exact-tree land checks, current principal validation and CAS; the no-code-lock arm reports expected exclusive-write safety violations separately and cannot be called a safe product arm. A repair is a fresh revision, checks and review in every arm. A baseline “turn” below is its change/run lifetime, since baseline has no exclusive issue slot.

| Arm | Issue/code acquisition and growth | Refusal, send, queue and distinguishing trace |
| --- | --- | --- |
| `v2` | No issue exclusion; declared file/symbol code units, grow on discovery. | Immediate refusal, online 2-second polls until five-minute stop or change end; send releases code, no preview. Two disjoint actors start one issue and both spend service. |
| `recommended` | One issue generation, incremental exclusive code; FIFO automatic wait with opt-out. | First send releases code; server custody through queue; reviewed preview offered. A second ordinary actor is refused while first is in review. |
| `atomic_start` | One issue plus **initial declared** code set in one transaction; empty set permits issue claim; growth uses R FIFO. | Failure to get any initial unit refuses both; later send/queue as R. A busy declared file leaves the issue Open where R would visibly claim it. |
| `fresh_auth` | R issue and code, but no automatic grant; priority turn requires current authenticated request. | Send/queue as R. An offline head misses its 45-second turn; next waiter proceeds. |
| `hold_through_queue` | R issue and growth; exclusive code holds retained and server-renewed through queue, bounded by queue phase and cancellation. | First send does **not** release code; land/eject/timeout does. A later same-unit writer waits even after predecessor review. |
| `preview_off` | R issue/code/wait. | First send releases code; child dispatch uses current main, not queued preview, and later rebase demand is counted. |
| `no_code_lock` | R issue slot, no exclusive code holds or code wait; declarations remain audit data. | First send, queue and exact check as R; overlapping edits may fail composition. Two actors on distinct issues edit one file concurrently. |

For `hold_through_queue`, renewal uses the 100-second server cadence and preserves fences; expiry, ejection and owner cancel release holds. For baseline, first-send release applies only to its actual code lease, never a nonexistent issue claim. **Worked example:** with A holding file F and B arriving on another issue, R lets B claim F after A sends at minute 10; hold-through-queue delays B until A lands at minute 20. This trace is reported beside any reduced rebase cost, under the full-results decision (D-GAIN-SEE-RESULTS).

The local principal table, issue state, holds, waits and queue share one SQLite writer and a monotone integer event clock. An authenticated claim checks live principal, open issue generation/version, stable intent, current actor epoch, change state, policy version and all requested units in one serialized transition. A transport replay of the same request key and call ordinal returns the same grant or refusal without extending deadlines; a later ordinal may re-evaluate availability but keeps the first-refusal deadline. A new grant increments each unit fence; renewal preserves it. First send verifies the diff against every held file or symbol unit, rejects undeclared changed units, releases blocking holds except in the named hold_through_queue arm and creates revision-specific server custody. Issue edits require acknowledgment; after send they invalidate inspection, review and queue results. Owner close or cancel invalidates every wait, code fence and landing authorization; reopen starts a new generation. Repair gets a new actor epoch and fresh code leases for **all** replacement-footprint units, including unchanged names. A contest is only a declared exception flag; this prototype does not invent contest scheduling. These are the reviewed design's custody rules (R1, R2 and R6) and the issue-claim redesign decision (D-ISSUE-CLAIM-REDESIGN). **Worked example:** writer A sends revision R and relinquishes the file hold. Review fails, so R loses landing authority. Repairer B claims the same issue slot with a new actor epoch and file fence; B's replacement must be checked and reviewed anew. A's late send is refused. The owner can cancel either actor or server custody immediately.

Wait advancement checks access revocation in the *same* transaction as grant. If a future deployment cannot order its identity catalog that way, the fresh-auth turn is the only permissible handover; a queued credential never becomes a grant. Owner force-release, cancel, pause and reasoned move-to-front are distinct requests. Pause prevents grants but does not stop deadlines; moving a waiter changes overlapping queue priority without changing its age or active holds. Build a waits-for graph containing both current holders and earlier conflicting queued requests. If cyclic, the youngest issue attempt (first claim time, then lexical intent tie) loses its holds and outstanding waits; append its still-needed request with a new sequence but the original deadline. **Worked example:** A holds X, B waits for {X,Y}, and A grows to Y. B waits for A's X while A waits behind B on Y. If B is younger, remove B's queue position even if B holds nothing, grant Y to A, then requeue B. This resolves the reviewed FIFO cycle (R7) and retains the owner wait controls (R13; D-LEASE-WAIT-LINE, D-LEASE-QUEUE-AUTO). An expired wait is terminal; no agent may renew it by retry (N1).

**Full symbol identity (contract choice resolving R11).** The Python-only canonical key is a versioned tuple `(repository label, normalized POSIX relative path, ordered node chain, leaf kind)`; the chain contains *every* enclosing class/function **and the node's own name**, with each segment `(kind, name)` from the CPython `ast` tree. Serialize as JSON with Unicode names preserved and sort keys lexically, not by line number. Thus top-level `def alpha` and `def beta` have `[(FunctionDef,alpha)]` and `[(FunctionDef,beta)]`; `class Box: def open` has `[(ClassDef,Box),(FunctionDef,open)]`. `async def open` has leaf `AsyncFunctionDef`, distinct from `FunctionDef`. A file key is `(repository, normalized path, file)`, overlaps all its symbol keys, and aliases both old and new path on a provable rename. Normalize `.` and separators, reject `..`, absolute paths and case-fold collisions; keep repository identity in every key. A line-number shift caused solely by unchanged text inserted *outside* the node leaves its key and lease identity stable. A changed decorator, signature, node header, nesting, start/end boundary, name, kind, or ambiguous duplicate chain widens the entire touched file to file scope on both parent and child. Import, module-level code, generated and non-Python files, parse failure and unprovable rename also widen. A changed line must map uniquely to the same full chain on both trees; otherwise widen. **Worked example:** adding a blank line above `alpha` shifts its line numbers but an edit inside `alpha` stays symbol-keyed; moving `alpha` inside `Box` changes the chain and both sides fall back to the file. Two separate function bodies can hold concurrently; two edits inside `alpha` cannot. This is a conservative CPython test slice, not a replacement for the owner's language-agnostic product direction (symbol test decision, D-TEST-SYMBOLS; lease-engine decision, D-LEASE-LANGUAGE-AGNOSTIC).

At extraction, freeze one underlying `Action` per observed or scenario first-touch/progress event, with its changed path and line range, service duration and logical ordinal. Both file and symbol arms replay **that exact action sequence and duration**; only `units.map_action(parent, child, action, policy)` changes the requested key. Do not derive new symbol actions or extra productive events when a file splits into symbols. Count eligible Python attempts, uniquely verified symbol pairs, and every file fallback; compare file-only and symbol policies on the same eligible attempts, also reporting the whole workload separately. **Worked example:** one action edits line 12 of `alpha` at logical minute 4 and another line 30 of `beta` at minute 9. File policy requests the same file twice; symbol policy requests two keys. Both emit progress at minutes 4 and 9 of active service, with any blocked interval shifting both later. This fixes the review's matched-progress concern (R11) and prevents granularity from silently changing the hang workload.

An eligible historical attempt takes the **longest exact reviewed queue prefix available at its own first dispatch**, ordered by queue admission sequence; the ticket names main OID, queue epoch, ordered revision OIDs, preview commit OID, tree OID and policy version. If none exists, use current main. Never choose by eventual historical land or by a later prefix. The same original parent/delta is transplanted onto that selected preview once, with a conflict logged rather than a fabricated edit. A preview-off arm always chooses main. A new preview commit has the preceding preview commit as its sole parent; child C has preview parent P. On predecessor failure, ejection, replacement or priority move, invalidate every descendant's ticket, pending results and authorization. Stop Claimed child actors and revoke their code fences and waits; published children become server-custodied repair offers. Reapply only `P..C` to new valid prefix N with `git merge-tree --write-tree --merge-base=P N C`; create C-prime with sole parent N, then obtain new actor, every replacement-footprint lease, checks and review. Equal tree OIDs do not imply equal ancestry. **Worked example:** reviewed A queues before B dispatches, so B sees A's preview. If A is ejected, B cannot land on its old ticket even if the B diff is textually clean; B's isolated delta is rebuilt on current main and rechecked. These are the design's queue rules and the reviewed ancestry/repair corrections (R2, R5, R9).

Only one scratch bare repository's `refs/heads/main` may move. Before `git update-ref refs/heads/main NEW OLD`, write a durable landing intent with old/new OIDs, ticket, authorization versions, revision and check digest. Cancellation and final authority recheck take the same short process lock as CAS. Cancellation acknowledged first wins; successful CAS first is a land, and a later cancel becomes a separate revert/repair request. Reconcile an interrupted intent on restart: ref at NEW means land completed, OLD means abort or revalidate, any third OID halts that repository sequence for investigation. Limit CAS retries to three. Test crashes before CAS, after successful CAS and before completion recording. `git merge-tree` clean, conflict and error are distinct. This follows the supplied landing script and design's race repair (R3, R16). **Worked example:** a cancel arriving during CAS waits for the lock; if CAS succeeded, the ledger records a post-land request rather than pretending that the commit vanished.

## Exact-tree validation and result classes

**Contract choice (B3): successful predecessor transition.** After CAS lands predecessor A, record `(preview A OID, landed A OID, tree OID)` and advance every descendant ticket to the new main/queue epoch. If the child's preview parent P equals landed A as a **commit**, preserve C; otherwise transplant only `P..C` onto landed A or the new valid prefix N, create C-prime, revoke old ticket/authorization, and require a fresh actor epoch, complete replacement-footprint leases, exact checks and review before admission. Never substitute equal tree OIDs for commit identity. **Worked example:** A's preview and landed commits contain equal trees but have different parents; B's old ticket is invalid, so B's delta is transplanted, checked and reviewed before B can land. If the two commit OIDs are identical, B's unchanged ticket may be reissued against the new epoch after authority recheck; no content is rewritten. The transition is durable before B's queue decision.

For each selected attempt, freeze literal `Validation:` commands from its linked work spec in order, executable path/version, declared required inputs, dependency/cache hashes and nonsecret environment. The history extractor does not guess a command when none is recorded. An absent or empty recipe creates one explicit `UNAVAILABLE_ENV` result with reason `MISSING_COMMANDS`; Git integrity checks alone cannot certify semantic land. **Contract choice (B1):** require at least one reproducible semantic command because an empty universal condition would otherwise pass. A runnable checker starts a disposable writable checkout **at the proposed combined commit** inside scratch, verifies `HEAD` and tree OID before the first command, and runs the frozen commands in one overlay in order with a 120-second timeout each. Set `HOME`, `TMPDIR`, `XDG_CACHE_HOME`, `PYTHONDONTWRITEBYTECODE`, and any documented tool output variable to scratch paths; the immutable source bare repo and its objects remain read-only to the checker. Capture stdout, stderr, exit code, elapsed wall and process CPU, output-path manifest and before/after tracked-file hashes. Permit disposable **untracked** build products in the overlay only when declared by the recipe; keep them for later listed commands, then discard the overlay. A tracked-file change, declared or not, invalidates certification of the original tree: record `UNAVAILABLE_ENV` with reason `TRACKED_OUTPUT`, discard the overlay, and require a new candidate revision with its own checks and review. **Contract choice (B2):** this prototype refuses tracked regeneration during a check because passing tests on rewritten content would certify the wrong tree; the owner's separate land-time regeneration direction (D-UNIT-6-REGEN) remains a product design, not evidence for this original revision. Attempted source-ref write, missing dependency/input, sandbox permission error or timeout is also `UNAVAILABLE_ENV`, never candidate failure or pass. An ordinary nonzero command exit with a complete compatible environment is `FAIL`. A zero exit for every required command plus `git diff --check OLD NEW` and scratch `git fsck --connectivity-only` is `PASS`, bound to exact tree and old-main OIDs. Redact secret values from logs, and never export private output. **Worked example:** declared untracked `dist/` survives between commands and is discarded afterward; a generated tracked `src/generated.py` makes the original revision unavailable even if tests then exit zero. An empty recipe likewise yields `MISSING_COMMANDS`, one protocol-only result, and zero semantic lands.

The scripted review oracle accepts only an exact revision/tree with all required checks `PASS` and no injected review-failure flag. It issues a digest of revision, tree, old main, check results and issue version; historical labels do not certify a new tree. If **any** semantic check is `UNAVAILABLE_ENV`, run an explicitly named `PROTOCOL_ONLY` branch: a fake check response can drive review, queue and CAS in a disposable scratch repo to test fences and ticket invalidation, but its lands are `protocol_lands`, excluded from semantic accepted-land rate and correctness claims. `FAIL` never becomes a fake pass in the semantic branch. Show a repository command/coverage table before comparison. **Worked example:** a missing compiler gives one protocol-only land after simulated approval and zero certified semantic lands, with the missing compiler counted. This resolves unavailable checks in the second review (R10) and N2. A reviewer of the future prototype should reject any report equating protocol lands with tested program behavior.

Execute each frozen literal validation command under its recorded interpreter (`sh`, `bash`, `python3`, or direct executable); an unrecorded interpreter makes that command unavailable. Never rewrite shell syntax or silently substitute a tool. The checker captures raw output privately in scratch and exports only counts, status, runtime and hashes. This **contract choice (N2)** lets a reviewer distinguish a candidate failure from a command that could not run with the available environment.
