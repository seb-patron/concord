# Executable offline protocol: duplicate work and claim hoarding

This is a synthetic discrete-event experiment, not a measurement of Concord or an authorization to deploy. Implement the rules below literally. All times are simulated minutes, intervals are half-open, and a smaller numerical ID wins every otherwise unspecified tie. Every candidate uses the same event stream and the same exclusive code-unit policy under the [exclusive-unit decision (D-UNIT-1-EXCLUSIVE)](../../decisions.md). The historical v2 anchor is descriptive; causal comparisons use the matched code-only arm. The owner has already approved an offline research/test spike under the [issue-claim spike decision (D-ISSUE-CLAIM-SPIKE)](../../decisions.md), while a live pilot and product choice remain separate. The preselected primary rule below does not supply owner trade-off values.

## Reproducibility and common random numbers

Run seeds 0 through 99 in every cell. Use independent counter-based streams keyed by `(seed, event-family, issue-id, attempt-number, worker-id, draw-index)`; a stream value is the first 53 bits of SHA-256 of the UTF-8 key, divided by `2^53`. Encode numerical tuple fields as decimal and separate all fields by `|`. Draws for different families never shift if one arm skips an event. Define `U(a,b)` as `a+(b-a)u`; categorical draws use cumulative probabilities in stated order; exponential duration with mean `m` is `-m ln(1-u)`. Poisson gaps have `m=60/rate-per-hour` minutes. For every arm, materialize the same issue arrivals, scopes, attempt-specific declarations, hidden requirements, durations, background starts, worker preference, feedback, crash and advisory-response draws at initialization. Even an arm that never reaches an attempt consumes its assigned draw by this indexed construction. Dynamic attempts use their stable issue ID and ordinal, including retries. A retry continues its original required-work ledger; it never redraws the issue's work. Report stream-key version and seed with results. Use IEEE-754 binary64 for event times, no pre-comparison rounding or tie tolerance; exact equal timestamps use the event order below.

Events at equal time process in this order: owner close/override and expiry, accepted land, inspection/review/queue completions, publish/repair transitions, lease grants and queue turns, work completion/discovery, arrivals, worker dispatch. Within a class sort issue, attempt, worker IDs. A server call takes the sampled call latency and commits only at its completion; validate versions and fences then. A list snapshot is read at the beginning of its call, so it can be stale by claim time. Log the entire event ledger.

## Workload, base cell, and load definition

Each run lasts 480 minutes; finish the event ledger at 480 without draining. Create 30 open, prerequisite-ready issues at time zero, IDs 0–29. Issue arrivals after time zero are a Poisson process with exponential gaps; the base rate is **five per hour**. Give each arrival the next ID. Issue arrival time is the dispatch-ready time, including the initial 30. A completed issue is removed and does not spawn another arrival; any unstarted issue retains its original arrival age. Five worker slots exist at time zero and persist. Each released worker immediately dispatches again. At most one worker-managed writing, pending or repair issue per worker; a queued but unclaimed code request does not count as active. One principal owns at most two worker-managed claims across sessions; server-held published reservations are excluded from both caps. Assign each worker a distinct principal in the base, and use pairs sharing one principal only in the named sensitivity. A failed/released attempt may retry only after another eligible issue has been considered; cap at three failed reclaims per issue in a rolling 72 simulated hours, then mark for human review and exclude it until cutoff. This cap is synthetic, not product policy.

For a scenario with `W` worker slots and mean productive service demand `S`, define capacity as `60 W / S` issue starts per hour. Set `S=60` minutes exactly for load calibration, regardless of later stochastic phase times; therefore light, equal and twice-capacity offer `0.5W`, `W`, and `2W` new issues per hour. Base `W=5`, equal load, hence five arrivals/hour. The initial backlog is held at 30 for every load cell. Background starts are separate from issue arrivals and do not count toward offered issue load or primary numerator; base rate two/hour. They occupy code units, not a worker slot in the measured pool. Generate their starts as an independent Poisson process. Background scope size is one with probability 0.7 and two with probability 0.3, using the same scope sampler below. Each background writing hold lasts 30 minutes with probability 0.7 or 90 minutes with probability 0.3; it has no issue, review or repair, and releases all units at end. If a requested unit is busy, it queues on the common code wait line; its duration starts at grant. Count its blocked time separately and do not add its work to the primary denominator.

Use 60 canonical units numbered 0–59. For each issue choose scope size 1, 2 or 4 with probabilities 0.5, 0.35 and 0.15. Choose a shared hot unit uniformly once per seed. In the base mixed shape, independently flag 25% of issues for forced overlap. If flagged, place the hot unit first; fill the remaining distinct units by uniform sampling without replacement from the other 59. If unflagged, sample all units without replacement from units excluding the hot unit; incidental collisions between such issues are permitted. The zero and 60% sensitivities change only the forced-overlap probability. The shared-hot shape sets this probability to 1, the mostly-disjoint shape to 0. A background start chooses the hot unit with probability 0.5 in mixed/shared-hot shapes, otherwise samples distinct uniform units. Record realized cross-issue and background overlap separately from the forced-overlap flag.

An attempt's intended work scope is drawn from its issue home scope. For a competing attempt on the same issue, with probability 0.25 replace its full scope with distinct units sampled from outside the first attempt's full scope. With probability 0.10, independently, its initial declaration is empty and scope is learned after a ten-minute bounded investigation; otherwise its declaration is its intended scope excluding a hidden required unit. A hidden required unit is added to 10% of issues: draw one unit uniformly outside the initial scope, independent of the disjoint-attempt draw. The hidden unit is **required initial work**, shared across attempts for that issue. The new unit is discovered when 25%, 50% or 75% of initial writing has elapsed, each with probability one third, or at pre-publish reconciliation if publication is scheduled earlier. It is acquired through all-unit grow before writing continues; refusal preserves prior grants, with no edit to the missing unit. Required initial work cannot vanish because review gives no feedback. Independently, 25% of **first published revisions** receive conditional repair feedback; this adds a fresh repair task of 10, 30 or 60 writing minutes with probabilities 0.4, 0.4, 0.2, and one extra unit with probability 0.2 (uniform outside current scope). A later repair revision gets no further feedback in the base. No feedback means no conditional repair exists. A first publish occurs only after **all required initial writing and required-unit reconciliation**. The 40%, 70%, 90% publish fractions, equally likely, mark earliest attempted publish; if required work remains, postpone to its completion. No unused initial coding draw is discarded. Review feedback creates conditional work only after review.

Base initial writing duration is 10, 30 or 90 minutes with probabilities 0.25, 0.5, 0.25, divided equally across the required units for progress accounting. Pre-change research takes 5 minutes. Issue-first planning delay after issue grant is 0, 0.5 or 2 minutes, each with probability one third. Every list, issue-claim, code-request, link, publish and renewal call has latency 0.2 seconds at base; race delay between list and claim is two seconds. Delays occupy a worker while it pursues the issue. Inspection lasts 10 minutes, review 37, queue 60; deterministic base values. A revision then lands if still authorized. Rejection/repair feedback is delivered at review completion and prevents queue entry for that revision. If a newer revision supersedes it, old authorization ends. No checks fail in the base; faults supply explicit failures.

## Dispatch, signals and common code rules

Base selection is oldest open, ready issue visible in the worker's list; do not peek at future scope or code availability. Exclusive arms skip visibly claimed issues, while code-only and advisory arms may choose them. Under move-on, skip an issue only if a prior live refusal made its code blockage known to this worker. A stale list may still select it. For selection sensitivity, uniform-among-five-oldest draws an indexed uniform choice from the five oldest visible eligible IDs (or fewer if needed); worker preference sorts eligible issues by a fixed hash keyed by seed, worker and issue, and uses oldest arrival then ID only to break a hash tie. Assignment and presence are advisory: after a 30-second delivery delay, a worker observes **another worker's** signal with probability 0.75 and, if observed, yields with probability 0.75; otherwise it proceeds. A worker never yields to its own assignment or presence. Planned-owner initialization assigns every third initial issue to worker `issue-id mod W` at time zero; new issues are unassigned. A crash leaves assignment in place; a human clears it after 60 minutes. Presence is initially empty, begins on selection, has a five-minute expiry, and renews every 100 seconds only while the worker is actively planning/writing that issue. It clears at release or issue close. Assignment never exists in the presence-only arm. In the shared-principal sensitivity, pairing workers does not combine their run IDs.

All causal arms use the same canonical code-unit leases, complete-set atomic request, grow, fair first-in-first-out line, five-minute writing lease and renewal every 100 seconds while writing. Automatic enqueue follows the [automatic-enqueue decision (D-LEASE-QUEUE-AUTO)](../../decisions.md); the fresh-auth turn is a simulation default, not a settled product choice. Original enqueue time determines queue age; ties use intent ID. A turn is a **fresh-auth notification**, not an automatic grant: recheck issue/version, session and units after the call latency. A later conflicting request cannot barge ahead of an older compatible turn. On crossed growth, the youngest original intent by grant time (then ID) yields: release issue claim and all writing units, preserve draft and required-work ledger, requeue behind older work with its original priority age. If no grant after ten minutes of initial unknown-scope investigation, release. Before first publish, compare actual diff units to declared units; atomically acquire any missing units, refuse publish if conflict, release unused writing units, check exact revision footprint and fences. Publication ends blocking writing holds and creates revision-specific, nonblocking landing authorization. Code expiry pauses writing and requires reacquisition. All arms use identical server validation and checker. The historical v2 anchor instead refuses/retries without full grow or durable FIFO; on a hidden unit it abandons the attempt, releases units, and a replacement attempt starts after five minutes. It cannot be the causal comparator.

For the common move-on policy, refusal **without an issue claim** queues a code request and immediately releases its worker for another issue. On turn, if that worker is busy, cancel this request; otherwise it may take that issue after revalidation. The wait-for-same-issue sensitivity keeps the worker occupied until grant or a five-minute timeout, then releases it. A queue position grants neither issue nor code authority.

## Arm-specific ownership after code refusal

The code-only, assignment, and presence arms have no issue fence. They use the common refusal rule. Atomic issue-plus-code start grants both or neither; on code refusal it has no issue claim and uses the common rule. Issue-first immediate release obtains an issue fence, waits its sampled planning delay, then asks for code; refusal atomically releases issue claim, enqueues code request and frees worker under move-on. The bounded-pending issue-first variant instead retains its issue claim for **at most five minutes from code refusal**, retains the same worker exclusively, and occupies that worker slot while awaiting a fair queue turn. It cannot select another issue during pending. On turn, revalidate issue fence/version and atomically grant all requested units; if successful, begin writing. On timeout, owner close, expiry or rejected turn, revoke the issue fence, remove the pending request, release worker; only then may it take another issue. Pending renewal never extends this deadline. This variant intentionally pays occupied waiting time; applying move-on to it would erase the design difference. For the link-derived arm, linked change creation and initial code request are atomic; refusal creates no link and follows common move-on. An existing linked change may hold the issue while later code grow waits; apply youngest-yield recovery and close it on yield. Plain link ownership lasts until terminal change even if idle; lease-ended link ownership ends when its code writing leases end, including first publish. The link arm has no issue fence.

Writing issue claims expire after five minutes absent successful 100-second renewal. After first publish, an exclusive claim becomes a server-held reservation for the exact revision through inspection, review and queue; the worker is released from that issue and may work another, subject to one-active-issue counting only **worker-managed** writing/pending/repair. A server reservation does not occupy the worker or consume its principal's two live worker-claim slots. Maximum reservation age is 120 minutes from publish at base, including repairs; no implicit renewal. On timeout, cancel revision authorization, advance issue fence, release reservation and permit successor. On repair feedback, reserve the issue while a worker becomes available; the original worker has first right for five minutes, then any eligible worker may take fresh code leases under the still-current reservation and acknowledged issue version. Repair occupies a worker from dispatch through republish; its code leases are fresh. If no worker starts repair before reservation maximum, cancel it. An accepted land at or before cutoff counts once, closes issue and releases reservation/authorization. Aborted revisions and old drafts remain readable but cannot land.

For **every phase**—writing, inspection, review, queue and repair—owner override or owner close first advances issue generation, invalidates old issue fence and exact-revision authorization, cancels pending turns, and revokes that attempt's current code writing leases. In inspection/review/queue there may be no blocking writing leases, but the revision authorization still must be canceled. Override reopens eligibility immediately under a new generation; close makes the issue ineligible until a separately logged reopen, also with a new generation. Successor gets fresh issue and code grants; it cannot inherit the old verdict or fence. Normal accepted-land close is distinguished from owner close and counts a completion. If code expires first during repair, pause and reacquire; a live issue reservation alone never authorizes source writes. In advisory/code-only arms, override cancels the chosen attempt's code leases and revision authorization, clears its signal or planned owner only if the owner requests that, and permits another attempt; no issue-fence safety assertion applies. For link ownership, owner closes the linked change and cancels its authorization in every phase, then successor may link. Apply owner actions as explicit injected faults, not random base events.

## Occupancy, estimator, cutoff, and decision rule

A worker is occupied from dispatch through planning, calls, initial writing, blocked grow, code refusal while bounded pending, and repair. It is free after first publish during server inspection, review and queue; these phases continue to use issue reservation but no worker time. A move-on queued request consumes no worker time. Background work uses no measured worker. If a worker starts another issue while an earlier revision is under review, count its occupancy only once by taking the union of that worker's occupied time intervals. A repair waits for a free worker; no double booking. Log productive, blocked and idle-commitment minutes separately. The primary denominator is the union of occupied worker minutes between dispatch and release across all attempts, including failed/unfinished work; divide by 60. The numerator is distinct issues accepted and landed by minute 480. A zero denominator yields missing, never infinity. **Primary result:** accepted distinct issues per occupied worker-hour. Also report accepted issues per available worker-hour (`W×8`) as context.

For each seed, compute candidate minus matched code-only primary rate using its own denominator, then average the 100 paired differences. A paired seed means the two arms face the same pre-generated demand and draws. Use a two-sided 95% percentile interval from 10,000 paired-seed bootstrap resamples of the 100 differences; bootstrap resampling uses a separate SHA-256 stream keyed `bootstrap|cell|replicate|draw`. Sort bootstrap means and use ranks 250 and 9750, counting from one, as endpoints. Report interval endpoints, per-arm rates and seed-wise differences. Apply the same paired estimator and interval to duplicate, idle and recovery metrics. No unpaired pooling of attempt records.

At cutoff, all in-progress attempts are **right censored**: they contribute occupied time to minute 480, no completion, and their status/phase is reported. Start-to-land and recovery durations are not assigned artificial completion times. Report completed-only quantiles explicitly as conditional; additionally report restricted mean time-to-land and recovery time through minute 480 by integrating the observed unfinished fraction over time, with unfinished and unrecovered cases remaining in the risk set. Recovery starts at failure/override and ends at successor's first productive writing minute; if no successor, it stays censored at 480 and contributes its remaining time to the restricted mean. An issue becomes **demanded** at its first selection or refused advisory signal; until then its backlog wait is reported separately. Idle-issue minutes accrue while a demanded, ready issue has no active worker or server inspection/review/queue progress because a claim or advisory signal deters a start; code-blocked minutes are separate. For each issue, count that elapsed time once even if several workers are deterred. Duplicate minutes include planning/writing discarded after another attempt's accepted land or abandoned by a failed attempt that is later reimplemented; simultaneous losing attempts count too. Work still unfinished at cutoff remains unresolved, rather than automatically being called duplicate, and is reported separately. If a successor reuses reviewed work, record actual reused minutes, with zero and full reuse bounds. Base reuse is zero. Hoarding is an exclusive claim held beyond five minutes without planning, writing, inspection, review, queue or repair progress; renewal is not progress. Starvation is a demanded ready issue never started by cutoff. Secondary outputs also include per-phase wait, median and 95th percentile, refusal, failed checks, human actions, overdeclared-unit hold minutes and missing-unit wait/retry minutes. Never drop abandoned attempts from cost.

Before seeing results, the owner must set a minimum valuable primary gain and acceptable losses on duplicate and idle minutes, plus values for wait, compute, repair and human intervention. Until then, show per-metric results and threshold frontiers with **no winner**. Once set, a candidate wins only if its paired primary lower 95% bound exceeds the minimum gain, duplicate and idle upper 95% bounds do not exceed owner tolerances, and all applicable safety assertions pass. It loses on a safety violation or if its primary upper bound is below zero or a secondary loss lower bound exceeds tolerance. Otherwise say inconclusive. This is a preset rule, not a claim that the owner has approved numeric thresholds.

## Sensitivity matrix and deterministic fault checks

Run one-factor-at-a-time cells against the base, using the same 100 seeds: worker slots 2/5/10; load light/equal/twice; open backlog 10/30/60; units 20/60/120; overlap probability 0/0.25/0.60 plus shared-hot 1; hidden need probability 0/0.10/0.25; disjoint same-issue probability 0/0.25/0.50; no-known-scope probability 0/0.10/0.25; planning delay 0/0.5/2 minutes fixed; server latency 0/0.2/2 seconds; list race 0/2/10 seconds; advisory delivery 0/30/120 seconds and observed/cooperative probabilities 0/0.75/1; feedback 0/0.25/0.50; reservation maximum 60/120/240 minutes; assignment clear 15/60/240 minutes; refusal move-on versus wait; selection oldest versus uniform among five oldest versus per-worker fixed random preference ranking; principal matching run-plus-intent versus principal-only; reuse 0 versus full; cutoff 480/960. In a cell changing issue or unit count, regenerate IDs and scopes with the same keyed stream. At 960 minutes extend arrivals and background starts using their pre-keyed streams. Report all cells, including ties. Vary writing duration mixture by scaling every duration by 0.5 and 2, and inspection/review/queue durations individually to 3 and 218 minutes for the tail cell. All non-varied values remain base.

Run each fault once for every relevant arm at a fixed seed; assert state invariants, not a statistical rate:

| Fault | Required assertion |
|---|---|
| Two attempts, same issue, disjoint code | Exclusive arms have at most one valid issue fence; code-only/advisory may duplicate; link arm can duplicate in pre-change or replacement gap. |
| Busy unit, partial request, stale code fence, missing actual unit | No partial grant; no protected edit or publish without current exact code grants; failed reconciliation causes no push. |
| Crash before/after issue-first claim and between calls | No ghost grant; idempotent request returns same result; bounded pending times out; successor obeys one-active-issue cap. |
| Crossed growth on two workers | Youngest yields issue and code, older eventually progresses, retry retains original age, no infinite mutual wait. |
| Writing issue expiry or code expiry first | Old worker cannot write/publish; successor has new issue fence where applicable; code expiry pauses work even with issue claim. |
| Owner override and owner close in each of five phases | Old issue fence, revision authorization and any repair leases are invalid; close blocks successor until reopen, override allows fresh successor; no old revision lands. |
| First publish, long review, feedback/repair, cancellation | Writing exclusion ends; exact revision authorization persists until replacement/cancel/max age; repair uses fresh leases; server review does not occupy worker. |
| Hidden required unit discovered after proposed early publish | Publish waits or reconciles and completes required initial work; no accepted issue silently drops the required unit, even without feedback. |
| Same principal, multiple sessions and stale resume | Run-plus-intent matching prevents shared-token collapse; stale session cannot renew; principal-only sensitivity exposes collapse. |
| Issue version edit, removed unit, reopen, accepted land | New criteria acknowledged before publish; unused code unit released; reopen gives fresh generation; normal land counts once. |

No implementer may choose an outcome-relevant setting. Stated defaults for otherwise unmentioned mechanics: issue readiness is always true; there are no human actions, spontaneous crashes, failed checks, reverts, dependencies, semantic conflicts, or task reuse in the base; all servers and workers have unlimited event-processing capacity apart from stated slots; all code units have equal cost; no overtime after cutoff; a worker not dispatched is free and contributes zero occupied minutes; no queue position survives cancellation; and all unlisted probabilities are zero.
