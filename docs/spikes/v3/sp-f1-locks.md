# SP-F1: Locks and concurrency control for many coding agents

**Research question.** When do locks help or hurt on one repository, and what should v3 claims do? Source-by-source reading notes, fetch details, hashes, and word counts are in [sp-f1-locks-notes.md](reads/sp-f1-locks-notes.md). The coding-source distinction is central: a task claim, a file/symbol claim, a Git ref, the whole repository, and an external resource are different locks with different costs.

## Finding

Locks help when concurrent edits cannot be merged safely or cheaply, and a server can enforce an exclusive reservation on the actual resource. This is the case Perforce, Git LFS, Unity Version Control, and Unreal describe for selected binary/design assets. Locks hurt when they cover mergeable independent work, coarse scopes, or long task lifetimes: they create waiting, stale ownership, bypass/reacquire failure modes, and contention. Cursor's reported slowdown was caused by agent-managed locks on tasks in a shared coordination file; it is not evidence against server-enforced file/symbol claims. Cursor later reports hundreds of workers writing to one branch with minimal conflicts, and Anthropic reports avoiding an effective global merge-queue lock while accepting and repairing concurrent conflicts. Kung and Robinson explain the underlying trade: pessimistic waiting pays lock overhead and can deadlock; optimism pays validation, backup/retry, and starvation risk when conflicts happen.

There is no single lock policy across these resource classes. Task locks are scheduler coordination; code-unit claims protect edit intent; ref/land locks serialize shared pointer updates; whole-repository locks suppress almost all concurrency; external-resource locks may be necessary for a single-writer device/account/service. Never infer one class's measured costs from another.

## When to use exclusive vs shared/optimistic claims

| Case | Better mode | Reason | Evidence |
|---|---|---|---|
| Binary/design asset whose format has no useful merge; one editor must produce the next valid version | **Exclusive** | Avoids unrecoverable overwrite/merge work; server can reject competing writes | Git LFS API/wiki; Perforce `+l`; Unity lock rules; Unreal binary assets [notes](reads/sp-f1-locks-notes.md#perforce-file-type-modifiers) |
| Shared task record whose only purpose is assigning work | **Shared/optimistic state plus scheduler ownership** | Stale agent-held task locks created severe waits; atomic compare-and-swap or explicit task assignment is narrower | Cursor “Learning to coordinate” [notes](reads/sp-f1-locks-notes.md#scaling-long-running-autonomous-coding--cursor) |
| Independent functions/rows/sections in text sources with reliable unit identity | **Shared/optimistic by default; exclusive opt-in when conflict cost warrants it** | Validate overlap at land and retry/merge disjoint changes; narrow units reduce false contention | Kung & Robinson; Jujutsu; v2 unit resolution [notes](reads/sp-f1-locks-notes.md#on-optimistic-methods-for-concurrency-control--kung-and-robinson) |
| Many edits to one map or structured file | **Decompose into actor/row/symbol units first** | Representation-level separation reduces both merge conflicts and need for coarse locks | Unreal One File Per Actor [notes](reads/sp-f1-locks-notes.md#unreal-engine-one-file-per-actor) |
| Shared ref update / landing | **Short server-side serialization or compare-and-swap** | The ref is one shared mutable pointer; serialize its update, not all preceding edit work | Anthropic Scion and Jujutsu [notes](reads/sp-f1-locks-notes.md#redesigning-source-control-at-anthropic--scion) |
| Whole repository or all-file lock | **Avoid by default** | It prevents disjoint work and makes lock duration the system throughput ceiling | Cursor, Anthropic, Kung & Robinson [notes](reads/sp-f1-locks-notes.md#scaling-long-running-autonomous-coding--cursor) |
| Truly single-writer external resource (for example, a non-shareable device or mutable deployment target) | **Exclusive resource lease** | Concurrent writes cannot be merged or safely reordered | Inference from the lock/optimism principles; not directly tested by these coding-tool sources |

## Recommended v3 claim model

This recommendation changes the current exclusive-lease direction in D-UNIT-1-EXCLUSIVE and so needs Seb's explicit decision before implementation. D-UNIT-1-EXCLUSIVE currently says each lease is exclusive on its file or symbol unit; D-SYMBOL-LEASES separately approves symbol-size units. The evidence supports a hybrid model:

1. **Default mode:** `shared` advisory/presence claim on mergeable source units, with server-side overlap detection at submit/land and optimistic merge/retry. A shared claim never promises protection. Keep a repository policy switch to restore exclusive-by-default while the owner decides whether to supersede D-UNIT-1-EXCLUSIVE.
2. **Exclusive units:** default exclusive for declared non-mergeable binary/assets and explicit owner-protected paths; support explicit exclusive claims for high-conflict or expensive-to-recreate text units. Require the server to enforce exclusivity on write/land, not agent convention.
3. **Granularity:** use symbol, Markdown section, or keyed row only when both sides prove stable identity; widen to file on ambiguity. Allow path prefixes only for a deliberately protected subtree. Prefer data decomposition (for example One File Per Actor) over locking one large collaborative file.
4. **Expiry:** server-owned lease with a bounded initial TTL, heartbeat renewal while an active run owns the unit, immediate release on submit/cancel, and expiry on dead session. Start at a short measured interval (e.g. 5 minutes TTL, renew each minute); these values are experimental, not findings from the cited products. Notify holders before expiry and expose holder, intent, issue, and expiry.
5. **Scheduler avoidance:** issue readiness and task assignment prevent duplicate task work; claim conflicts should not be used as a substitute for task scheduling. Shared/optimistic code units do not wait in an exclusive queue. For exclusive conflicts, offer a FIFO wait line with ETA and permit work on other units while waiting.
6. **Owner controls:** inspect claims and policy; release, pause, reassign, or force-release with reason and an auditable event; set per-path/per-extension mode; pause new exclusive grants; and define human-only protection for review. Do not silently revoke an active lease.

## Measurement plan

Run a staged, fixed-workload comparison on representative repositories and replayable real task sets. Compare current exclusive claims, shared/optimistic claims, and the hybrid policy; hold task decomposition, agent/model, checks, and land ordering constant. Include text-only disjoint edits, overlapping symbols, shared config/lockfile edits, generated files, and non-mergeable binary assets. Use a bounded swarm size progression rather than an unbounded load generator.

Record per unit class and concurrency level: claim wait and hold-time distributions; abandoned/expired claims; overlap rate; merge conflict rate; validation failures and retry count; agent time spent waiting, repairing, and redoing work; time to land; landed changes per wall-clock hour; regressions/reverts; owner overrides; and correctness/check failures. For the exclusive asset cohort, compare prevented collisions and wait time. For the optimistic cohort, compare conflict repair cost and retry loss. Use matched tasks and multiple fixed repetitions, publish confidence intervals and raw counts, and stop expansion if correctness regressions rise. Choose policy by total useful landed work and recovery cost, not raw claim count. Review the result with Seb before changing D-UNIT-1.

Only Anthropic and Cursor describe large coding-agent operations directly; vendor locking docs describe asset workflows, not agent swarm throughput.
